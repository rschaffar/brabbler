# 0007 — Session-scoped Git workflow preferences and bounded local Git review

## Status

Accepted for session preferences, worktree continuation, guarded commits, read-only Git comparisons, explicit verification, and separately approved local merge.

## Context

Pi Web already groups linked worktree sessions under one project, but each chat has its own persisted cwd. A project-level preference should guide new chats without retroactively changing existing or legacy chats. A browser selection of a branch or a commit must not silently authorize an unseen integration, deletion, or remote publication. Relying on an optional external `git workflow` CLI would make the feature depend on an additional executable (and its platform availability) at runtime.

## Decision

- Implement a self-contained Pi Web policy store and Git operations using the installed Git executable, not a mandatory optional workflow CLI. Project defaults are private Pi Web data keyed by the canonical main/linked-worktree project root; a new chat snapshots the default or explicit new-chat override into a versioned Pi session custom entry. Absence means no saved policy; explicit `null` means opt-out. Forks/clones inherit the saved snapshot. An initialized but unpersisted chat currently refuses a later override rather than pretending it can update the pending initialization.
- Persisted, idle session edits append a new policy entry. The hidden extension reads that entry at `before_agent_start`, so the **next run** receives updated guidance without a browser reload or wrapper rebuild; there is no mid-run policy change. Chat-only excludes extensions. A policy supplies intent (checkout mode/base branch, on-create continuation/fork/stay, agent/manual commits, optional local integration target and method); it does not perform those operations or override stricter repository instructions. Agent shell tools are not confined by this policy.
- Keep checkout mutation attributable. The sidebar creates/attaches a worktree only with a selected local base and checked full tip(s), not a remote ref or implicit HEAD. Workspace workflow controls let a user confirm idle relocation or fork into an existing registered checkout. An ordinary agent with a saved worktree-mode policy can also explicitly call `git_workspace_start` to create a new worktree from a supplied full expected base OID; that action durably records the selected `onCreate` intent. Only its own idle run settlement attempts an automatic continuation/fork, with an exclusive private claim before any copy/move. The receipt is never replayed on browser reconnect or restart, and a failure leaves all resources for manual inspection. One agent-owned automatic start per chat is supported. Saving a preference or using the sidebar does not trigger a move. No uncommitted files are copied; they remain in the source checkout.
- Share a bounded preview/confirm commit engine between the browser and the session-bound agent tool. Human confirmation is independent of `commits: agent`; the agent tool requires a **saved session** policy granting agent commits. Preview captures the selected whole-file candidate tree along with branch, HEAD and index state; confirm re-derives the candidate and refuses stale or dirty-index states. Refuse unsupported hooks, signing and filters rather than silently executing or bypassing configured behavior. A ref update followed by failed index finalization is reported as **partial success with the commit ID**, never as a safe-to-retry failure. This is not an atomic transaction against arbitrary other Git writers.
- Provide reusable read-only tree/series comparisons derived from saved session target and feature branch refs. Require the target on the feature's first-parent chain. Compare the proposed merge tree with the target tree, or a single first-parent commit or contiguous cumulative range; recheck refs and reject stale/oversized patches.
- Verification and execution are separate from review. Run only explicitly selected saved argv checks (without a shell), storing bounded private logs and state-bound process-local success receipts. The user must separately prepare a full candidate-diff plan and approve that exact plan ID. Support only ordinary unsigned, hook-free **non-fast-forward local merge** into a distinct registered clean checkout, with conditional ref update, in-process checkout/agent gate, and retained private recovery data on partial failure. Reject unsupported Git configuration/index states; neither an `ff` nor a `squash` preference silently changes the method. No automatic rebase, cleanup, fetch, push, or publication. External Git processes remain outside the admission gate; exact-state checks reduce, but cannot eliminate, their races.

## Consequences and boundaries

Preferences may be edited without restarting the browser; the next agent run sees the saved snapshot, but no preference is an approval for an exact unseen integration or remote/cleanup action. Human commit confirmation applies to the displayed candidate identity, not merely a working-tree diff; separate repo instructions and manual verification still matter. Existing chats do not follow changed project defaults. The worktree UI and Git plumbing are implemented without the optional CLI, but **Windows portability of this workflow remains unverified**; do not claim cross-platform completion until tested. See [Session Git workflow](../git-workflow.md) for operational steps and recovery.

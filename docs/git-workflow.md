## Independent invocations and native concurrency

**An operation proceeds on its own authority and exact current Git state, not on another session's inactivity or settled history.** There is no application checkout gate, common-directory reservation, usage/deletion lease, historical-success admission or persistent quarantine in the replacement contract. Another session's activity, failed check, uncertain outcome or missing/corrupt history cannot veto it. Distinct invocations can address the same repository; the same consumed invocation cannot execute twice.

Each operation captures its physical source/target, exact refs, index/content, candidate and original authority. Ask approves only that candidate. An explicit `confirmation: "none"` requires its own fresh eligible saved authorization; it is neither an implicit Ask answer nor a check waiver. Private process-local invocation, receipt and native-proof identities cannot be reconstructed from IDs, copied objects, JSON or history after restart.

Commits retain native index protection and exact expected-ref compare-and-swap (CAS). Checked-out FF, non-FF and preparation apply use the shared native transaction: pin physical Git/worktree administration, retain the original target index and acquire the real `index.lock`, then obtain Git's acknowledgement of a **prepared** source-verify/target-CAS ref transaction **before checkout file effects**. Revalidate original bytes, modes, symlinks, HEAD/index bindings and authority under those protections, apply through a private index, verify the exact result, write/fsync through the original owned lock descriptor, commit the prepared refs, and install that same lock inode. Preparation reverses which captured branch is updated and which is verified. No hooks, signing, configured filters or method fallback are introduced.

Native locks last only for bounded native effects, never human waiting, checks, coding or optional history I/O. Genuine Git contention or changed relevant state rejects the captured invocation; there is **no automatic target-movement retry, rebaseline, rollback or transfer of approval**. Inspect the new facts and invoke a separately authorized new candidate when appropriate. No application-retained or recreated index lock represents quarantine. A naturally crash-left Git lock is not automatically deleted by another invocation.

Files, index and refs are **not crash-atomic together**. Report checkout application, ref commit sent/acknowledged, index installation and observed partial effects separately. Lost native acknowledgement can mean uncertainty; optional diagnostic failure cannot make an acknowledged native result unknown. Preserve actual OIDs/checkpoints and inspect partial results manually rather than repeating the operation.

The user accepts responsibility for concurrent edits and for not deleting a worktree still needed by a session or terminal. Native validation is not a sandbox against same-user or arbitrary external filesystem writers. Session/terminal inventory is informational, not exclusive ownership. Git operations never move or fork chats automatically to make concurrency or deletion work.

## Settings, authority and the Workflow home

**Workflow** in the top bar is the single home for Global, Project and Session settings. The selected project can differ from the chat cwd. Drafts, revisions, inheritance and resets are keyed by scope and canonical project; saving in B cannot erase A's draft. Inherited displays use saved ancestors, not another scope's unsaved draft. Selecting a project or saving settings starts no Git action, agent, task adoption or chat move. The read-only Git Explorer remains independent.

Resolve settings through **Global → canonical Project → Chat × Project**. Missing means inherit; explicit `null`, `false` and `[]` are saved values. Ordered recipe lists replace rather than concatenate. Project defines `mainBranch`; `baseBranch` and `targetBranch` can name a local branch, `null`, or `:project-main`. The symbolic value resolves only against that project's main. Global may use symbolic/null branches, not named branches or nonempty recipes; newly saved Chat × Project overrides cannot introduce branch names/recipes either. Older named Global/unqualified Session values remain readable without gaining new consent. `delivery: pr` or `leave` prohibits local integration and grants no fetch, push or PR action. Cleanup defaults to retain.

Global/project settings live in private `pi-web/git-workflow-settings.json` under the agent directory (`~/.pi/agent` by default, or `PI_CODING_AGENT_DIR`). Linked worktrees share canonical project identity. Legacy `git-workflow-defaults.json` stays readable until new settings replace that project's defaults; resetting the new override does not resurrect old defaults. Saving defaults does not retarget a legacy captured task; its idle **Apply** action is separate metadata capture, not authority for selected operations.

**Editor revisions and execution authority are different.** Global/project editors use whole-document revision CAS to avoid overwriting another editor. An invocation instead retains its original monotonic relevant authority baseline, captured **before asynchronous discovery**. Canonical caller and selected project scopes discovered later are derived from that original baseline, never recaptured. Relevant supported settings/grant/trust/tool/session writers revoke their own affected invocation even on change-and-restore and across awaits; unrelated project/session writes are neutral. Global changes remain relevant. Final synchronous guards follow awaited checks without yielding before native effects. A current-value hash or newly read Allow cannot revive the old invocation.

Deny, Off/Manual/disabled modes, chat opt-out, Pause all, active tool/caller capability, allowed roots, trust and stronger project/user instructions remain independent restrictions. Selecting Beta from an Alpha chat uses Beta's policy and recipes, while Alpha's canonical Project, own Chat × Project and unqualified chat negatives still clamp the request. Beta Allow cannot cancel Alpha Deny or borrow another chat's consent. Unknown canonical identity fails closed; a UI display grouping is not a canonical authority key.

**Turn off for this chat** is a reversible opt-out for an idle persisted ordinary chat. The next wrapper omits managed Git tools/guidance; already-loaded calls still check the live opt-out. Global/Project/Session On and Resume all cannot override it. Turning it back on restores prior captured metadata, not a passing check, approval or waiver. Historical review remains available. **Pause all managed Git actions** is unconditional and cannot be overridden by lower scopes. Pending approvals cannot bypass revocation; checks observe cancellation/revocation. These controls are not a shell sandbox.

**Managed Git tools only · guidance** defaults On with the same inheritance. It tells the agent to use guarded tools for supported work; Off permits alternatives only where independently allowed. Neither setting authorizes shell fallback after a denial. Ordinary questions need no Git status/setup ritual. `git_workflow status` is optional discovery. Chat-only loads no workflow/commit extensions; read-only/Chat-only agents and subagents cannot escape their mutation restrictions. An operator's permitted human actions remain distinct from agent tool eligibility.

Commit availability (Off/Manual/Ask), action confirmation and verification are separate choices. Manual refuses agent commits but permits eligible human actions; Off refuses both. Each workspace, commit, preparation, check, integration and cleanup confirmation preference has its own origin/reset. Saving `none` alone is **not Allow**. An explicit draft action can set new agent commits to Ask availability plus confirmation none, but does not save, override old restrictions, capture a task or create a grant. Automatic scheduling remains unsupported.

### Agent-proposed settings

A persisted ordinary chat can call `git_workflow_propose_settings` with bounded Global, Project or Session field changes. Project proposals identify an allowed physical registered checkout; Session proposals can target that chat × selected project without moving it. Omitted values reset to inherit; explicit null/false/empty values do not. The card shows saved/proposed overrides and effective values. **Apply settings** uses the same revision-checked write path as the editor; **Dismiss** writes nothing. Creating the proposal writes nothing and starts no Git work.

Session Apply requires an idle persisted ordinary chat; Global/Project Apply does not. Stale revision, changed project or moved chat needs a new proposal, not an implicit merge. Process-local proposals expire after 30 minutes and cannot be recovered from a transcript or restart. This is an authenticated operator convenience, not isolation from a same-user agent with shell/browser API access.

## Select a project without moving the chat

**Configuration project → Use project** selects an allowed physical registered Git checkout. Agent selectors are **`repositoryPath`** (canonical primary repository root) plus **`checkoutPath`** (physical registered checkout root); optional `workspaceBranch` must match its local checked-out branch. Duplicate registrations, detached/unregistered checkouts, changed identities or denied roots refuse. Branch names alone do not identify a repository.

For compatibility, `repositoryPath` alone can name an allowed registered checkout seed and `workspaceBranch` select within it. Omitting both deliberately uses the actual chat checkout, optionally another branch in that repository—not the last browsed project. A lone `checkoutPath` refuses. Selection never retargets shell/file cwd, session storage or loaded instructions. A positively verified physical non-Git caller can explicitly select a Git project; ambiguous/failed Git discovery is not that proof and does not widen special no-confirmation commit eligibility.

Project-qualified preferences are plain `pi-web:git-project-settings` entries. Forks can copy preferences, not invocation authority; old unqualified overrides/tasks are not imported across projects. New matching-project negatives clamp legacy actions too, including nested caller directories. A Project PR/leave restriction cannot be cancelled by a Chat × Project local override.

Browser read-only inspection uses `GET /api/git/inspection?repositoryPath=…&checkoutPath=…` and `POST /api/git/inspection` with selectors, `targetBranch` and `selection: { kind: "merge" }` or `{ kind: "commits", commitOids: [...] }`; optional `workspaceBranch` must match. POST is not approval or an execution token. Existing session-bound `/api/git/review` remains separate.

Explicit-project comparisons require Linux directory-descriptor binding. Captured checkout/Git/common directory instances are read through `/proc/<parent>/fd` with explicit Git arguments, not rediscovered through a mutable `.git` pathname. Recheck before/after capture and before return; unavailable descriptor support refuses without a weaker fallback. Status/settings do not need that comparison mechanism. Full patches stay out of ordinary tool-result text.

## Selected operations: current public contract

The public TypeBox schema is in `lib/agent-git-workflow-extension.ts`; dispatch enters `lib/git-selected-operation-runtime.ts` before legacy task gates. This is the migration's source API, subject to the acceptance notice above. Narrower legacy capability summaries are not the whole selected contract.

`git_workflow.operation` accepts `status`, `preferences`, `review`, `commit`, `integrate`, `artifact`, `workspace`, `prepare`, `verify`, `cleanup`, `reconcile`. Inputs are flat public fields, not private callbacks, proof objects, invocation owners, policy/receipt objects, commands or launch options. Unknown and wrong-operation fields refuse. Provider accounts and credentials are not Git arguments; never put secrets in recipes/history.

Mutations require a persisted ordinary caller, known capable active tools and their own live authorization, original resource/candidate binding and native checks. Default confirmation is Ask. Each explicit `confirmation: "none"` additionally needs that action's fresh effective saved Allow, selected confirmation none and compatible instructions. Deny blocks even Ask.

| Operation | Additional accepted fields and behavior |
| --- | --- |
| `workspace` | `workspaceMode: "current"` is metadata only, accepts selectors and starts nothing. `"create"`/`"attach"` require `destinationPath`, `newBranch`, `baseBranch`, `expectedBaseOid`; attach also requires `expectedTipOid`, while create rejects it. OIDs are full lowercase 40/64-hex local tips. No implicit HEAD, remote base, existing-name fallback or chat move. |
| `prepare` | Optional `targetBranch`, `targetCheckoutPath`; target must be the saved explicit **Project main** and its registered checkout. One bounded rewrite attempt or truthful `already-prepared`, never checks/integration afterward. |
| `verify` | `stage: "none" \| "commit" \| "integration" \| "handoff"` (default integration), optional `checkIndexes`, `revisionDependency`. Indexes are distinct original saved recipe positions, integers 0–63. No inline checks, target selector or command override. |
| Selected `integrate` | Optional `targetBranch`, `targetCheckoutPath`, `receiptIds`, `revisionDependency`. Saved local target/method and required integration-stage checks govern; contradictory targets and inline checks refuse. Use explicit repository selectors to avoid the legacy path. |
| `cleanup` | Optional exact `ignoredNames` (no globs); independently authorized eligible source worktree **and local branch** only. No force, target override or automatic follow-on. Own-caller-checkout deletion retains the original authority through the authenticated removal transition below. |
| `reconcile` | Optional matching `targetBranch`, `targetCheckoutPath`; fresh independently proved clean already-prepared state against Project main. Not replay, rebaseline of an old approval or a quarantine reset. |
| `commit` | Explicit complete changed `paths`, exact `message`, optional `mode: "whole-file" \| "staged"`, `confirmation`, `receiptIds`. Also available through `git_commit operation: "commit"`. |
| `artifact` | Only `actionId`, required UTF-8 byte `offset`, optional `limitBytes` (4–24576). No selectors or mutation authority. |

`status` accepts selectors only. `review` additionally accepts a local `targetBranch` or selected saved target and optional ordered consecutive `commitOids`; it is read-only. `preferences` is legacy compatibility, not selected execution policy. Selected integration is chosen by repository selectors or selected receipt/dependency/target-checkout arguments; top-level schema acceptance does not make every field valid for every operation.

### Commits and no-confirmation eligibility

Selected commits require Linux physical-resource checks, canonical repository plus physical registered checkout, exact paths and message. Ask captures one exact candidate for approval. Allow alone never suppresses that question.

Both commit aliases accept explicit none only with fresh effective saved commit Allow, selected `commitConfirmation: none`, an enabled managed Ask caller and **untouched, session-ID-bound persisted ordinary creation provenance**. Old, legacy, copied/forked, recreated or recaptured chats cannot silently acquire that eligibility. No human decision is fabricated. Stronger caller/selected-project restrictions still apply, and authorization is checked after preview and at the native effect boundary.

Every required saved commit-stage recipe is enforced through the common gate, including Ask, none, manual/browser and legacy confirm. Pass authentic current `receiptIds`; missing required evidence blocks commit. Check Deny can therefore block a commit despite commit Allow. No required recipe yields only truthful `no-required`/`no-defined`, never a waiver of repository instructions. Unsupported inherited required recipes refuse rather than disappear.

### Saved checks and truthful evidence

Selected checks execute **saved canonical source-Project recipes only**. Effective recipes must match that list; Global or Chat overrides cannot silently substitute. Recipes support `label`, executable/argument `argv`, optional checkout-relative physical `cwd`, bounded literal `env` and exact `requiredStage` (default integration). No shell strings/substitution, URLs, obvious credentials or unknown fields. Bounds: 12 recipes, 32 arguments after the executable, 80-byte labels, 256-byte executable/cwd, 512-byte arguments/values, 32 environment entries and 8 KiB overrides. Environment sanitation does not sandbox project code.

Stages are exact, not cumulative. `none` recipes are optional/manual and run only when explicitly selected by index; omitting indexes runs nothing at that stage. Commit, integration and handoff require their own stage recipes. Direct-main, handoff and optional checks need no fake target, second checkout or task. Empty selection issues no passing receipt. Check execution permission is independent of commit/integration permission; confirmation none **never waives required checks**.

Each explicit batch has its own original process-local cohort, with each declared member entering once. Independent calls—even from the same session—do not silently become sibling checks. The native required-batch validator authenticates actual private attempt/settlement/registration membership in the **same original cohort**, exact required saved indexes and corresponding unique ordered receipt IDs. Mixed, partial, duplicate, reversed, unpublished or optional-superset sets refuse. Public cohort IDs/index metadata are display information, not proof or authority; original leaf source/policy/physical/expiry checks remain mandatory at capture and final native use. A failed, cancelled or uncertain member retires only its own cohort; a late completion cannot reopen it. Another session's successful current cohort remains usable. A failed current batch never silently substitutes older passes; an independently selected older complete batch still needs its own current validation. Passing receipts come only from authentic successful native execution and final source/authority validation, not an exit-status-shaped callback, diagnostic row or copied receipt.

Fresh snapshots carry `dependencyVersion: 2`: selected/working evidence names its source ref, paired evidence its feature/target refs, rather than hashing all unrelated repository refs. Historical snapshots are not upgraded into fresh proof. Own relevant source/target/index/content/recipe/authority movement still invalidates affected evidence. Arbitrary commands can have external dependencies not represented by these bounded snapshots.

**Working-workspace receipt/snapshot v3** uses physical manifest v2: HEAD/index tracked-path union, index bytes, nonignored physical contents, modes, symlink bytes, absent paths and bounded inventory. It tests the actual possibly dirty workspace, **not an isolated selected commit tree**. Partial staging remains supported; unstaged fixes and unrelated staged changes may be visible to checks but absent from the commit. Summaries explicitly retain `evidenceScope: "working-workspace"`, `candidateTreeVerified: false`, `repositoryChecksWaived: false`.

**Source-only clean-checkout v2** serves selected integration/handoff/manual stages; **legacy paired v1** binds feature and target. They are not interchangeable with each other or dirty-workspace v3. Fresh dependency-v2 clean/paired snapshots bind raw physical bytes, modes and link bytes, rechecked before/after execution, at publication and fresh use—not Git's cached-stat cleanliness. Fresh-use authority is captured before its first await and retained through final callbacks/getters; it cannot be rebaselined from the issuer's still-valid receipt. None claims the resulting candidate/merge tree was tested. Ignored caches, symlink targets and external inputs are outside complete content coverage. Working-manifest bounds include 20,000 paths, 1,024 directories, 128 MiB content, 16 MiB/file/index and 60 seconds capture; unsupported/excess state refuses without truncation.

Linux checks require positively verified systemd user-service cgroup containment and process accounting. Cancellation supervises and attempts cleanup of the invocation's own descendants. Incomplete cleanup is non-success/warning for that invocation, not cross-session quarantine. Active or uncertain spools are not retention input and are not pruned. Containment is not isolation from other sessions or external writers.

**Legacy recipe limit:** the paired legacy/browser runner deliberately refuses extended `cwd`, `env` or explicit `requiredStage` fields, including `requiredStage: none`. Do not drop/filter required siblings to make a recipe fit, relabel paired evidence as selected evidence, or claim every editor recipe is executable through the legacy browser. Modern selected v2/v3 paths support their own stages and recipe extensions. The browser runs one explicit required-check batch. Independent per-check calls are not a complete original cohort merely because every row says passed; a failed current batch does not fall back to old passes.

### Preparation, reentry and integration

Preparation never rewrites the explicitly designated Project main and refuses when it cannot establish that designation. Other branches are assumed private under the accepted policy unless positive local sharing/publishing evidence or stricter instructions blocks rewriting. Missing Pi Web creation provenance alone is not a blocker; no fetch guesses privacy. Dirty/conflicted/unsupported history, active operation markers and unsupported Git policies refuse. Preparation verifies exact physical tracked blob bytes and modes through pinned descriptors, including unchanged paths, not cached-stat status. Bounds include 10,000 entries, 64 MiB total and 8 MiB/file.

Every actual rewrite returns new source OID, captured target OID, scope and action ID to the agent before any later stage. Original native completion—not successful history persistence—issues an unpredictable process-only `revisionDependency`. Dependent verify/integrate must use it in a **later assistant tool turn**; prequeued/batched siblings cannot skip agent assessment. This proves control flow, not semantic correctness. Unconsumed freshness is at most five minutes from native completion; a consumed check launch has a separate completion window capped at 30 minutes, with selected execution capped at five minutes per check. Only actual successful completion can issue a successor. `already-prepared` mints or refreshes nothing.

After adaptation, expiry or a settled recoverable launch, explicit independently proved `reconcile` can renew ordering with **zero carried receipts**, at most three times per live operation scope. It does not replay or revive the old invocation, borrow foreign history or release quarantine. An active/unknown own launch cannot yield restored authority. Restart/history cannot restore a dependency, approval, receipt or cleanup capability.

Integration is separately authorized for the exact candidate and target using saved **FF-only** or ordinary unsigned **non-FF merge**. There is no method fallback, hidden prepare/check/commit, local handoff override or remote action. Distinct clean registered source/target checkouts, supported policies, required stage receipts and exact refs remain mandatory. No required integration recipe means truthful no-required evidence, not a fabricated passing test.

A moved target invalidates the old candidate. Native no-effect/partial/unknown classification must come from the original native result/error, not message matching or reconstructed proof. Return the facts to the agent; no automatic retry, movement budget loop or authority rebaseline. A new preparation, verification and exact approval may be required. Partial results preserve actual checkpoints, not an invitation to repeat.

### Workspace creation and cleanup

Workspace create/attach authenticates explicit local base/tips, clean source/base state, destination/parent identities and actual native result. Repeated selected calls need no legacy one-transition-per-chat allowance and schedule no continuation/fork. Known partial directory/branch/worktree creation is reported, not rolled back or retried. Attach provenance is not create provenance.

Retain is the default. Eligible cleanup needs explicit saved `worktree-and-branch`, separate Ask or qualified none, **genuine original private create and integration proofs**, safe integrated history, exact source/target/main identities and unchanged supported file state. History cards or journal success cannot supply provenance. Primary/main/target checkouts remain protected. Exact ignored-data deletion always asks, even under Allow/none. Neither a vanished checkout nor an old creation row permits deleting whatever branch remains.

There is no positive idle-use inventory prerequisite or continuous usage lease. Deleting a used worktree is the user's responsibility, not a reason to move its chats automatically. Own-checkout deletion uses the **same original caller and fence**: `bindGitCheckCleanupCandidate` binds the original native candidate before effects; `acceptGitCheckCleanupRemoval` authenticates that exact candidate/removal pair through fixed private native readers at the first removal handoff, **before any ordinary fence or caller-policy read after disappearance**. A premature ordinary read revokes that fence rather than accepting a new baseline. Copies, IDs, old/foreign pairs and reconstructed metadata cannot establish the transition.

The private `git-check-cleanup-authority.ts` helper pins surviving project/common/target/main/parent identities and checks exact source/admin absence on subsequent reads. Policy readers retain the original canonical caller classification/resources and project scopes while reading current policy, Deny/grants, tools, pause, opt-out and trust; original trust generations and the original-path live trust decision remain binding. Native refs/index/config/hooks and exact approval are still independently checked. No new fence, omitted caller path, fake non-Git/moved caller or chat relocation is introduced. Same-pair acceptance is idempotent; unexpected replacement or relevant revocation permanently invalidates the original fence.

Native worktree removal and conditional branch deletion are separate effects. Report known removal, remaining branch and uncertain/partial facts truthfully; optional diagnostic failure cannot revoke native acknowledgement or stop a valid subsequent boundary merely to publish history. No force, automatic retry, rollback, repository quarantine or cleanup after integration is implied.

Legacy resource-using tools support `workspaceBranch` in the calling chat's repository; omission means its checkout. In an idle persisted ordinary chat, capture legacy task settings, name a goal, select an originating request from the current branch and a registered checkout, then list explicit Markdown dependencies. The app does not follow prose links automatically, fetch URLs or execute resources.

Preview discloses exact linked physical destinations before reading; explicit destination approval permits only those reads. **Adopt reviewed task metadata** publishes reviewed immutable snapshots and a generation head, not a Git action or loaded-instruction refresh. There is no review checkbox or response timer. Replacement, cancellation, expiry/restart or changed source/session/settings invalidates the live preview. Supported settings writes, including change-and-restore, fence these legacy reviews through their own write epoch; that epoch is not the replacement Git invocation authority baseline.

Private records live under `pi-web/git-task-bindings/v1/`; `pi-web/git-workflow-write-epoch.json` remains separate legacy metadata fencing. Copies/forks/imports do not inherit bindings; moves/settings recapture invalidate them, including failed moves. Release is a tombstone. No transcript anchor, fabricated user turn, wrapper or grant is created. Malformed/missing namespace evidence cannot reconstruct authority. A current disk snapshot does not prove loaded instructions or complete prose-policy interpretation. Private storage is not tamper-proof against same-user writers.

## Durable action history and optional diagnostics

Live exact candidates, Ask requests, native capabilities and required receipts are independent of optional diagnostic storage. Failure to write a record, anchor, log or artifact reports unavailable diagnostics; it cannot suppress the rightful live Ask, authorize execution, veto another invocation or turn known native completion into unknown. Missing mandatory native evidence still prevents that invocation from claiming success. Only the original live request may expose approval controls; history is always read-only.

Cards distinguish candidate/prepared identity, decision and actual result. A prepared merge/commit OID does not prove its ref was updated. A partial integration result may contain only the proposed object; inspect measured ref/index/file checkpoints. Forks can display inherited history references, not capabilities. Tiny plain SDK `pi-web:git-action` custom anchors contain version/action ID, never patch-sized model context or fabricated user messages. GETs do not create AgentSessions; small SSE notifications and GET refresh reconcile views. Standard SDK HTML export does not include these private artifacts.

Completed diagnostics use one fixed, physically pinned **`<agentDir>/git-diagnostics-v2`** namespace: **16 MiB records, 100 MiB logs, 64 MiB artifacts** (180 MiB combined full-envelope targets). Per-item bounds are 256 KiB for record envelopes; log and artifact payloads are limited to 8 MiB and 2 MiB respectively, with at most 1 KiB envelope overhead. Immutable no-replace publication binds retained artifacts to the exact record summary/digest/size. Only terminal finalization submits artifact copies; the exact active candidate remains private in memory and is never quota-evicted.

Each append accounts for aggregate bytes and directory slots, including both members of a record/log pair. The entry target is 4,096; inventory is bounded to 8,192 entries, 256 MiB read work and a 250 ms pass (125 ms for inventory, the remainder for validated retirement). These are bounded observations, **not a global reservation, hard quota, syscall deadline or Git admission gate**. Concurrent writers can overshoot; unsafe/unknown data or failed deletion can prevent publication. Omit optional diagnostics with a warning, not the native operation.

Incoming correlation IDs are protected across suffixes: conflicts discovered during inventory abort before retirement, destinations are rechecked afterward, and final exclusive publication cannot overwrite a winner. Incomplete byte/count/time scans never publish but may retire only a fully validated, unprotected completed prefix within the remaining budget. Later bounded calls/restarts can therefore shrink a stable valid overshoot without an unbounded sweep/retry loop. Recognized pressure can expire display data below category targets; retention is not a minimum-lifetime promise. Unknown/temp/foreign/malformed/link entries are never swept; observing them makes capacity unknown and suppresses retirement/publication for that pass. Active/uncertain spools remain untouched. Same-user final filesystem races and blocked syscalls are not sandboxed.

Legacy `pi-web/git-actions/v1/` history is preserved read-only, not migrated/pruned during this work. Rotation touches only recognized completed application diagnostics, never project data, worktrees, native locks, active transports or uncertain process spools. Development checks use disposable fixtures, not live private history. Deleting or restoring diagnostics cannot retire/restore another invocation or recreate receipt authority.

Captured patches are read from original private evidence, **never reconstructed from today's checkout or Git objects when expired/unavailable**. Missing/incompatible/evicted artifacts show unavailable/expired. While retained, they can be viewed after session/worktree deletion. There is no artifact export or check-log viewer promise here. Shell Git is not automatically instrumented.

The read-only `artifact` operation authorizes actual persisted full JSONL/trusted leaf ancestry against the captured action; IDs or cached/off-branch anchors alone are insufficient. Its Linux pinned reader bounds history to 8 MiB, 50,000 entries, 1 MiB/entry and depth 64. Chunks identify SHA-256, UTF-8 byte offsets/`nextOffset`, binary/end and `completePatch`; a prefix/suffix/middle chunk is not the complete patch and carries no mutation authority. Anchorless workspace/preparation lazy GETs instead require an opaque, privately issued **original RPC pending-read ticket**: the registered live wrapper, original request/response pair and issuance, candidate identity/kind/action ID, and SDK manager/session/file/cwd/header must still match. Capture precedes session/root awaits; validate the same ticket and saved/SDK owner across those awaits and before returning `readLiveGitAction` bytes. A settled/restored pair, cancelled/replaced request or changed owner cannot revive issuance. Once captured, a stale live association refuses without recapture or historical fallback. Requests without a live association use the separate valid history-anchor path. Neither path grants approval, receipt or mutation rights. Human previews continue to carry inline patches; no generic human metadata bypass is introduced.

**Legacy check recovery is diagnostic only.** Authenticated `GET /api/git/check-recovery` can report old evidence; POST returns **410 Gone**. There is no recovery-release approval, replay, passing receipt or `cgroupRelease` grant. Existing stopped-unit/cleanup records remain historical facts, not execution authority. Inspect actual Git/process state when needed; history or its absence cannot certify an external writer has stopped.

## Worktrees and continuing a chat (optional legacy controls)

Selected workspace operations create/use resources without task adoption or a chat transition. Sidebar **New worktree…** explicitly selects a local base/full tip and create-new or attach-existing branch/full tip. The server rejects stale tips, existing create names/destinations, already checked-out attach branches and dirty source/base checkouts (including untracked files). It uses the chosen local commit, not implicit HEAD or remote tracking, and does not fetch. Default destinations are `<repo>-worktrees/<sanitized-branch>`. See [Worktrees in Pi Web](worktrees.md).

Manual **Continue here…** or **Fork chat here…** selects another registered checkout for an idle persisted ordinary chat and asks separately before relocation; fork needs an assistant leaf. These controls do not copy, stash or reset source edits and are not triggered by sidebar creation or policy save. Moving the session family has its own idle/identity safety, not cross-session Git placement ownership.

Legacy `git_workspace_start` retains its explicitly requested optional continuation/fork flow, separate from selected workspace/cleanup. It requires a captured worktree-mode task or saved legacy worktree policy and full expected local base OID. A missing managed captured base can be proposed with `baseBranch` for **one exact-approved create-only/stay operation**: no Save/Apply, future grant or move receipt. Existing configured bases cannot be overridden this way. For explicitly selected legacy continuation/fork, a one-shot private receipt belongs only to that run's idle settlement; restart/reconnect cannot replay it. Failed creation/persistence/clone/move retains resources for manual inspection, never a blind retry. The browser follows server status rather than initiating movement. None of this is an automatic relocation mechanism for independent Git operations or deletion.

Session Save/task Apply remain unavailable while a run waits. Use the create-only missing-base proposal, or Stop before deliberately editing persistent legacy settings. Cancelling one question may continue the run. Old app-owned workflow reminder entries remain in raw history but are filtered from future ordinary context; already-flattened summaries and loaded wrappers can still need review/reload.

## Review and commit selected files

The human commit panel uses the persisted ordinary session's actual saved cwd, not the sidebar/configuration project. Choose **Whole files from working tree** or **Only selected staged index entries**, explicitly select paths and message, then **Preview** and **Confirm commit**. Staged mode preserves unrelated staged entries and unstaged hunks, including both paths of a selected staged rename. Working-tree file previews are read-only aids, **not** the authoritative candidate.

Preview identifies checkout, branch, parent, selected paths, exact tree and bounded candidate-tree diff. Binary/oversized/unsupported diffs are labelled, not silently truncated or replaced with another preview. Confirmation authenticates a process-local single-use session-bound candidate and exact message, then rechecks branch/HEAD/index bytes/paths/tree and original authority. Changing selection/message or refreshing clears the UI preview. Browser commit previews expire after 15 minutes; restart/history cannot restore them.

Legacy `git_commit preview/confirm` is only for existing saved `commits: agent` session consent; managed tasks use the common Ask path. Project defaults alone are not consent. Whole-file mode refuses dirty/staged or conflicted index; explicit staged mode supports deliberate entries while rejecting conflicts, unsupported flags/submodules/filters. Both use a temporary-index candidate, `commit-tree`, exact ref CAS and index preservation. Hooks/signing/configured filters do not run. Worktree-local merge/rebase/am/sequencer/bisect markers are checked again at native boundaries and never removed to make the action succeed.

No application gate surrounds preview, human waiting or apply. A stale candidate or native lock conflict refuses that invocation. If the ref advances but index finalization fails, report **partial success** with actual commit/tree/parent/author details and inspect manually; do not retry blindly. Optional record failure after known completion yields a diagnostic warning, not fictitious native uncertainty or a new approval opportunity.

## Local integration review and explicit approval (legacy/browser path)

The legacy browser panel derives feature and target from the saved session/task, requires local refs and the target on the feature's **first-parent chain**, and computes a reproducible merge-result tree equal to the feature tree. Missing `merge-tree --write-tree`, conflicts or unsupported topology refuse. Read-only whole/single/contiguous-range comparisons use committed trees; they do not approve execution. Stale tips require refresh; binary/oversized patches are explicitly bounded.

Verification runs local project code only after explicit permission. This paired path supports original saved `{ label, argv }` recipes, **not extended cwd/env/stage recipes**. One explicit browser action runs the complete required-check batch; a failed current batch stays failed rather than selecting older passes. Public batch metadata only groups display rows. Native validation independently requires the exact ordered required receipt set from the same original private cohort at plan capture and final apply; mixed independent passes refuse even when the UI metadata appears compatible. Successful checks are not merge permission.

**Prepare exact integration proposal** captures the exact plan, refs, receipts and candidate diff, including either the proposed non-FF commit or existing FF tip with actual parents. **Confirm exact plan** is the separate approval; there is no additional review checkbox. Original authority, physical bytes/index/refs, policy, required evidence and single-use identity are revalidated. Native prepared refs and the owned original index lock protect checked-out effects as described above—not an application prompt/checkout gate.

Only explicit FF or ordinary unsigned non-FF is available; no squash, hidden rebase, remote publication or cleanup. Changed targets/candidates return facts without retry/rebaseline. Partial effects require inspection; optional diagnostics may be unavailable and are not a recovery prerequisite. The selected `prepare` path remains independently authorized and returns to the agent before fresh verification/integration.

These native paths are bounded Linux support. Windows-equivalent behavior and portability have **not been verified**. Full runtime acceptance and installed instruction/policy alignment remain separate from this source documentation.

# Git workflow in Pi Web

## Intended experience versus current implementation

For the revised **design**, start with [ADR 0011 — Project policies and agent-driven Git operations](adr/0011-policy-driven-git-tools.md): one chat may use several worktrees/projects without moving or binding the session; saved project policies preanswer routine questions, and preparation against a moving target returns to the agent after every rebase. Human commit confirmation is intended to default off, independently of verification. This is not yet the installed tool contract.

**The rest of this guide documents current behavior**, including its same-repository selectors, captured session settings and explicit approvals. Task binding/source review is non-authoritative metadata, not a prerequisite for ordinary supervised commits or the new target design. The [successor roadmap](plans/2026-09-29_policy-driven-git-tools-plan.md) separates reusable mechanisms from the retired session-ownership/coordinator direction. This documentation update changes no runtime permissions.

**Workflow** in the top bar is the single home for Global, Project, and Session settings and current-task actions. It remains accessible without a chat and when disabled. Commit, integration review, and workspace continuation are focused views within that panel; the read-only Git Explorer remains independent. This first integrated slice still requires human approvals: saving defaults does not create a worktree, execute a check, commit, integrate, or clean up. Repository instructions still apply. Managed-action gates are not a sandbox for shell tools, terminals, or external Git processes. Chat-only loads no workflow/commit extensions.

## Agent-triggered review and local actions

In an ordinary coding session, `git_workflow operation: "status"` reports captured task choices, saved values and origins, live pause/enablement, a concise private task-binding status (never source contents), and the same permission facts shown under **Current task → Permissions & blockers**. Configure related choices in the Workflow panel. `git_commit operation: "commit"` takes explicit complete changed `paths` and an exact `message`; in Ask mode it presents the candidate tree, parent, diff, and message for human approval. The workflow tool's `commit` operation is a compatibility alias of that same path. Manual mode refuses agent commits; Off also refuses human commit actions. Cancellation does nothing, changed candidates fail closed, and partial success requires manual inspection. Read-only/Chat-only agents and subagents cannot use mutation tools to escape their restrictions.

`git_workflow operation: "review"` still presents a bounded read-only local comparison (`targetBranch`, optionally an ordered consecutive `commitOids` range). Dismissing or acknowledging a comparison is not approval to merge. Legacy sessions may still use earlier saved preferences and explicit integration arguments. A legacy `preferences` request now offers a link to Workflow rather than a second settings form; opening it dismisses that request and does not continue an operation. That old preference namespace cannot retarget a managed task: managed integration uses its captured target/checks and refuses contradictory arguments.

`operation: "integrate"` takes an explicit local `targetBranch` and an ordered nonempty list of checks (`{ label, argv }`, no shell). It first displays every command for **separate permission to execute project code**. It then checks the distinct registered clean checkouts, trust and other running sessions; reserves both checkouts while executing the checks, records state-bound receipts, prepares the exact candidate merge diff/refs/commit/receipts, and displays a **second** card for approval of that exact plan ID. It releases gates while waiting for user input and reacquires them for the final exact-state unsigned non-fast-forward merge. Stop cancels pending UI and running checks. Any failed check or stale checkout requires a fresh review; a `partial-state` result requires manual recovery. This tool does not rebase, perform a remote operation, or clean up the feature worktree.

**Git questions wait for you without an automatic response timeout.** This covers preferences, comparisons, commit approvals, check permissions and exact merge approvals. A live request survives browser disconnect/reload; answering, Stop or session teardown settles it. Server restart does not restore executable approval. Waiting is not permission and does not renew verification: native merge plans/check receipts and manual browser previews retain their own freshness limits, and every eventual approval still revalidates the candidate. If those checks fail, prepare a fresh candidate rather than reusing or silently transferring the old approval. Command execution timeouts are unchanged. The operation-specific approval button is the decision: no extra “I reviewed” checkbox or acknowledgement gate is required. File/check selectors still select scope, and permission to run checks remains separate from approval to merge.

All three agent Git tools accept an optional `workspaceBranch` naming a checked-out local branch in another registered worktree **of the calling chat's repository**. Without it, they use the chat checkout. The selected worktree must be a physical checkout inside Pi Web's allowed file roots; an arbitrary path, unrelated project, detached HEAD or remote branch is not accepted. The chat's policy and identity remain authoritative, not those of any session in the selected worktree. Review and approval cards identify the source checkout; verification commands execute there. When a tool can collect the relevant choice/approval, agent guidance prefers it over asking in prose, provided repository and user instructions permit; this never skips a required approval or overrides stricter rules. See [ADR 0009](adr/0009-cross-worktree-agent-git-tools.md).

**This remains staged implementation, not end-to-end automation.** Commits, comparisons, checks and integrations now retain durable action cards and captured multi-file diffs. Standing grants, recipe environments, automatic integration and agent cleanup remain unimplemented. Mandatory per-task workspace ownership is withdrawn from the revised target, rather than a prerequisite still to build. A closed approval dialog is not a successful Git result. Native hooks/signing/filter restrictions remain. The revised target and active implementation queue are [ADR 0011](adr/0011-policy-driven-git-tools.md) and [the policy-driven tools plan](plans/2026-09-29_policy-driven-git-tools-plan.md); ADR 0010 and its plan retain historical design and verification evidence.

## Configure defaults and capture task choices

The same five rows—Workspace, Commits, Checks, Integration, Cleanup—are edited at **Global**, **Project**, or **Session** scope. Fields inherit individually; their source is shown. Reset removes an override. Explicit Off, no target (`null`), and no checks (`[]`) do not mean inherit. Ordered check lists replace rather than concatenate. No project branch or command is hard-coded into global defaults.

Global/project settings live privately in `~/.pi/agent/pi-web/git-workflow-settings.json` (or under `PI_CODING_AGENT_DIR`), separate from Pi's settings and repository files. Project identity is canonical across linked worktrees. Existing `git-workflow-defaults.json` remains readable until that project's settings are saved in the new store; resetting to an empty project override then inherits Global instead of resurrecting the old file. Importing legacy defaults never grants new automation: legacy agent-commit defaults become Ask for newly managed sessions.

Save applies only to the named scope. Drafts survive scope/panel navigation, and unsaved parents do not alter another scope's inherited display. Revision conflicts require a deliberate reload/reconciliation instead of overwriting another client's changes. Global/project editing never creates a chat. Session editing currently needs a persisted idle ordinary chat; initialized-but-unsent chats do not queue hidden overrides in this editor.

New chats capture effective defaults in versioned non-context metadata. Existing legacy sessions remain pinned, including their explicit old agent-commit consent. Saving defaults or session overrides does not retarget the **current task**. Use its explicit Apply action to capture the saved effective choices. Fork/clone preserves those captured preferences, not newer defaults or live approval capabilities. After v2 adoption a preceding v1 opt-out prevents an older runtime from skipping the new record and reviving older commit consent; malformed/newer configuration blocks managed execution rather than falling back.

Enablement and commit Off are live restrictions, rechecked by already-loaded tools and browser mutation routes. Lower-scope explicit enablement can override a global default-off. **Pause all managed Git actions** is separate and unconditional: it cannot be overridden by project/session defaults. Pending approvals cannot bypass a later pause; cancellable checks observe it. A ref/index update already at its apply boundary is not interrupted halfway. Neither toggle controls external Git writers or arbitrary shell programs.

Permission summaries and live route/tool gates share `lib/git-workflow-permissions.ts`. They distinguish agent requests from explicit human actions: Manual refuses the agent but still permits human review, Off refuses both, and Ask requires exact approval. Read-only/Chat-only tool selection does not prevent the operator's human actions; subagent sessions refuse both. Unknown active tools are not assumed to be Full: a disk-only session without a saved tool selection reports that agent eligibility needs loading, without starting a wrapper. Legacy worktree starts are labelled **Saved policy**, not falsely described as a fresh approval; legacy commit consent remains a separate compatibility fact. These are settings/actor checks, **not** a grant or a successful repository/candidate preflight.

Automatic remains unavailable, including in settings writes. Private binding/source evidence now exists, but it is not task authority or executable policy. Future confirmation-free operations need validated project/action scope, user-saved authorization/revocation and the relevant admission/recovery safeguards. ADR 0011 withdraws mandatory task/source adoption and full prose-policy normalization as prerequisites; the current runtime still refuses Automatic. No imported record, ordinary preference, status response or editor draft supplies execution authority.

Supported choices are current checkout or a dedicated worktree from an explicit local base; continue/fork/stay; Off/Manual/Ask commits; executable/argv checks; a local non-FF merge target or none; and resource retention. Automatic modes and agent cleanup are intentionally unavailable. Fast-forward/squash preferences can be read from old policies but cannot be executed by the native integration engine.

## Explicit task binding and source review

**Current task → Task binding & source review** is a metadata prerequisite, not a new execution mode. First capture saved task settings with the existing Apply action. In an idle persisted ordinary chat, name a goal, explicitly select an originating user request from the current branch, choose an existing registered local checkout, and list any delegated Markdown skills/documents needed for this review. A dependency is relative to that selected checkout or an explicit allowed absolute path. The app does not follow prose links, discover referenced skills automatically, fetch URLs, or execute resources.

Select **Preview task & instruction sources**. A linked instruction/dependency path first discloses its exact physical Markdown destination; **Read these exact source destinations** permits only those file reads, not their surrounding directories. Subsequent destination prompts retain earlier explicit selections. Inspect the complete captured text, settings, session/request and checkout identity, then use the single **Adopt reviewed task metadata** button. There is no review checkbox or response timer. Replacement/cancellation/restart loses the live preview; confirmation always revalidates sources, session/settings, checkout/branch/HEAD and the previous private generation. Supported settings writes—including legacy defaults and Pause-on/off round trips in another process—change a durable write epoch, so restoring equal values cannot revive an old preview.

The source-discovery contract is pinned to SDK 0.87.1: global and root-to-cwd context selection in `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, `CLAUDE.MD` order, including missing higher-priority candidates and nested-worktree shadowing. Shadowed selection-critical documents are captured separately as probes, not labelled loaded instructions. Missing named dependencies, unreadable/nonregular/invalid UTF-8/binary/oversized sources and changed directory/file identities block the entire review. Limits are 24 named dependencies, 64 total captured documents/probes, 256 KiB per file and 1 MiB of source bytes; there is no silent truncation or fallback. **Secure source capture currently requires Linux and descriptor-relative `/proc/self/fd` access**, with readable parent directories. Parent components are pinned with no-follow descriptors and the opened file identity is checked before reading bytes; unavailable platforms/capabilities do not fall back to weaker reads.

Private immutable snapshots and generation heads live under `~/.pi/agent/pi-web/git-task-bindings/v1/` (or `PI_CODING_AGENT_DIR`); the separate write fence is `pi-web/git-workflow-write-epoch.json`. Each adoption creates a fresh private binding ID; generations increase across adoption, release and invalidation. Records bind the physical session file/header, user entry digest/goal, captured settings and physical registered workspace/Git-directory/branch identities. Reads do not create records or AgentSessions. No anchor, copied source text or synthetic user turn is appended to the transcript, and startup/default snapshots cannot mint a binding. Ordinary copies/forks/imports do not inherit it; moves and settings recapture invalidate it, including failed moves. After server restart, retained evidence requires fresh review rather than resuming work. Release is a tombstone, not deletion. A malformed/newer/missing head or artifact in an existing namespace fails closed; orphan snapshots never reconstruct it. Atomic publication syncs directory entries, including retries after an earlier sync failure.

**Adoption does not approve any Git operation, start a coding task, reserve ownership, reload the agent's instructions, or retarget existing tools/action views.** A “current” source snapshot means checked disk evidence, not proof of loaded instructions, complete prose-rule coverage or normalized executable policy. The unchanged Ask/Manual/legacy and native transaction safeguards still govern actions. One current binding slot per session is supported. ADR 0011 replaces the proposed mandatory orchestration/ownership/handoff model with independently scoped operations; these binding records will not become grants or a required setup step. No artifact deletion/export UI is provided yet. Private storage/digests are not a sandbox against a same-user process rewriting private state, and comprehensive external-writer admission is still missing.

## Durable action history

Commit, review, verification and integration cards retain their captured candidate and result across browser reload, raw branch-history pagination, compaction and chat moves. Existing legacy agent-consented commits are recorded too. A fork can display inherited references after the original session is deleted. Cards read private artifacts, never today's working files or Git objects, so declined patches survive Git garbage collection and removal of their old workspace.

- A compact card identifies its operation, source, branch, message, timestamps, decision and outcome. Expand **Captured candidate** for selected paths and lazy per-file **Side by side**, **Unified**, or **Raw patch** views. Split columns scroll independently on phones. These are captured hunks, not arbitrary full-file history; binary/metadata-only and unavailable/oversized content are explicitly labelled.
- A live agent request is coalesced into its matching card. Only that original server-owned request can expose approval controls. Browser-origin actions are approved through their existing Workflow detail; history never offers a replay button. Stop and decline are distinct; unanswered agent Git questions have no response timer. Expired/interrupted history still represents lost process ownership or unavailable live candidates. After server restart, pending history is expired/interrupted and uncertain execution needs recovery; nothing resumes automatically.
- **Prepared OIDs are not completed results.** The commit engine records its intended object before updating the ref, and integration records intent before touching the target checkout. Actual successful/partial results are recorded afterward. An integration `partial-state` merge OID may still be only the proposed object, not an updated ref. If recording fails after mutation, retain the known result and inspect the checkout; do not repeat the operation.
- Private, bounded, digest-checked records/artifacts live under `~/.pi/agent/pi-web/git-actions/v1/` (or `PI_CODING_AGENT_DIR`). Tiny plain SDK `pi-web:git-action` custom entries contain only version/action ID. They are **not** `custom_message` entries and never add patch-sized data or fabricated user turns to model context. History GETs do not create AgentSessions. SSE supplies small revision notifications; visible cards also reconcile through GET. Another idle browser's newly added anchor appears on transcript refresh.
- Artifacts have no automatic deletion or export UI yet. They remain independent of session/worktree cleanup; missing or incompatible artifacts show a placeholder, not substituted current content. Standard SDK session HTML export does **not** include these private artifacts. Checks retain their approved commands and outcome; their private native logs are not yet exposed in a card log viewer. Worktree creation/continuation and legacy preference editing still use their existing live UI rather than this journal. Raw shell Git is not automatically instrumented.

## Worktrees and continuing a chat

Use **New worktree…** in the sidebar from a Git checkout root. Explicitly choose a local base branch and review its full expected HEAD; choose **Create new branch** with a new name, or **Attach existing local branch** with its full expected tip. The server rechecks the refs and rejects stale tips, an existing create-branch name, an already checked-out attach branch, dirty source/base checkouts (including untracked files), and existing destination directories. It creates from the chosen base commit, not an implicit current HEAD or a remote-tracking ref; it does not fetch. Worktrees live under `<repo>-worktrees/<sanitized-branch>`. See [Worktrees in Pi Web](./worktrees.md) for switcher and removal details.

For a persisted idle chat at a registered checkout root, open **Workflow** and its workspace detail, choose a *different already registered* worktree from **Destination worktree**, and select **Continue here…** or **Fork chat here…**. Each action presents a separate confirmation before relocating the same chat/session family or creating a new chat at that checkout. Fork requires an assistant leaf. The manual controls do not create a worktree. Neither manual action is triggered by a policy save or a sidebar worktree creation.

In an ordinary persisted chat with a **captured worktree-mode task or legacy saved policy**, the agent can explicitly invoke `git_workspace_start` to create a **new** branch and linked worktree from its saved local base branch and a supplied full expected base OID. A managed task requests human approval before creation; pause/disablement is rechecked before creation and automatic continuation. This invocation, not the saved preference alone, records the checkout created and the `onCreate` action. When **that run** settles and the chat is idle, Pi Web attempts the recorded **continue** or **fork** once on the server, even without a connected browser. `stay` creates only the worktree. Selecting another creation source with `workspaceBranch` does not move or fork a chat in that source: `continue`/`fork` still applies to the calling chat. A private receipt is claimed before movement; a reconnect or server restart never replays a prior receipt. Only one automatic start is supported per chat: use the manual worktree controls for later starts. If persistence, checkout validation, cloning, or relocation fails, the worktree (and any fork already made) remains for manual inspection; a failed attempt is **not retried automatically**. The UI follows successful transitions and displays a manual-recovery notice on failure. Do not start a new worktree merely to retry a failed transition.

All continuation/fork paths leave **uncommitted source files in the original checkout**; they never copy, stash, or reset them. The manual UI displays changed-file status as a warning. Use Git yourself to move changes if needed. Manual continuation/fork is disabled while busy; the server checks session state and registered checkout identity. If a fork is made but moving it fails, use its reported ID to inspect it, not a blind new fork.

## Review and commit selected files

The commit detail inside **Workflow** is a human action on a persisted ordinary session, using its actual saved cwd rather than the sidebar's selected checkout. The cwd must be a physical Git checkout root on a local branch. Refresh status, select **complete changed files** (none selected by default), enter a message, then **Preview** and separately **Confirm commit**. Optional working-tree file diffs are *read-only aids*, **not** the authoritative candidate: unsupported/binary/large patches can be absent, while the whole selected file is still in the candidate. Preview reports checkout, branch, parent HEAD, selected paths, the exact candidate tree, and a bounded **candidate tree diff** against HEAD; inspect them before confirming. If that exact diff is too large, the UI says so instead of displaying a truncated patch. You can still identify the tree and review through Git, but do not treat an unsupported working-tree file preview as a replacement for the candidate diff. Changing selection/message or refreshing clears the preview in the UI. The server authenticates a preview token and re-derives branch, HEAD, index bytes, paths and tree at confirmation, refusing a stale candidate. The token is process-local and does not survive a server restart. Browser preview also binds the exact message to a single-use, session-scoped live action ID; both are required at confirmation. An abandoned browser preview expires after 15 minutes (an integration proposal may expire sooner). A stored card or copied fork reference cannot recreate it.

The legacy `git_commit preview/confirm` interface remains available **only for an existing saved `commits: agent` session policy**. Managed tasks use the common Ask path instead; neither defaults nor a tool argument create automatic commit authority. Both interfaces and the browser enforce the same live pause/enablement gate. This engine refuses a dirty/staged or conflicted index, unsupported index flags/submodule changes and unsupported configured hook, signing, or filter policies; it does **not** run hooks, sign commits, or run configured filters. It builds a temporary-index tree, uses `commit-tree` and a compare-and-swap ref update, then installs the index. It does not push or integrate. It cannot promise atomicity against arbitrary external Git writers: if the branch ref advances but checkout/index finalization fails, the result is **partial success** with the created commit ID, tree, parent and author email. Inspect the branch, index and checkout before taking any further action; **do not retry blindly**. Other failures can require a fresh status and preview.

Agent Ask commits and legacy preview/confirm now reserve the same in-process checkout gate as browser commits during capture and application, never while waiting for an answer. Other running/starting sessions at that checkout block commits; only the initiating agent session is excluded. Browser commits exclude nobody. An approval remains recorded even when subsequent admission fails. The gate still does not cover every terminal/process/subdirectory alias; this is not exclusive workspace ownership or sufficient admission for Automatic.

Native commit preflight refuses unfinished merge, rebase, `git am`, cherry-pick/revert sequences, and bisect state, even with a clean index. Checks use the selected worktree's Git directory and run again immediately before ref CAS; markers and historical refs are never removed to make an operation succeed. A known operation-state refusal after intent recording is **blocked**, with prepared identity retained but no claimed result. Unclassified post-boundary exceptions still require recovery. External writers can race these checks; nothing auto-aborts or retries their operations.

## Local integration review and explicit approval

With a captured task or legacy saved policy containing an integration target, open the integration detail inside **Workflow** in a persisted ordinary chat. It derives the feature from that chat's checked-out local branch and the target from the *saved session* policy; both must be local refs. The target commit must be an ancestor **on the feature's first-parent chain** (being a second-parent ancestor is insufficient). Git computes a proposed merge-result tree; conflicts or unavailable `merge-tree --write-tree` prevent a review. No checkout files, index, uncommitted edits or remotes are included.

Choose a patch for the **whole proposed merge** (target tree → merge-result tree), a **single commit** (its first-parent tree → its tree), or an ordered **contiguous** range on the feature's first-parent chain (tree before its first commit → last commit's tree). Ranges are cumulative, not individual patch bundles or cherry-pick previews. The UI shows exact ref and tree IDs; the server checks both branch tips before and after generating a bounded patch, and stale tips require refresh. Binary differences are summaries, not full contents; an oversized patch fails rather than returning a partial one. These selectable patches are **read-only comparisons**, not approval cards. An explicit **Show read-only patch** captures that comparison in history; its outcome means the comparison was captured, not that a person approved execution.

For a saved **merge** method and configured checks, the separate integration section lists check labels and matching, time-limited successful receipt IDs. Run each check explicitly; these commands execute local project code and can modify files. Passing checks are not approval. After every check has a matching receipt, select **Prepare exact integration proposal** to get an exact plan ID, feature and target OIDs, merge commit ID, receipt IDs and the bounded **authoritative candidate diff**. Inspect the candidate (binary contents are summarized), then select **Confirm exact plan**. There is no additional review-acknowledgement checkbox or button. Neither verification nor planning confirms automatically. Confirmation rechecks exact checkout/ref/policy/index state; stale failures require refreshing and verifying again. A **partial-state** result means checkout/ref/index finalization may have failed: inspect both worktrees, refs and the reported recovery record manually; do not retry blindly. Only ordinary unsigned local merge is available; fast-forward/squash, worktree cleanup, remote fetch/push/publication are not performed.

Local integration requires **distinct registered feature and target checkouts**, a clean standard index and checkout on both sides, a target on the feature's first-parent chain, a reproducible merge result equal to the feature tree, supported Git policies (no configured hooks, signing, filters or attributes), and successful receipts for **every** saved check. Pi Web holds an in-process prompt/checkout gate during the merge; other Git processes are not coordinated. The verification commands themselves are explicitly selected, never run merely because they were saved. No automatic rebase is performed: prepare the feature on the local target yourself, then rerun checks. A failed attempt after checkout begins retains a private recovery record, not an automatic rollback. Cleanup remains a separate, explicit worktree action; no cleanup is implied by integration.

The Git workflow's Windows portability has **not been verified**. Do not assume these paths, Git policies or transactions have been tested there.

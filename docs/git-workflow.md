# Session Git workflow in Pi Web

Pi Web offers an on-demand **Git & workspace** menu near the top of the chat (with **Workspace workflow**, **Review & commit**, and **Local integration review** for persisted ordinary chats), and the sidebar worktree switcher. These controls no longer occupy permanent rows above the composer. These are local preferences and bounded Git operations, not an automated feature-branch lifecycle. Repository instructions still apply; a preference does not approve integration, cleanup, or a remote operation. The agent can still use its other enabled tools (including shell tools) outside this workflow; the preference is guidance, not a sandbox. Chat-only loads no workflow/commit extensions.

## Agent-triggered review and local actions

In an ordinary non-Chat-only session with coding tools enabled, the agent can call `git_workflow` without a saved session policy. `operation: "review"` takes an existing local `targetBranch` and optionally an ordered consecutive `commitOids` range; it displays exact feature/target/tree IDs and the bounded tree diff in a transient chat card. Acknowledging the card is **not** permission to merge. `operation: "commit"` takes complete changed `paths` and a `message`, displays the exact selected candidate tree, parent, diff, and message, and calls the guarded commit engine only after explicit approval. Cancellation does nothing; changes after approval fail closed; a `partial-success` result requires manual inspection.

`operation: "integrate"` takes an explicit local `targetBranch` and an ordered nonempty list of checks (`{ label, argv }`, no shell). It first displays every command for **separate permission to execute project code**. It then checks the distinct registered clean checkouts, trust and other running sessions; reserves both checkouts while executing the checks, records state-bound receipts, prepares the exact candidate merge diff/refs/commit/receipts, and displays a **second** card for approval of that exact plan ID. It releases gates while waiting for user input and reacquires them for the final exact-state unsigned non-fast-forward merge. Stop cancels pending UI and running checks. Any failed check or stale checkout requires a fresh review; a `partial-state` result requires manual recovery. This tool does not rebase, perform a remote operation, or clean up the feature worktree.

**This is an incremental agent tool.** Capturing early preferences, agent-triggered cleanup, and safe chat relocation during cleanup are not yet implemented. Use the on-demand menu for saved-policy controls and the sidebar for worktree removal. Neither menu approval nor a reviewed comparison authorizes cleanup or publication. See `docs/plans/2026-09-27_agent-git-review-plan.md` for the remaining redesign.

## Choose a policy

Open **Git & workspace → Workspace workflow** before starting a chat to save a **Project default for new chats**, queue an **Override for this new chat**, or **Opt out for this new chat**. A project default is keyed by the canonical project root (main checkout and linked worktrees share it), stored in `~/.pi/agent/pi-web/git-workflow-defaults.json` or beneath `PI_CODING_AGENT_DIR`. At session initialization, Pi Web records a versioned snapshot in the Pi session file. Changing or clearing the default affects **only subsequently initialized chats**; legacy chats with no saved policy do not adopt it on read. A new-chat override or explicit opt-out (`null`) must be chosen *before* initialization (even model/tool inspection can initialize a chat). An initialized but not-yet-persisted chat currently refuses a session override: start a new chat instead.

For a persisted, idle chat, select **Save this session's policy** or **Opt out for this session**. A running chat must be stopped first; subagent policy edits are refused. Saving appends a new snapshot; forks/clones inherit the effective saved snapshot rather than a newer project default. The hidden workflow extension reads the saved policy before **each new agent run**, so an idle session edit affects the next run without reloading the browser; it does not change a run already in progress. Chat-only loads neither this extension nor the built-in `git_commit` tool, even if a policy is saved.

The policy records checkout mode (**dedicated worktree** from a named *local* base branch, or **current checkout** with an optional branch requirement), what to do *when the agent explicitly starts a worktree* (**continue**, **fork**, or **stay**), whether the agent may commit (**agent** or **manual**), and optionally a *local* integration target and method (**merge**, **fast-forward**, or **squash**). Saving these values does **not** create a worktree, move/fork a chat, enforce a branch switch, make a commit, run verification, or integrate anything. A target/method is a proposal preference, not approval; only the ordinary local merge method can be executed from the integration review, after saved checks and a separate exact-plan approval. Fast-forward and squash are not supported.

## Worktrees and continuing a chat

Use **New worktree…** in the sidebar from a Git checkout root. Explicitly choose a local base branch and review its full expected HEAD; choose **Create new branch** with a new name, or **Attach existing local branch** with its full expected tip. The server rechecks the refs and rejects stale tips, an existing create-branch name, an already checked-out attach branch, dirty source/base checkouts (including untracked files), and existing destination directories. It creates from the chosen base commit, not an implicit current HEAD or a remote-tracking ref; it does not fetch. Worktrees live under `<repo>-worktrees/<sanitized-branch>`. See [Worktrees in Pi Web](./worktrees.md) for switcher and removal details.

For a persisted idle chat at a registered checkout root, expand **Workspace workflow** and choose a *different already registered* worktree. **Continue here…** confirms relocation of the **same chat/session family** to the selected checkout; **Fork chat here…** confirms a new chat there while retaining the source chat. Fork requires an assistant leaf. The manual controls do not create a worktree. Neither manual action is triggered by a policy save or a sidebar worktree creation.

In an ordinary persisted chat with a **saved worktree-mode session policy**, the agent can explicitly invoke `git_workspace_start` to create a **new** branch and linked worktree from its saved local base branch and a supplied full expected base OID. This invocation, not the saved preference alone, records the checkout created and the `onCreate` action. When **that run** settles and the chat is idle, Pi Web attempts the recorded **continue** or **fork** once on the server, even without a connected browser. `stay` creates only the worktree. A private receipt is claimed before movement; a reconnect or server restart never replays a prior receipt. Only one automatic start is supported per chat: use the manual worktree controls for later starts. If persistence, checkout validation, cloning, or relocation fails, the worktree (and any fork already made) remains for manual inspection; a failed attempt is **not retried automatically**. The UI follows successful transitions and displays a manual-recovery notice on failure. Do not start a new worktree merely to retry a failed transition.

All continuation/fork paths leave **uncommitted source files in the original checkout**; they never copy, stash, or reset them. The manual UI displays changed-file status as a warning. Use Git yourself to move changes if needed. Manual continuation/fork is disabled while busy; the server checks session state and registered checkout identity. If a fork is made but moving it fails, use its reported ID to inspect it, not a blind new fork.

## Review and commit selected files

**Review & commit** is a separate human action on a persisted ordinary session, using its actual saved cwd rather than the sidebar's selected checkout. The cwd must be a physical Git checkout root on a local branch. Refresh status, select **complete changed files** (none selected by default), enter a message, then **Preview** and separately **Confirm commit**. Optional working-tree file diffs are *read-only aids*, **not** the authoritative candidate: unsupported/binary/large patches can be absent, while the whole selected file is still in the candidate. Preview reports checkout, branch, parent HEAD, selected paths, the exact candidate tree, and a bounded **candidate tree diff** against HEAD; inspect them before confirming. If that exact diff is too large, the UI says so instead of displaying a truncated patch. You can still identify the tree and review through Git, but do not treat an unsupported working-tree file preview as a replacement for the candidate diff. Changing selection/message or refreshing clears the preview in the UI. The server authenticates a preview token and re-derives branch, HEAD, index bytes, paths and tree at confirmation, refusing a stale candidate. The token is process-local and does not survive a server restart.

A separate built-in agent `git_commit` tool offers the same two-step preview/confirm engine **only when a saved session policy says `commits: agent`** and the tool is available to that ordinary non-Chat-only session. A project default alone is not agent-commit consent. The browser's human commit flow is separate from that agent setting. This engine refuses a dirty/staged or conflicted index, unsupported index flags/submodule changes and unsupported configured hook, signing, or filter policies; it does **not** run hooks, sign commits, or run configured filters. It builds a temporary-index tree, uses `commit-tree` and a compare-and-swap ref update, then installs the index. It does not push or integrate. It cannot promise atomicity against arbitrary external Git writers: if the branch ref advances but checkout/index finalization fails, the result is **partial success** with the created commit ID, tree, parent and author email. Inspect the branch, index and checkout before taking any further action; **do not retry blindly**. Other failures can require a fresh status and preview.

## Local integration review and explicit approval

With a saved session policy containing an integration target, open **Local integration review** in a persisted ordinary chat. It derives the feature from that chat's checked-out local branch and the target from the *saved session* policy; both must be local refs. The target commit must be an ancestor **on the feature's first-parent chain** (being a second-parent ancestor is insufficient). Git computes a proposed merge-result tree; conflicts or unavailable `merge-tree --write-tree` prevent a review. No checkout files, index, uncommitted edits or remotes are included.

Choose a patch for the **whole proposed merge** (target tree → merge-result tree), a **single commit** (its first-parent tree → its tree), or an ordered **contiguous** range on the feature's first-parent chain (tree before its first commit → last commit's tree). Ranges are cumulative, not individual patch bundles or cherry-pick previews. The UI shows exact ref and tree IDs; the server checks both branch tips before and after generating a bounded patch, and stale tips require refresh. Binary differences are summaries, not full contents; an oversized patch fails rather than returning a partial one. These selectable patches are **read-only comparisons**, not approval cards.

For a saved **merge** method and configured checks, the separate integration section lists check labels and matching, time-limited successful receipt IDs. Run each check explicitly; these commands execute local project code and can modify files. Passing checks are not approval. After every check has a matching receipt, select **Prepare exact integration proposal** to get an exact plan ID, feature and target OIDs, merge commit ID, receipt IDs and the bounded **authoritative candidate diff**. Inspect the candidate (binary contents are summarized), acknowledge that you have reviewed it, then separately select **Confirm exact plan**. Neither verification nor planning confirms automatically. Confirmation rechecks exact checkout/ref/policy/index state; stale failures require refreshing and verifying again. A **partial-state** result means checkout/ref/index finalization may have failed: inspect both worktrees, refs and the reported recovery record manually; do not retry blindly. Only ordinary unsigned local merge is available; fast-forward/squash, worktree cleanup, remote fetch/push/publication are not performed.

Local integration requires **distinct registered feature and target checkouts**, a clean standard index and checkout on both sides, a target on the feature's first-parent chain, a reproducible merge result equal to the feature tree, supported Git policies (no configured hooks, signing, filters or attributes), and successful receipts for **every** saved check. Pi Web holds an in-process prompt/checkout gate during the merge; other Git processes are not coordinated. The verification commands themselves are explicitly selected, never run merely because they were saved. No automatic rebase is performed: prepare the feature on the local target yourself, then rerun checks. A failed attempt after checkout begins retains a private recovery record, not an automatic rollback. Cleanup remains a separate, explicit worktree action; no cleanup is implied by integration.

The Git workflow's Windows portability has **not been verified**. Do not assume these paths, Git policies or transactions have been tested there.

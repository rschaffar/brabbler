# Git workflow in Pi Web

## Source support versus installed behavior

**Accepted revision, not yet connected:** [ADR 0012 — Independent Git invocations](adr/0012-optimistic-git-invocations.md) replaces cross-session quarantine/reservations with exact per-invocation authorization and native optimistic Git transactions. Another session's history or activity will not veto an operation; required passing checks and stale-candidate rejection remain. Implementation is tracked in roadmap Phase 6. The quarantine/lease descriptions below still describe the existing runtime, not that replacement or an installed promise.

[ADR 0011 — Project policies and agent-driven Git operations](adr/0011-policy-driven-git-tools.md) records the decision: one chat can select several projects/worktrees without moving or adopting a task; separate saved permissions can preanswer routine decisions, and every actual preparation rewrite returns to the agent.

**This guide documents the feature source, not an installed release or activated policy.** The selected runtime now connects native workspace creation/attachment, preparation, source-only checks, FF/non-FF local integration, eligible cleanup and explicit reconciliation to live authorization, admission and durable history. Whole-file and explicit staged commits remain supported. Task/source metadata and chat transitions are not prerequisites for selected operations. Separately saved Global, Project and Chat × Project Allow/Deny records are not execution tokens: explicit `confirmation: "none"` additionally needs that action's selected confirmation preference `none`, compatible instructions and every live native gate. No policy save schedules work. The special fresh-creation restrictions on no-confirmation commits are described below.

Source implementation is not full-suite acceptance: the coordinator's settled full-suite result remains authoritative; focused results alone do not establish it. Integration of **this feature** into `rst-main`, deletion of its resources, remote publication, installation, Nix/instruction changes and live policy activation each remain separately authorized actions. This guide grants none of them. The [roadmap](plans/2026-09-29_policy-driven-git-tools-plan.md) retains implementation/verification evidence; historical slice descriptions are not the current dispatch contract.

**Workflow** in the top bar is the single home for Global, Project, and Session settings. **Turn off for this chat** is a separate, reversible opt-out for an idle persisted ordinary chat: the next agent run receives no Pi Web Git workflow prompt section, and chat-bound managed Git mutations (including selected-project commits) refuse while it is off. Project-scoped sidebar worktree controls are independent of the chat and retain their own authorization. Toggling the opt-out evicts an idle chat wrapper; its next load omits Pi Web's managed Git tools entirely. In-flight or stale tool calls still check the live opt-out before any managed mutation. Global/Project/Session On, or Resume all, cannot override the opt-out. Turning it back on restores the prior captured task; it does not erase failed-check quarantine, make a test pass, approve a Git operation or waive repository/user instructions. Historical action review and recovery remain accessible. This switch is neither a shell sandbox nor authorization to bypass other instructions. It remains accessible without a chat and when disabled. Existing commit, integration and workspace-continuation views sit under the collapsed **Existing chat actions · legacy compatibility** disclosure and still identify the chat checkout as their source; selecting another configuration project cannot retarget them. The read-only Git Explorer remains independent. Saving defaults does not create a worktree, execute a check, commit, integrate, or clean up. Ask requests still require exact human approval; supported saved-Allow/none requests use their independently validated authority, never a fabricated approval. Repository instructions still apply. Managed-action gates are not a sandbox for shell tools, terminals, or external Git processes. **Managed Git tools only · guidance** defaults On and inherits Global → Project → this chat for the selected project. On instructs agents to use guarded Git tools for supported actions; Off lets them choose other tools where permitted. It never changes execution grants, blocks shell commands, overrides stricter repository rules or permits bypassing a denied managed action. Chat-only loads no workflow/commit extensions.

## Select a project without moving the chat

**Configuration project → Use project** selects an allowed physical registered Git checkout root, even while a chat is open. Global → canonical Project → **Chat × Project** inheritance uses that repository, not the chat's cwd. Drafts, revisions and reset controls are separately keyed; saving in B cannot erase A's unsaved draft. Selecting or saving starts no Git action, agent, task adoption or chat move.

In a persisted ordinary chat, the agent can call `git_workflow_propose_settings` to propose a bounded set of field changes at **Global**, **Project** or **Session** scope. Project proposals name an allowed physical registered checkout; Session proposals may optionally name one to target **this chat × that project**, independently of the chat cwd. Omitting a value resets that field to inherit, whereas `null`, `false` and `[]` are explicit saved values. The in-chat card shows saved versus proposed overrides and their effective values; **Apply settings** saves only that scope through the same revision-checked settings path as the Workflow editor. **Dismiss** writes nothing. No settings are changed when the proposal is created. Session Apply is unavailable until the chat is idle and its checkout is free; Global/Project apply does not require an idle chat. A stale revision, moved chat or changed project requires a new proposal rather than silently merging another editor's work. Proposals are bounded process-local review candidates and are unavailable after restart or expiry (30 minutes); a copied transcript/tool result is not apply authority. Applying does **not** capture or reapply a task, start Git work, grant automatic actions or relax project rules. This is a convenience for the authenticated operator, not a security boundary against a same-user agent with shell/browser API access.

Project-qualified chat preferences are plain `pi-web:git-project-settings` entries, keyed by canonical repository root. They do not import old unqualified session overrides or captured tasks. Forks can copy these preferences; copies, session moves and stored records do not create execution authority. Existing Off/Manual/disabled restrictions remain intact. New matching-project Off/Manual/disabled preferences also clamp legacy mutation paths, including chats in repository subdirectories; permissive new preferences cannot relax old restrictions. A saved Project PR/leave delivery setting blocks local integration through the legacy gate as well; a Chat × Project `local` choice cannot cancel that restriction. If a caller's canonical repository cannot be resolved for these restrictions, legacy actions block instead of ignoring them.

For `git_workflow status` and `review`, the new explicit selector is **`repositoryPath` (canonical primary repository root) plus `checkoutPath` (physical registered checkout root)**. Both must be allowed; optional `workspaceBranch` must match the checkout's local branch. Duplicate branch registrations, detached/unregistered checkouts and changed resource identities fail closed. For compatibility, `repositoryPath` alone still names an allowed registered checkout seed and optional `workspaceBranch` selects by branch within it; omitting both retains the calling chat default. Review uses an explicit `targetBranch` or the selected project's saved target, never another project's chat preferences. A prior selection never persists into a later call: A/worktree1 → B/checkout → A/worktree2 needs no chat move. Shell/file-tool cwd, session storage and loaded instructions never change. Branch names alone do not identify a repository.

Browser clients can call `GET /api/git/inspection?repositoryPath=…&checkoutPath=…` for read-only resource status and `POST /api/git/inspection` with `{ repositoryPath, checkoutPath, targetBranch, selection: { kind: "merge" } }` (or `{ kind: "commits", commitOids: [...] }`) for a bounded read-only comparison. Both accept an optional matching `workspaceBranch`. The POST does not create a history card or approval and is not an execution token. Existing session-bound `/api/git/review` and the chat default remain unchanged. The public schema and operation-specific runtime allowlists also support the selected operations below. Unknown or wrong-operation arguments are refused, not ignored; selectors alone grant nothing.

Explicit-project comparisons currently require **Linux directory-descriptor binding**. Git reads the captured checkout/Git/common directory instances through live `/proc/<parent>/fd` paths with explicit Git-directory arguments; temporarily retargeting `.git` or replacing a directory pathname cannot substitute a foreign patch. Unsupported descriptor access fails closed. Resources are rechecked before/after capture and before the comparison result is returned; changed identity blocks the read-only action. Status/settings do not need this comparison mechanism. Captured patches remain private history artifacts, not tool-result text. A new agent comparison returns concise selection/OID/action metadata without a UI acknowledgement; old live pending comparison questions remain answerable on reconnect.

**Selected-project commits** require Linux physical-resource checks, a persisted ordinary chat, a canonical `repositoryPath`, an explicit physical registered `checkoutPath`, complete changed `paths` and an exact `message`. Ask is the default and presents a captured candidate. Both `git_commit operation: commit` and the workflow commit alias accept a separate `confirmation: "none"` request only with fresh effective saved commit Allow, selected-project `commitConfirmation: none`, an enabled managed Ask caller and untouched, session-ID-bound persisted ordinary creation provenance. No human approval is fabricated or UI required for that qualified request. Old, copied/forked, legacy or recaptured chats cannot silently acquire it and must use their existing gates. Default/explicit Ask still requests exactly one candidate approval; Allow alone never suppresses it. Calling-chat canonical Project and Chat × Project Off/Manual/disabled restrictions also clamp an explicitly selected other project, including nested caller directories. Authorization is reread after preview and immediately before ref CAS. A known committed result whose admission resolution fails reports its action ID and recovery requirement—not a stale-candidate invitation to retry. Project/user instructions may still require Ask, and saved Allow never overrides those instructions. Live Deny blocks supported legacy and selected managed actions; stale records fail closed. Allow alone does not suppress Ask for checks, preparation, integration, workspace creation or cleanup: each selected action needs its own explicit none request and live confirmation:none preference. A denied action is not permission to bypass it through a shell. The editor saves Global, canonical Project or Chat × Project Allow/Deny/Inherit against fresh settings/identity revisions; API summaries have `approvalToken: false`. Supervised commits, checks and integration publish durable per-Git-resource intent: partial or uncertain results quarantine further supervised work until inspected. Linux verification uses a positively checked systemd user-service cgroup: unavailable containment refuses checks, and failure/abort retains quarantine. This accounts for check descendants, not an external-writer sandbox. **Check quarantine recovery** is a separate, explicit human review in the Integration view, not a check retry or passing receipt: the original pinned cgroup's durably recorded empty/terminal proof, identical original pre/post Git snapshots, and matching unit, original policy and action evidence are mandatory. For an agent-triggered check, the original policy is reconstructed from the immutable action's target and checks using the same validated ephemeral policy as execution, then compared with the recorded digest; it is not replaced by an unrelated legacy chat policy. The ordinary path requires the current repository snapshot to match the original post-check snapshot exactly. For **later repository movement only**, a separate human-reviewed path requires the same physical worktree identities, repository, branches, policy and saved check, clean current checkouts, a fresh original-unit stopped query and an expiring one-use review bound to both current checkouts. Its preview shows current branch OIDs/status, original OIDs found by matching immutable fingerprints to reachable Git commits (bounded to 8,192 commits), and the original ref fingerprint. Missing historical commits deny recovery; finding them does not attribute later ref movement to an actor. The operator explicitly acknowledges reviewing that drift and potential ignored/out-of-tree effects; fresh GET/POST checks reject any intervening change. This releases only the failed-check quarantine, never a passing check receipt or merge approval. Inspect both worktrees, refs, status and potential ignored/non-Git effects before approving. Changed original pre/post snapshots, changed physical identities, a candidate requiring unavailable original-tree review, dirty later state, simulated/missing/uncertain proof or unknown process state remain blocked; no files are reset, no Git mutation is replayed, and old check receipts/merge plans are invalidated. A check that changed tracked Git state cannot use either bounded path. **Back to chat defaults** returns to the old unqualified settings without copying either namespace into the other.

## Selected operations: current public contract

The public TypeBox schema is in `lib/agent-git-workflow-extension.ts`; selected dispatch enters `lib/git-selected-operation-runtime.ts` before legacy captured-task gates. Tool-description/foundation comments that still say these adapters are unavailable describe an earlier subslice, not the connected source runtime. `status` also retains a narrower legacy capability summary; it is not a complete selected-runtime capability promise.

`git_workflow.operation` accepts `status`, `preferences`, `review`, `commit`, `integrate`, `artifact`, `workspace`, `prepare`, `verify`, `cleanup`, `reconcile`. Inputs are flat public fields, **not** private controller `selector`, `target`, callbacks, proof objects or launch options. `providerAccount`, credentials, arbitrary commands, recovery flags and policy/receipt objects are not Git-operation arguments. Provider-account selection remains separate; do not place secrets in recipes, history or tool requests.

For selected operations, use canonical physical `repositoryPath` plus physical registered `checkoutPath`; optional `workspaceBranch` must match its checked-out local branch. Omitting both deliberately resolves the actual chat checkout (optionally `workspaceBranch` in that repository), never the last browsed project. A lone `checkoutPath` refuses. All resources must be within allowed roots with unchanged registration and physical identities. Selected mutations require a persisted ordinary caller, known active coding tools, trust, live policy/authorization, admission and native authority guards. A **positively verified physical non-Git caller** can explicitly select a Git project without moving, task adoption or a transition; failed/ambiguous Git discovery is not that proof. This does not broaden the special no-confirmation commit caller contract.

Common selected inputs are `operation`, the resource selectors, and optional `confirmation: "ask" | "none"` (default Ask). An action's saved Deny blocks even Ask. Selected project Beta supplies its own branch/delivery/check policy and action authority; caller Alpha's canonical Project, keyed Chat × Project and unqualified chat negatives still clamp it. Beta Allow cannot override Alpha Deny, pause, opt-out, disabled capability or stricter instructions. Alpha's recipes/targets are not borrowed for Beta.

| Operation | Additional accepted public fields and behavior |
| --- | --- |
| `workspace` | `workspaceMode: "current"` is metadata only, accepts only selectors, and starts nothing. `"create"`/`"attach"` require `destinationPath`, `newBranch` (also names the existing attach branch), `baseBranch`, `expectedBaseOid`; attach additionally requires `expectedTipOid`, while create rejects it. OIDs are full lowercase 40/64-hex local tips. No implicit HEAD, remote base, existing-name fallback or chat move. |
| `prepare` | Optional `targetBranch`, `targetCheckoutPath`; target must be the explicit saved **Project main** and its real registered checkout. It cannot be retargeted by a tool argument. One native bounded rewrite attempt or truthful `already-prepared`; never checks/integrates afterward. |
| `verify` | `stage: "none" \| "commit" \| "integration" \| "handoff"` (default integration), optional `checkIndexes`, `revisionDependency`. Indexes name the original saved recipe positions (distinct integers 0–63), not a filtered list. No inline `checks`, target selector or command override. |
| Selected `integrate` | Optional `targetBranch`, `targetCheckoutPath`, `receiptIds`, `revisionDependency`. Uses the selected saved local target/method and required integration-stage checks; a contradictory target refuses. Use explicit repository selectors to choose this path. Legacy inline `checks` are rejected here. |
| `cleanup` | Optional exact `ignoredNames` (no globs); only the selected eligible source worktree **and its local branch**, under separate authority. No force, target override or automatic follow-on. |
| `reconcile` | Optional matching `targetBranch`, `targetCheckoutPath`; fresh native clean/admitted already-prepared state against Project main, not mutation replay or a general quarantine reset. |
| `commit` | Explicit `paths`, exact `message`, optional `mode: "whole-file" \| "staged"`, `confirmation`, `receiptIds`; the same commit surface is available as `git_commit operation: "commit"`. |
| `artifact` | Only `actionId`, required UTF-8 byte `offset`, optional `limitBytes` (4–24576). No resource selectors or mutation authority. |

`status` accepts only resource selectors. `review` additionally accepts a local `targetBranch` (or the selected saved target) and optional ordered consecutive `commitOids`; it is read-only. `preferences` is legacy compatibility with optional inline `{ label, argv }` `checks`, not selected execution policy. A top-level schema field is not accepted on every operation: wrong-operation fields refuse. Selected integration is chosen by `repositoryPath` or selected receipt/dependency/target-checkout arguments, so explicit selectors avoid ambiguity with the legacy inline-check path.

Workspace create/attach authenticates the explicit base/tips, clean source/base state, destination/parent instances and native result. Repeated explicit workspace calls are supported without the legacy one-transition-per-chat limit; neither schedules continue/fork. A newly created worktree-parent directory, if required, is separately captured and any known partial creation is reported, not rolled back or silently retried. Attach provenance is not create provenance for cleanup.

### Saved checks and truthful evidence

Selected checks execute **saved canonical source-Project recipes only**. Effective recipes must match that saved source list; inherited/overridden Global or Chat recipes cannot silently substitute. A recipe accepts `label`, executable/argument `argv`, optional checkout-relative physical `cwd`, bounded literal `env`, and `requiredStage` (default integration). No shell command strings/substitution, URLs, obvious credentials or unknown fields; environment sanitation is not a project-code sandbox. Bounds include 12 recipes, 32 arguments after the executable, 80-byte labels, 256-byte executable/cwd, 512-byte arguments/values, 32 environment entries and 8 KiB total overrides.

Stages are exact, not cumulative. `none` recipes are optional/manual: explicitly select their `checkIndexes` to run them; omitting indexes runs nothing. Commit, integration and handoff select their own required recipes. Direct-main, handoff and standalone optional checks need no fake target, second checkout, task or receipt. Empty selection returns `no-defined`/`no-required`, creates **no passing receipt**, and never waives repository-required checks. Check execution has its own Ask or Allow/none permission, separate from commit/integration confirmation.

Commit-stage native **receipt/snapshot v3** checks the actual dirty working workspace, using physical **manifest v2**: index/HEAD tracked-path union, index bytes, nonignored physical contents, modes, symlink bytes, absent paths and bounded inventory. It is not an isolated selected commit tree. Partial staging remains valid; unstaged fixes and unrelated staged changes can be seen by checks but excluded from the commit. Summaries/history preserve `evidenceScope: "working-workspace"`, `candidateTreeVerified: false`, `repositoryChecksWaived: false`. Ignored caches and external inputs are not fully covered. Clean-checkout **v2** integration/handoff/manual evidence is source-only, not paired legacy v1 or dirty-workspace proof; its summaries likewise do not claim candidate-tree verification or a repository-check waiver. These receipt versions are not interchangeable.

Every saved required commit-stage recipe is enforced by the common commit gate, including Ask, Allow/none, manual/browser and legacy confirm paths. Pass actual returned matching `receiptIds`; no required receipt means no commit. No-confirmation commits do not skip this. A check Deny can therefore block a commit needing checks even with commit Allow. If there genuinely are no required commit-stage recipes, a truthful `no-required`/`no-defined` commit summary is possible without running checks; that still does not waive instructions. Receipt freshness, cohort, exact physical content, source policy and independent check authority are revalidated, including a synchronous final guard under the owned commit boundary. Unsupported inherited commit recipes refuse rather than disappear.

### Preparation, reentry and integration

Preparation never rewrites the explicitly designated Project main, and refuses when that designation is unavailable. Other branches are assumed private under the accepted policy, **unless positive local sharing/publishing evidence or stricter instructions blocks rewriting**; missing Pi Web creation provenance alone is not a blocker. No fetch discovers privacy. Dirty/conflicted/unsupported history, active operation markers and unsupported Git policies refuse. Native preparation verifies exact tracked blob bytes **and modes** through pinned directory/file descriptors, including unchanged paths before/after apply; a cached-stat “clean” status is not sufficient. The original immutable authority revision is retained across owned progress. Async authorization callbacks are followed by mandatory synchronous live-revision guards at no-yield native effect boundaries; no resolved promise, static Allow or changed-and-restored policy can substitute.

Every actual rewrite returns its new source OID, captured target OID, resource scope and action ID to the agent before another stage; old/new mappings and review evidence remain in the captured artifact. The completed, durably sealed result returns an unpredictable `revisionDependency`. Dependent verify/integrate must use the current returned dependency **in a later assistant tool turn**; batched/prequeued siblings are refused. Its strict unconsumed freshness is at most five minutes from native completion. A consumed check launch has a separate completion window capped at 30 minutes (selected check execution itself is capped at five minutes per check); only actual successful completion can issue the successor. `already-prepared` does not mint, refresh or erase a dependency. After adaptation, expiry or a settled recoverable launch, explicit independently proved `reconcile` can renew ordering with **zero carried receipts**, at most three reconciliations per live operation scope. It invalidates old source receipts; active/unknown launches or unresolved native recovery still deny. Restart/history cannot restore a dependency, approval or receipt: old preparation evidence is deny-only, and a fresh live reconciliation must independently qualify.

Integration is separately authorized for the exact candidate and target, using saved **FF-only** or ordinary unsigned **non-FF merge**, never a method fallback, hidden prepare/check/commit, local handoff override or remote publication. Distinct clean registered source/target checkouts, supported policies, required stage receipts and exact live refs remain mandatory. No required integration recipe means truthful no-required evidence, not a fabricated test. A moved target makes the old candidate unusable: inspect the new facts and return to preparation/reconciliation and fresh verification/authorization as applicable; never retry implicitly. Native `target_moved` is precise only when proven; the selected bridge can conservatively return a generic blocker/recovery result rather than promising every native diagnostic is projected. Partial results retain actual checkpoints and recovery evidence, not an invitation to repeat the operation.

### Cleanup, bounds and runtime limits

Retain is the default. Cleanup requires explicit saved `worktree-and-branch`, separate Ask or Allow/none, **authentic create and actual integration facts sealed through native journal/admission**, unchanged eligible history/state and a positive idle-use inventory. It never deletes primary/main/target checkouts or treats an attach/removed checkout/history card as creation proof. One continuous usage lease covers worktree removal and local branch CAS deletion; each effect is durably recorded. Exact ignored-data deletion always asks even under Allow/none. A partial deletion is retained/quarantined for inspection, never forced or retried.

Production inventory uses `readTerminalWorkspaceUsage` plus RPC/persisted-session, check and in-flight producers—not a global “quiet” fixture. Unknown terminal/process inventory denies. An **idle persisted chat inside the candidate still blocks deletion**: explicit relocation is a separate user decision, never automatic. Sealed process-local facts can qualify across live controllers, but parsed old history or restart cannot recreate cleanup capabilities.

These selected source paths are **bounded Linux, fail-closed support**, not a Windows portability claim. Descriptor access, positive systemd user-service cgroup containment for check descendants, live monotonic authority writers, original physical identities and durable admission must be available. Failed/cancelled/uncertain checks can quarantine resources; reconciliation is not containment proof by elapsed time. Preparation's tracked reader caps 10,000 entries, 64 MiB total and 8 MiB/file; the working manifest caps 20,000 paths, 1,024 directories, 128 MiB content, 16 MiB/file/index and 60 seconds of capture. Excess/unsupported/changed state refuses without silent truncation. In-process reservations and cgroup containment do **not** sandbox shell/file tools, terminals, same-user private-state writers or arbitrary external Git writers; races remain outside complete coordination.

`artifact` reads captured private evidence without live Git, UI or policy approval. A Linux descriptor-pinned reader reconciles actual persisted full JSONL and the trusted leaf ancestry with the manager's raw history: cached-only/off-branch anchors and action IDs alone deny. Bounds are 8 MiB history, 50,000 entries, 1 MiB/entry and depth 64. Chunks report whole-patch SHA-256, byte offsets/`nextOffset`, binary/end and `completePatch`; a prefix/suffix/middle chunk is **not** the complete patch. Reads never mint mutation authority and work independently of the old workspace's existence.

## Agent-triggered review and local actions (legacy compatibility)

When Git information is relevant, `git_workflow operation: "status"` can report captured task choices, saved values and origins, live pause/enablement, a concise private task-binding status (never source contents), and the same permission facts shown under **Current task → Permissions & blockers**. Configure related choices in the Workflow panel. `git_commit operation: "commit"` takes explicit complete changed `paths` and an exact `message`; in Ask mode it presents the candidate tree, parent, diff, and message for human approval. The workflow tool's `commit` operation is a compatibility alias of that same path. Manual mode refuses agent commits; Off also refuses human commit actions. Cancellation does nothing, changed candidates fail closed, and partial success requires manual inspection. Native integration now distinguishes allowlisted pre-approval stages from stale candidates without exposing raw failure data: a pre-approval diagnostic means check approval was not requested and no checks or merge ran, not that trust, journaling or verification succeeded. If captured managed integration settings change during approval, old check/target policy is refused before verification; request fresh approval. Read-only/Chat-only agents and subagents cannot use mutation tools to escape their restrictions.

`git_workflow operation: "review"` captures a bounded read-only local comparison (`targetBranch`, optionally an ordered consecutive `commitOids` range), records its exact patch privately and returns concise IDs without waiting for human acknowledgement. The history card distinguishes **Comparison captured** from older human-acknowledged reviews; neither grants permission to merge. Legacy sessions may still use earlier saved preferences and explicit integration arguments. A legacy `preferences` request now offers a link to Workflow rather than a second settings form; opening it dismisses that request and does not continue an operation. That old preference namespace cannot retarget a managed task: managed integration uses its captured target/checks and refuses contradictory arguments.

`operation: "integrate"` takes an explicit local `targetBranch` and an ordered nonempty list of checks (`{ label, argv }`, no shell). It first displays every command for **separate permission to execute project code**. It then checks the distinct registered clean checkouts, trust and durable resource admission; reserves both checkouts against other Pi Web Git transactions and newly starting tools while executing the checks, records state-bound receipts, prepares the exact candidate diff/refs/receipts and method-specific result (a new merge commit or the existing FF tip), and displays a **second** card for approval of that exact plan ID. It releases gates while waiting for user input and reacquires them for the final exact-state unsigned non-fast-forward merge or fast-forward. Stop cancels pending UI and running checks. Any failed check or stale checkout requires a fresh review; a `partial-state` result requires manual recovery. This tool does not rebase, perform a remote operation, or clean up the feature worktree.

**Blocking Git questions wait for you without an automatic response timeout.** This covers preferences, commit approvals, check permissions, exact merge approvals and any still-live comparison request created by an older wrapper. New read-only comparisons do not ask a question. A live request survives browser disconnect/reload; answering, Stop or session teardown settles it. Server restart does not restore executable approval. Waiting is not permission and does not renew verification: native merge plans/check receipts and manual browser previews retain their own freshness limits, and every eventual approval still revalidates the candidate. If those checks fail, prepare a fresh candidate rather than reusing or silently transferring the old approval. Command execution timeouts are unchanged. The operation-specific approval button is the decision: no extra “I reviewed” checkbox or acknowledgement gate is required. File/check selectors still select scope, and permission to run checks remains separate from approval to merge.

For resource-using legacy calls without an explicit `repositoryPath`, the three agent Git tools accept an optional `workspaceBranch` naming a checked-out local branch in another registered worktree **of the calling chat's repository**. Without it, they use the chat checkout. The selected worktree must be a physical checkout inside Pi Web's allowed file roots; an arbitrary path, unrelated project, detached HEAD or remote branch is not accepted. The chat's policy and identity remain authoritative, not those of any session in the selected worktree. Review and approval cards identify the source checkout; verification commands execute there. When a tool can collect the relevant choice/approval, agent guidance prefers it over asking in prose, provided repository and user instructions permit; this never skips a required approval or overrides stricter rules. See [ADR 0009](adr/0009-cross-worktree-agent-git-tools.md).

**Source support is not autonomous orchestration.** Selected workspace/preparation/check/integration/cleanup and recipe environments are connected as described above; legacy actions retain this section's separate gates. Automatic scheduling, background retries, remote delivery, replay and comprehensive prose-policy interpretation remain outside the implementation. Mandatory per-task ownership was withdrawn, not postponed. A closed dialog or prepared OID is not a successful result. Native hooks/signing/filter restrictions remain. [ADR 0011](adr/0011-policy-driven-git-tools.md) and [the active plan](plans/2026-09-29_policy-driven-git-tools-plan.md) supersede incompatible future directions; ADR 0010 and earlier slice evidence remain historical.

## Configure defaults and legacy task choices

The five rows—Workspace, Commits, Checks, Delivery & preparation, Cleanup—are edited at **Global**, **Project**, or **Session** scope (Chat × Project when a configuration project is explicitly selected). Fields inherit individually with origins and explicit reset. Explicit Off, no target (`null`), and no checks (`[]`) do not mean inherit. Ordered check lists replace rather than concatenate. Project names `mainBranch` and can set `baseBranch` and `targetBranch` to either a local branch, `null`, or symbolic `:project-main` (invalid as a Git branch name; resolves only against that project's main, leaving old literal `project-main` branches unchanged); Global can use only the symbolic/null forms, never introduce branch names or nonempty recipes. Newly saved Chat × Project overrides also cannot introduce branch names/recipes. Older records with named Global or unqualified Session defaults stay readable and may be retained unchanged, but do not gain new execution consent. Direct/current-checkout strategy reuses an already selected compatible checkout; worktree strategy permits explicitly requested creation or selection without a mandatory chat move. `delivery: pr` and `leave` suppress local integration; they do not fetch, push or create PRs. `method: ff` selects the guarded FF-only engine for supported session-bound local integration; historical squash stays read-only.

Global/project settings live privately in `~/.pi/agent/pi-web/git-workflow-settings.json` (or under `PI_CODING_AGENT_DIR`), separate from Pi's settings and repository files. Project identity is canonical across linked worktrees. Existing `git-workflow-defaults.json` remains readable until that project's settings are saved in the new store; resetting to an empty project override then inherits Global instead of resurrecting the old file. Importing legacy defaults never grants new automation: legacy agent-commit defaults become Ask for newly managed sessions. For an explicitly new agent-commit configuration, the editor offers one draft action setting commit availability to Ask and the confirmation preference to none; it does not save either field, alter inherited Off/Manual/Ask or captured tasks, bypass a chat opt-out, or create a saved Allow. Existing saved defaults remain Ask until explicitly changed.

Save applies only to the named scope. Drafts survive scope/panel navigation, and unsaved parents do not alter another scope's inherited display. Revision conflicts require a deliberate reload/reconciliation instead of overwriting another client's changes. Global/project editing never creates a chat. Session editing currently needs a persisted idle ordinary chat; initialized-but-unsent chats do not queue hidden overrides in this editor.

New chats capture effective defaults in versioned non-context metadata. Existing legacy sessions remain pinned, including their explicit old agent-commit consent. Saving defaults or session overrides does not retarget the **current task**. Use its explicit Apply action to capture the saved effective choices. Fork/clone preserves those captured preferences, not newer defaults or live approval capabilities. After v2 adoption a preceding v1 opt-out prevents an older runtime from skipping the new record and reviving older commit consent; malformed/newer configuration blocks managed execution rather than falling back.

Enablement and commit Off are live restrictions, rechecked by already-loaded tools and browser mutation routes. Lower-scope explicit enablement can override a global default-off. **Pause all managed Git actions** is separate and unconditional: it cannot be overridden by project/session defaults. Pending approvals cannot bypass a later pause; cancellable checks observe it. A ref/index update already at its apply boundary is not interrupted halfway. Neither toggle controls external Git writers or arbitrary shell programs.

Permission summaries and live route/tool gates share `lib/git-workflow-permissions.ts`. They distinguish agent requests from explicit human actions: Manual refuses the agent but still permits human review, Off refuses both, and Ask requires exact approval. Read-only/Chat-only tool selection does not prevent the operator's human actions; subagent sessions refuse both. Unknown active tools are not assumed to be Full: a disk-only session without a saved tool selection reports that agent eligibility needs loading, without starting a wrapper. Legacy worktree starts are labelled **Saved policy**, not falsely described as a fresh approval; legacy commit consent remains a separate compatibility fact. These are settings/actor checks, **not** a grant or a successful repository/candidate preflight.

Each workspace, commit, preparation, check, integration and cleanup confirmation preference has its own origin and reset (commit availability remains Off/Manual/Ask, independent of commit confirmation). `none` is **not an Allow grant**: saving it alone never authorizes prompt-free execution. Each supported selected action additionally requires its own fresh effective Allow and explicit `confirmation: "none"` request under compatible instructions; commit has the extra untouched fresh-creation caller requirement. Other existing exact approvals and native blockers still apply. Cleanup defaults to retain; explicit eligible worktree-and-branch cleanup is separately gated above. The editor summarizes confirmation changes and their scope before Save, which changes no task or action. An empty configured check list does not waive tests required by project instructions. Automatic remains unavailable, including in settings writes. Private binding/source evidence now exists, but it is not task authority or executable policy. The connected selected confirmation-free operations enforce validated project/action scope, separately saved authorization/revocation and native admission/recovery safeguards. Legacy Git-action records without recoverable resource identity can conservatively deny new commit admission even when their old checkout has been removed; the UI and API do not present a reset or bypass for uncertain effects. ADR 0011 withdraws mandatory task/source adoption and full prose-policy normalization as prerequisites; the current runtime still refuses Automatic. No imported record, ordinary preference, status response or editor draft supplies execution authority.

Current legacy execution supports the calling checkout or a dedicated worktree from an explicit local base; continue/fork/stay; Off/Manual/Ask commits; executable/argv checks; a local FF or unsigned non-FF target or none (each requires its exact plan and receipts); and resource retention. Selected operations additionally resolve live direct/worktree, main/base/target, local/PR/leave, stage recipes and independent action confirmation/Allow; they do not reuse legacy task consent. Native fast-forward is available for an existing linear feature tip whose target is on its first-parent chain; it reuses exact receipts and approvals without inventing a merge object. Historical squash remains unsupported. Agent preparation and eligible cleanup use the selected runtime, not these legacy controls.

## Explicit task binding and source review

**Existing chat actions · legacy compatibility → Current task → Source evidence · optional legacy metadata → Task binding & source review** is an optional metadata interface, not a prerequisite for Git settings or actions. To review this legacy task metadata, first capture saved task settings with its existing Apply action. In an idle persisted ordinary chat, name a goal, explicitly select an originating user request from the current branch, choose an existing registered local checkout, and list any delegated Markdown skills/documents needed for this review. A dependency is relative to that selected checkout or an explicit allowed absolute path. The app does not follow prose links, discover referenced skills automatically, fetch URLs, or execute resources.

Select **Preview task & instruction sources**. A linked instruction/dependency path first discloses its exact physical Markdown destination; **Read these exact source destinations** permits only those file reads, not their surrounding directories. Subsequent destination prompts retain earlier explicit selections. Inspect the complete captured text, settings, session/request and checkout identity, then use the single **Adopt reviewed task metadata** button. There is no review checkbox or response timer. Replacement/cancellation/restart loses the live preview; confirmation always revalidates sources, session/settings, checkout/branch/HEAD and the previous private generation. Supported settings writes—including legacy defaults and Pause-on/off round trips in another process—change a durable write epoch, so restoring equal values cannot revive an old preview.

The source-discovery contract is pinned to SDK 1.0.0 (previously captured 0.99.1 and older source sets require renewed review): global and root-to-cwd context selection in `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, `CLAUDE.MD` order, including missing higher-priority candidates and nested-worktree shadowing. Shadowed selection-critical documents are captured separately as probes, not labelled loaded instructions. Missing named dependencies, unreadable/nonregular/invalid UTF-8/binary/oversized sources and changed directory/file identities block the entire review. Limits are 24 named dependencies, 64 total captured documents/probes, 256 KiB per file and 1 MiB of source bytes; there is no silent truncation or fallback. **Secure source capture currently requires Linux and descriptor-relative `/proc/self/fd` access**, with readable parent directories. Parent components are pinned with no-follow descriptors and the opened file identity is checked before reading bytes; unavailable platforms/capabilities do not fall back to weaker reads.

Private immutable snapshots and generation heads live under `~/.pi/agent/pi-web/git-task-bindings/v1/` (or `PI_CODING_AGENT_DIR`); the separate write fence is `pi-web/git-workflow-write-epoch.json`. Each adoption creates a fresh private binding ID; generations increase across adoption, release and invalidation. Records bind the physical session file/header, user entry digest/goal, captured settings and physical registered workspace/Git-directory/branch identities. Reads do not create records or AgentSessions. No anchor, copied source text or synthetic user turn is appended to the transcript, and startup/default snapshots cannot mint a binding. Ordinary copies/forks/imports do not inherit it; moves and settings recapture invalidate it, including failed moves. After server restart, retained evidence requires fresh review rather than resuming work. Release is a tombstone, not deletion. A malformed/newer/missing head or artifact in an existing namespace fails closed; orphan snapshots never reconstruct it. Atomic publication syncs directory entries, including retries after an earlier sync failure.

**Adoption does not approve any Git operation, start a coding task, reserve ownership, reload the agent's instructions, or retarget existing tools/action views.** A “current” source snapshot means checked disk evidence, not proof of loaded instructions, complete prose-rule coverage or normalized executable policy. The unchanged Ask/Manual/legacy and native transaction safeguards still govern actions. One current binding slot per session is supported. ADR 0011 replaces the proposed mandatory orchestration/ownership/handoff model with independently scoped operations; these binding records will not become grants or a required setup step. No artifact deletion/export UI is provided yet. Private storage/digests are not a sandbox against a same-user process rewriting private state, and comprehensive external-writer admission is still missing.

## Durable action history

Commit, review, verification and integration cards retain their captured candidate and result across browser reload, raw branch-history pagination, compaction and chat moves. New records distinguish the captured canonical project, physical source checkout and physical target checkout (where available), with versioned Git-common and project-directory instances for conservative recovery classification. Older cards keep their original `repositoryRoot` as a source-path label, never an inferred canonical project. Complete new evidence can keep its own repository quarantined after a feature worktree disappears without blocking a positively distinct repository; older path-only unresolved actions remain globally quarantined because their original directory instances cannot be proved from current paths. These identities are evidence, not execution authority. Existing legacy agent-consented commits are recorded too. A fork can display inherited references after the original session is deleted. Cards read private artifacts, never today's working files or Git objects, so declined patches survive Git garbage collection and removal of their old workspace.

- A compact card identifies its operation, source, branch, message, timestamps, decision and outcome. Expand **Captured candidate** for selected paths and lazy per-file **Side by side**, **Unified**, or **Raw patch** views. Split columns scroll independently on phones. These are captured hunks, not arbitrary full-file history; binary/metadata-only and unavailable/oversized content are explicitly labelled.
- A live agent request is coalesced into its matching card. Only that original server-owned request can expose approval controls. Browser-origin actions are approved through their existing Workflow detail; history never offers a replay button. Stop and decline are distinct; unanswered agent Git questions have no response timer. Expired/interrupted history still represents lost process ownership or unavailable live candidates. After server restart, pending history is expired/interrupted and uncertain execution needs recovery; nothing resumes automatically.
- **Prepared OIDs are not completed results.** The commit engine records its intended object before updating the ref, and integration records intent before touching the target checkout. Actual successful/partial results are recorded afterward. An integration `partial-state` merge OID may still be only the proposed object, not an updated ref. If recording fails after mutation, retain the known result and inspect the checkout; do not repeat the operation.
- Private, bounded, digest-checked records/artifacts live under `~/.pi/agent/pi-web/git-actions/v1/` (or `PI_CODING_AGENT_DIR`). Tiny plain SDK `pi-web:git-action` custom entries contain only version/action ID. They are **not** `custom_message` entries and never add patch-sized data or fabricated user turns to model context. History GETs do not create AgentSessions. SSE supplies small revision notifications; visible cards also reconcile through GET. Another idle browser's newly added anchor appears on transcript refresh.
- Artifacts have no automatic deletion or export UI yet. They remain independent of session/worktree cleanup; missing or incompatible artifacts show a placeholder, not substituted current content. Standard SDK session HTML export does **not** include these private artifacts. Checks retain their approved commands and outcome; their private native logs are not yet exposed in a card log viewer. Selected workspace, preparation, checkout-verification and cleanup now also retain durable candidates and measured outcomes. Legacy creation/continuation and preference editing retain their existing live UI; neither gains replay authority. Raw shell Git is not automatically instrumented.

## Worktrees and continuing a chat (optional legacy controls)

The selected `workspace` operation above creates/selects resources without a task or chat transition and supports repeated invocations. The one-shot start/continuation behavior below belongs only to `git_workspace_start` and does not limit selected operations.

Use **New worktree…** in the sidebar from a Git checkout root. Explicitly choose a local base branch and review its full expected HEAD; choose **Create new branch** with a new name, or **Attach existing local branch** with its full expected tip. The server rechecks the refs and rejects stale tips, an existing create-branch name, an already checked-out attach branch, dirty source/base checkouts (including untracked files), and existing destination directories. It creates from the chosen base commit, not an implicit current HEAD or a remote-tracking ref; it does not fetch. Worktrees live under `<repo>-worktrees/<sanitized-branch>`. See [Worktrees in Pi Web](./worktrees.md) for switcher and removal details.

For a persisted idle chat at a registered checkout root, open **Workflow** and its workspace detail, choose a *different already registered* worktree from **Destination worktree**, and select **Continue here…** or **Fork chat here…**. Each action presents a separate confirmation before relocating the same chat/session family or creating a new chat at that checkout. Fork requires an assistant leaf. The manual controls do not create a worktree. Neither manual action is triggered by a policy save or a sidebar worktree creation.

In an ordinary persisted chat with a **captured worktree-mode task or legacy saved policy**, the agent can explicitly invoke `git_workspace_start` to create a **new** branch and linked worktree from its saved local base branch and a supplied full expected base OID. If a managed worktree task's captured base is **missing**, the agent may instead pass `baseBranch` as explicit operation input with the full expected tip: exact human approval creates that one worktree only, leaves the chat where it is, and does not Save/Apply a base, grant future work or schedule `continue`/`fork`. An existing configured base cannot be overridden through this argument; current-checkout tasks, opted-out/legacy-unconfigured chats, read-only/subagent modes and live Pause/disablement remain blocked. A managed task requests human approval before creation; pause/disablement is rechecked before creation and automatic continuation. This invocation, not the saved preference alone, records the checkout created and the `onCreate` action. When **that run** settles and the chat is idle, Pi Web attempts the recorded **continue** or **fork** once on the server, even without a connected browser. `stay` creates only the worktree. Selecting another creation source with `workspaceBranch` does not move or fork a chat in that source: `continue`/`fork` still applies to the calling chat. A private receipt is claimed before movement; a reconnect or server restart never replays a prior receipt. Only one automatic start is supported per chat: use the manual worktree controls for later starts. If persistence, checkout validation, cloning, or relocation fails, the worktree (and any fork already made) remains for manual inspection; a failed attempt is **not retried automatically**. The UI follows successful transitions and displays a manual-recovery notice on failure. Do not start a new worktree merely to retry a failed transition. A late settings/source recheck closes the ordinary asynchronous preflight window, but externally replacing the destination parent directory between the last native identity check and Git's path resolution is not coordinated or guaranteed race-free; inspect unexpected paths/partial results manually.

While an agent run is waiting for input, Session Save and task Apply are unavailable. For a missing base, the create-only proposal above avoids the circular instruction to edit settings during the run. If automatic chat continuation is required, Stop the run, Save the Session base, explicitly Apply the effective saved settings to the task, then resume. Cancelling a question alone may continue the run; the Workflow panel does not silently replace a captured task. Old app-generated `pi-web:git-workflow-context` reminders remain in raw history but are filtered from future ordinary model context; they are not user requests or current authority. Conditional Git guidance is an instruction-layer section, not a new synthetic user message. Chat-only/subagent inherited context filters are scoped to the exact old reminder type; SDK summarization may retain already flattened historical text, and existing loaded wrappers need a reload to receive the new extension. No actual mutation gate is weakened by this guidance change.

All continuation/fork paths leave **uncommitted source files in the original checkout**; they never copy, stash, or reset them. The manual UI displays changed-file status as a warning. Use Git yourself to move changes if needed. Manual continuation/fork is disabled while busy; the server checks session state and registered checkout identity. If a fork is made but moving it fails, use its reported ID to inspect it, not a blind new fork.

## Review and commit selected files

The commit detail inside **Workflow** is a human action on a persisted ordinary session, using its actual saved cwd rather than the sidebar's selected checkout. The cwd must be a physical Git checkout root on a local branch. Choose **Whole files from working tree** (default) or explicitly choose **Only selected staged index entries**; select changed paths (none selected by default), enter a message, then **Preview** and separately **Confirm commit**. In staged mode the candidate uses the named index entries only, includes both paths for a selected staged rename, and preserves other staged entries and unstaged edits. Optional working-tree file diffs are *read-only aids*, **not** the authoritative candidate: unsupported/binary/large patches can be absent while the selected content is still in the candidate. Preview reports checkout, branch, parent HEAD, selected paths, the exact candidate tree, and a bounded **candidate tree diff** against HEAD; inspect them before confirming. If that exact diff is too large, the UI says so instead of displaying a truncated patch. You can still identify the tree and review through Git, but do not treat an unsupported working-tree file preview as a replacement for the candidate diff. Changing selection/message or refreshing clears the preview in the UI. The server authenticates a preview token and re-derives mode, branch, HEAD, index bytes, paths and tree at confirmation, refusing a stale candidate. The token is process-local and does not survive a server restart. Browser preview also binds the exact message to a single-use, session-scoped live action ID; both are required at confirmation. An abandoned browser preview expires after 15 minutes (an integration proposal may expire sooner). A stored card or copied fork reference cannot recreate it.

The legacy `git_commit preview/confirm` interface remains available **only for an existing saved `commits: agent` session policy**. Managed tasks use the common Ask path instead; neither defaults nor a tool argument create automatic commit authority. Both interfaces and the browser enforce the same live pause/enablement gate. Default whole-file mode refuses a dirty/staged or conflicted index; explicitly requested staged mode accepts selected changed index entries while refusing conflicts, nonstandard flags, unsupported submodules and unsafe filters. Both modes reject unsupported configured hook, signing or filter policies; neither runs hooks, signs commits, or runs configured filters. Both build an authenticated temporary-index candidate tree, use `commit-tree` and a compare-and-swap ref update, then install an index preserving unselected staged entries in staged mode. It does not push or integrate. It cannot promise atomicity against arbitrary external Git writers: if the branch ref advances but checkout/index finalization fails, the result is **partial success** with the created commit ID, tree, parent and author email. Inspect the branch, index and checkout before taking any further action; **do not retry blindly**. Other failures can require a fresh status and preview.

Agent Ask commits and legacy preview/confirm now reserve the same in-process checkout gate as browser commits during capture and application, never while waiting for an answer. Another session merely active in or targeting the checkout does not block commits, checks or integration. A concurrent Pi Web Git transaction still blocks on its checkout reservation; uncertain operations remain quarantined by durable admission. An approval remains recorded even when subsequent admission fails. An already-running arbitrary tool or external Git process is not stopped by the reservation; native stale-state checks remain essential and external writers can still race them. This is not exclusive workspace ownership or sufficient admission for Automatic.

Native commit preflight refuses unfinished merge, rebase, `git am`, cherry-pick/revert sequences, and bisect state, even with a clean index. Checks use the selected worktree's Git directory and run again immediately before ref CAS; markers and historical refs are never removed to make an operation succeed. A known operation-state refusal after intent recording is **blocked**, with prepared identity retained but no claimed result. Unclassified post-boundary exceptions still require recovery. External writers can race these checks; nothing auto-aborts or retries their operations.

## Local integration review and explicit approval (legacy/browser path)

With a captured task or legacy saved policy containing an integration target, open the integration detail inside **Workflow** in a persisted ordinary chat. It derives the feature from that chat's checked-out local branch and the target from the *saved session* policy; both must be local refs. The target commit must be an ancestor **on the feature's first-parent chain** (being a second-parent ancestor is insufficient). Git computes a proposed merge-result tree; conflicts or unavailable `merge-tree --write-tree` prevent a review. No checkout files, index, uncommitted edits or remotes are included.

Choose a patch for the **whole proposed merge** (target tree → merge-result tree), a **single commit** (its first-parent tree → its tree), or an ordered **contiguous** range on the feature's first-parent chain (tree before its first commit → last commit's tree). Ranges are cumulative, not individual patch bundles or cherry-pick previews. The UI shows exact ref and tree IDs; the server checks both branch tips before and after generating a bounded patch, and stale tips require refresh. Binary differences are summaries, not full contents; an oversized patch fails rather than returning a partial one. These selectable patches are **read-only comparisons**, not approval cards. An explicit **Show read-only patch** captures that comparison in history; its outcome means the comparison was captured, not that a person approved execution.

For a saved **merge or ff** method and configured checks, the separate integration section lists check labels and matching, time-limited successful receipt IDs. Run each check explicitly; these commands execute local project code and can modify files. Passing checks are not approval. After every check has a matching receipt, select **Prepare exact integration proposal** to get an exact plan ID, feature and target OIDs, a merge commit ID **or the existing FF result tip and its actual parents**, receipt IDs and the bounded **authoritative candidate diff**. Inspect the candidate (binary contents are summarized), then select **Confirm exact plan**. There is no additional review-acknowledgement checkbox or button. Neither verification nor planning confirms automatically. Confirmation rechecks exact checkout/ref/policy/index state; stale failures require refreshing and verifying again. If the approved target ref provably moves before apply, browser and agent receive `target_moved`: stop, inspect the new target and request a fresh review, checks and approval; there is no implicit rebase or retry. Other staleness stays a generic refusal. A **partial-state** result means checkout/ref/index finalization may have failed: inspect both worktrees, refs and the reported recovery record manually; do not retry blindly. Only explicit ordinary unsigned non-FF merge or FF to the existing feature tip is available; FF creates no merge commit, and may preserve an existing feature signature. Squash, worktree cleanup, remote fetch/push/publication are not performed.

Local integration requires **distinct registered feature and target checkouts**, a clean standard index and checkout on both sides, a target on the feature's first-parent chain, a reproducible merge result equal to the feature tree, supported Git policies (no configured hooks, signing, filters or attributes), and successful receipts for **every** saved check. Pi Web holds an in-process prompt/checkout gate during the merge; other Git processes are not coordinated. The verification commands themselves are explicitly selected, never run merely because they were saved. This legacy/browser integration path performs no rebase. The independent selected `prepare` operation can perform an authorized native rewrite, return to the agent, then require fresh checks/ordering before integration. A failed attempt after checkout begins retains a private recovery record, not an automatic rollback. Cleanup remains a separate, explicit worktree action; no cleanup is implied by integration.

The Git workflow's Windows portability has **not been verified**. Do not assume these paths, Git policies or transactions have been tested there.

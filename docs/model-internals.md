# Model and account implementation contracts

Implementation reference moved from `AGENTS.md`; repository-relative code paths remain unchanged. Read the relevant section before modifying that area. Focused user guides and ADRs linked below retain their existing scopes.

### Generated session titles
General Settings stores a server-wide optional title model beside the title language in `~/.pi/agent/pi-web/title-settings.json`. The default is the session model. A selected provider/model ID resolves through the active session's `ModelRuntime` so it uses that session's provider account, without switching the chat model; if it disappears, title generation errors rather than silently charging the chat model. The picker lists models visible for the selected session via `/api/models`.

### Model defaults for new sessions
`GET /api/models` returns `defaultModel` read from `~/.pi/agent/settings.json`. `ChatWindow` pre-selects this on mount for new sessions. Explicit browser model/thinking selections are applied atomically during AgentSession construction, then `lib/startup-preferences.ts` persists their effective values without replaying `set_model`/`set_thinking_level`; implicit `enabledModels` fallbacks and thinking pins are not persisted.

### Session model speed
`pi-web:model-speed` custom entries store only `standard` or `fast`, independently of Thinking. The latest valid entry across the entire session wins (not branch-local); legacy sessions default to Standard. Copy the current value explicitly on forks/clones/subagent creation and preserve it during transient account/tool recreation. Never persist a global/browser speed default.

`lib/session-model-speed-runtime.ts` wraps the pinned SDK 1.3.0 runtime with a **session-local proxy view**, never mutating a runtime shared with subagents. Matching native `openai-codex` / `openai-codex-responses` chat streams must carry the owning agent's active signal **and** payload callback (session ID alone also matches SDK auxiliaries). They use full runtime options (`default` / `priority`), preserving auth, reasoning, token clamping and request/header hooks; `streamSimple` drops the tier, and payload-only injection loses pricing intent. Auxiliary calls and other providers/session IDs keep existing behavior. Reject conflicting payload tiers; retain native priority pricing and correct only explicitly reported legacy Codex `fast` from recomputed base costs. The picker is request intent, not delivered-tier proof, and dollar estimates are not subscription quota charges. Review this adapter on SDK upgrades; see `docs/model-speed.md`.

### Remote provider catalogs
pi's built-in model lists are generated when the SDK is built and pi-web pins one SDK version, so a model a provider ships after that release is invisible until pi-web publishes a new version (#914). The SDK carries the other half: each built-in provider is wrapped in a pi.dev catalog overlay that `ModelRuntime.refresh()` fetches and persists to `~/.pi/agent/models-store.json`, and restoring that overlay needs no network. Both of pi-web's refresh paths ask for the offline half only (`createAgentSessionServices()` and `lib/provider-usage.ts` pass `allowNetwork: false`), which is why running the pi CLI once used to be the fix — the CLI refreshed with the network on and pi-web read what it left behind.

`lib/model-catalog-refresh.ts` runs that network pass, and **only when the user asks for it**: the "Refresh catalog" button in `EnabledModelsSection` posts to `/api/models/refresh`. Nothing refreshes catalogs on a timer or on another request's path — a pass fetches a catalog per authenticated provider, and a save must not wait on a slow one, the same reason `/api/auth/api-key/[provider]` stores the credential itself instead of calling `ModelRuntime.login()`. `refresh()` is called with `force: true`, since pressing the button is exactly a request to skip the SDK's four-hour freshness window, but *without* `allowNetwork`, so the runtime keeps applying its own `PI_OFFLINE` rule instead of pi-web overriding it; the module reports `reason: "offline"` rather than pretending a pass ran. `shareModelCatalogRefresh()` joins concurrent presses only for the same complete account snapshot and provider set. All passes within one store scope are serialized, including all-provider/subset overlaps; different identities never join. The backend accepts optional validated `accounts` on `/api/models/refresh`; missing or empty means Pi default, not project defaults. A present `provider` must be a nonblank string; invalid filters return 400, never widen to all providers. Account-management UI is unchanged.

Change detection deterministically serializes model identity, capability, thinking, input limits, token limits, cache and pricing metadata (not credential-bearing headers), never the stored bytes: a successful revalidation rewrites `checkedAt` and `etag` on every pass. It only decides whether `invalidateModelsCache()` runs and whether the panel reloads — the overlay itself reaches the UI through the ordinary `/api/models` and `/api/models/enabled` loads: the former builds services on cache misses and the latter refreshes its settings-only runtime offline to restore the store. The refresh route never returns a model list of its own.

### `enabledModels` scoping
The `enabledModels` setting uses pi's `--models` syntax: minimatch globs against `provider/modelId` or a bare `modelId`, fuzzy matching for non-glob patterns, and an optional `:thinkingLevel` suffix. Never compare those patterns as literal strings — `lib/model-scope.ts` delegates to the SDK's `resolveModelScopeWithDiagnostics()` so pi-web and the TUI agree on the visible model list, and falls back to all available models when patterns resolve to nothing. `startRpcSession()` resolves that scope before creating an AgentSession and passes the selected initial model, thinking pin, and SDK-native `scopedModels` atomically; `GET /api/models` reuses the helper only for selector data, `thinkingLevelPins`, and `modelScopeWarnings` display.

SDK 1.3 returns all provider matches for an ambiguous bare model ID. The settings editor reflects those matches so the entry can be repaired, but selector/session startup still rejects ambiguous exact entries and requires `provider/modelId`. Disabling one owner rewrites the survivor explicitly, preserving its thinking pin; disabling the last model remains refused. The editor's SDK matching is not permission to bypass startup validation.

Editing that setting from the Models panel goes through `/api/models/enabled`, never through pattern strings composed in the browser. Each toggle is a **minimal edit** of the stored list (`lib/enabled-models.ts`): a pattern that matches no available model is preserved verbatim, only the pattern covering the switched-off model is expanded in place (keeping its `:level` suffix), and every provider that ends up fully enabled with two or more entries collapses back into one glob — pi refreshes provider catalogs from the network into `models-store.json`, so an enumerated list rots when a model is renamed (deepseek's `deepseek-v4-flash` became `deepseek-flash`), while a glob heals itself. A lone exact reference is a deliberate pick and is left alone. **Never assume `provider/*` covers a provider**: pi matches with minimatch, whose `*` stops at `/`, so that glob silently misses every nested model id (`commandcode/sakana/fugu-ultra`, most OpenRouter ids) — writing it turned "enable all" into 15 of 71 models. `resolveProviderGlobs()` resolves `provider/*` then `provider/**` and keeps one only when its match set is exactly the provider's models; a provider that neither covers is written model by model. Also never rewrite the whole list from `getAvailable()` the way the TUI's `/scoped-models` does — it only sees providers that currently pass `checkAuth()`, so that would delete every entry for a provider whose credential is missing right now, and flatten globs and pins.

Disabling the last enabled model is refused with `409 { reason: "last-model" }`: pi falls back to every model when a scope resolves to nothing, so an empty list silently means the opposite. Writes always target the global settings file; a project `.pi/settings.json` replaces the global array instead of merging, so the route reports `scope: "project"`, renders the switches read-only, and returns that file's path as `settingsPath` — the banner names the file it just wrote (`~/.pi/agent/settings.json · enabledModels 20/104`) instead of describing the effect in prose. Built-in *and* extension-registered providers get per-model switches; models.json providers are switched as a whole by `EnabledModelsProviderSwitch` in their detail header, next to Delete, because a custom model can simply be deleted and both bulk buttons only ever sent the same provider-wide write. That switch is on only when every model of the provider is on, so a partial selection reads as off beside the sidebar's `1/2` badge and one click completes it; reading it as "any enabled" would leave partial unreachable in both directions once the last-model guard blocks the way down. Why it cannot move is its tooltip, not body text. `op: "prune"` is the only operation that drops unmatched entries, for cleaning up after such a rename; everything else preserves them. Saving models.json re-reads the switches through `op: "resync"`, which repairs the stored patterns against the new catalog: it rewrites renamed **models** and then renamed **providers**, **cuts back entries whose provider prefix no longer scopes them**, and re-asserts the providers that were fully enabled before the save. (Model references first: they still spell the old provider id, which the provider rewrite would otherwise have replaced already.) All three are needed because a pattern's meaning depends on the catalog. pi matches a pattern against the bare `modelId` as well as `provider/modelId`, so `stepfun/*` also matches another provider's model whose id *is* `stepfun/Step-5-Preview` — renaming a provider to `stepfun` silently enabled three `commandcode` models, and switching stepfun off then wrote them into the file. In the other direction, renaming a model to an id with a slash drops it out of `provider/*` (minimatch `*` stops at `/`), so a fully enabled provider silently loses it. A model renamed in the panel is a known move, not the kind of mismatch worth preserving: leaving `stepfun/ddd` behind after it became `stepfun/ddd1` loses the selection, and when it was the only entry the scope resolves to nothing, which pi reads as "no scope" and quietly enables every model. `ModelsConfig` mirrors every array move of the draft in `savedModelIdsRef` so `collectModelRenames()` can tell a rename from an add or a delete without guessing. Only `resync` repairs entries; ordinary toggles stay minimal edits and never rewrite what the user did not touch. A models.json provider missing from the runtime (unsaved edits, no models, a key that does not work) must not be reported as a sign-in problem, which is why it has its own control: the switch renders disabled with that reason as its tooltip, while `EnabledModelsSection` — now built-in only — keeps the sign-in empty state. See `docs/adr/0004-enabled-models-toggles.md`.

### Subagent model references

Subagent call/profile references use exact whole-ID-first lookup with an optional valid `:thinkingLevel` suffix, not fuzzy CLI resolution or auth-based provider disambiguation. Literal colon-containing IDs win. Explicit call thinking beats the suffix; call suffix beats profile thinking; otherwise the selected profile's thinking/model suffix precedes the parent's level. SDK capability clamping still applies. Account and speed bindings are unchanged. Child-context input-file budgets use an early existing-runtime estimate and a final offline, trusted-services recheck of the loaded bytes; see [Session contracts](session-internals.md).

### Provider account selection
- Pi's `auth.json` remains the single-credential-per-provider **Pi default** shared with the CLI. Additional identities are stored only in permission-restricted `pi-web-accounts.json` by `lib/provider-accounts.ts`; never return credential values from account routes.
- `lib/session-accounts.ts` persists a complete provider-to-account snapshot in `pi-web:provider-accounts` custom entries. Legacy sessions with no entry use Pi default; project defaults (keyed by `resolveProject(cwd).projectRoot`) apply only to new sessions. Forks and subagents copy the snapshot even when their branch history omits its earlier entry.
- `lib/account-model-runtime.ts` captures and validates a frozen complete provider-to-account snapshot before SDK awaits. Empty selections retain `agentDir/models-store.json`; selected identities use `agentDir/pi-web/model-stores/v1/<sha256 of sorted provider/account-ID entries>/models-store.json`, with restricted directories. The same snapshot binds credentials and catalog storage. The extension runtime helper accepts only self-bound immutable bindings constructed here; malformed supplied bindings (including null and legacy credential stores) reject before SDK initialization. Omitted/undefined arguments retain Pi default. Keys never depend on credentials or labels. Never copy or fall back to a shared catalog with unknown ownership: SDK 1.2.0 persists personalized OpenRouter lists, limits and prices, including offline restoration. Pending-login construction may omit a credential only for an existing ID owned by that provider; ordinary construction still requires authorization.
- `startRpcSession()` injects a session-bound `ModelRuntime` before loading resources. OAuth refresh updates only its selected account under the file lock; a missing/deleted binding must fail closed instead of falling back to ambient or Pi-default credentials. `setRpcSessionAccount()` serializes idle switches and rebuilds wrappers; `/api/agent/[id]` waits for an in-progress switch before sending a command. No mutable process-global active account.
- `GET /api/models` bypasses the cwd-only cache for a selected account snapshot; otherwise models for the Pi default or another project's account would leak across selectors. Extra-account OAuth uses `GET /api/auth/login/[provider]?accountId=...` and API keys use `/api/auth/accounts/[id]/api-key`; provider-wide auth routes still change Pi default.
- `ProviderAccounts` sits beside the model selector as a compact current-provider indicator; its popover retains session/project selectors and account management. Both this popover and Models settings allow only HTTPS or loopback HTTP OAuth/device URLs before linking or opening them and offer a Copy button for device codes. The provider selector is locked during an in-flight login, and manual responses use that login's provider. Closing the popover retains an in-flight login; Cancel or unmount closes its EventSource.

### Model/provider searches
The shared model picker matches model names, IDs, provider IDs and qualified `provider/modelId` case-insensitively after trimming; matching never changes provider/model identity, account scope or grouping. Desktop autofocuses the filter; viewports at the existing mobile breakpoint do not. Add provider matches OAuth and API-key provider IDs as well as displayed names, while retaining existing logged-in/configured eligibility.

### Model picker and mobile keyboards

An open picker follows its trigger on window/visual-viewport resize and scroll, root height/keyboard-state writes and trigger resizing. Updates coalesce into one animation frame and clean up on close. Upward fixed panels use layout-coordinate `top` plus translation, accounting for `visualViewport.offsetTop`; a keyboard-covered Settings trigger is clamped above the keyboard. Panel height never imposes a minimum larger than the available space; upward preference can fall back below a trigger at the visible top. Filter DOM/value/focus and provider/model/account identities stay unchanged by geometry updates. The panel remains inside its existing DOM owner, not a new body portal.

`useViewportHeight` distinguishes substantial keyboard shrink from browser chrome using zoom-corrected height, and follows late WebKit/IME settling with one bounded, non-restarting reread chain. Editable activity can start a new chain; teardown cancels frames/timers/listeners and clears root state. Unscaled page-scroll correction remains unchanged. Keyboard state does not hide the composer toolbar or Stop. Browser acceptance simulates shrink/pan/no-event changes; native phone keyboards and Safari/PWA remain actual-device verification, not a Chromium claim.

### Per-model endpoint and adaptive thinking overrides

Models → a custom model → Advanced settings exposes SDK-native `baseUrl`; empty removes the override and inherits the provider endpoint. Catalog lookup uses the effective model/provider URL. A connection-test generation is invalidated by draft identity/config changes and unmount, so a late success cannot attach to a different endpoint/model.

Reasoning-capable `anthropic-messages` models offer Claude adaptive thinking through `compat.forceAdaptiveThinking`, not a new reasoning enum. The checkbox reads merged provider/model compat: disabling over an inherited true writes explicit false; restoring inheritance removes redundant overrides and preserves unrelated compat. Other APIs hide the control. `thinkingLevelMap` remains separate. Synthetic SDK 1.3 tests inspect adaptive effort versus budget payloads and stop before HTTP; connection-test success is not evidence a provider accepts adaptive thinking. Saving definitions retains existing runtime lifecycle. Existing sessions require wrapper recreation to reliably apply edited definitions; ordinary resource `/reload` alone is insufficient.

### Managed-model context budgets

Managed provider rows offer a compact context-window input in the existing global `models.json` draft (`ModelContextWindow`, `lib/model-context.ts`). The shared Save writes it; enabled-model switches remain immediate and independently scoped. Blank removes only `modelOverrides[modelId].contextWindow`, pruning empty containers while retaining sibling overrides, credentials and custom models. Overrides-only entries resolve to their managed provider rather than a duplicate custom-provider form; they wait for provider discovery before rendering.

Typed text must be a positive safe whole token count; existing positive finite numeric values accepted by the SDK (including fractional values) remain saveable. Client and server validate, preserve invalid text and refuse invalid saves without replacing the file. Placeholders describe the Pi-default runtime's resolved metadata, not necessarily another account's personalized catalog. These are global accounting budgets, not increased provider limits. Existing account scopes and read-only project-shadowed enabled-model controls remain unchanged.

New runtimes read saved definitions. Existing sessions require wrapper recreation to reliably apply them; ordinary resource Reload does not rebind model metadata. This UI adds no refresh/reselection, automatic model switching or catalog network request.

### Settings resource listing runtime

`lib/settings-listing-runtime.ts` reuses extension registrations for provider lists and enabled-model settings, not session runtimes or `/api/models` responses. Each agent-directory scope is Pi default only, explicitly excludes project resources (including `agentDir/.pi`) and shares successful construction for ten minutes, non-sliding. Every request refreshes offline and deeply clones its projection inside a generation-local queue; returned SDK objects/closures never escape. SDK 1.3 registration-triggered background refreshes are serialized through this listing instance's public `refresh` method before resource loading and drained before projection. This does not change any session/account runtime.

Enabled-model operations take detached catalog data and then create fresh cwd-specific settings. Writes execute once; invalidated reads fail rather than replaying callbacks or mutations. Credentials, models.json and the scope's models-store.json are reread on each call, not cached as listing responses. OAuth, API-key authentication and explicit network catalog refresh retain private runtimes and immutable account bindings. Selected-account `/api/models` requests still bypass its separate cwd-only response cache.

Package mutation attempts invalidate before and after effects; successful reloads and partial reload failures invalidate both listing generations and model responses. SDK package updates may affect both global and project scopes even when the request names one. A failed package effect can leave parallel writers unsettled, so that agent directory stops retaining listing runtimes until process restart; fresh construction is not proof the files have settled. Other agent directories are unaffected. Degraded builds, refresh failures and failed projections are not retained. Invalidation does not cancel old work, and replacement generations have independent queues.

Extension code updates still require explicit session Reload. Dropping this cache or expiring its TTL does not flush the SDK's single-cwd factory cache; even an empty extension load can re-key that SDK cache. Offline catalog refresh can still execute extension-provider hooks, and resource resolution retains SDK package behavior. These are not side-effect-free or live-provider performance guarantees.

### Auth and model config
- `ModelsConfig` combines models from `~/.pi/agent/models.json` with provider auth status from pi's `AuthStorage`/`ModelRegistry`.
- Provider listing is capability-driven, never id-driven: `lib/provider-listing.ts` decides membership from `auth.apiKey.login` / `auth.oauth` plus the stored credential type, so dual-auth providers (anthropic and github-copilot today — which providers declare both changes between SDK releases, so never assume it from an id) appear exactly once and never fall through both lists (#309). `lib/provider-listing-runtime.ts` adapts `ModelRuntime` to those pure helpers.
- auth.json holds **one** credential per provider and `ModelRuntime.logout()` deletes whichever it is. The delete routes therefore use `removeStoredCredentialIfType()` to compare and delete under the same file lock used by pi's auth storage. `ModelsConfig` also refreshes *both* provider lists after any auth change — refreshing one leaves a dual-auth provider rendered twice.
- OAuth/device-code/manual-code flows are streamed by `GET /api/auth/login/[provider]`; manual code responses POST back with a short-lived token stored in `globalThis.__piLoginCallbacks`.
- API-key routes store and remove keys through `AuthStorage`. Status endpoints must never return the raw key.
- The model test route is `app/api/models-config/test/route.ts`; `app/api/models/test/` is not a real route.

# Session implementation contracts

Implementation reference moved from `AGENTS.md`; repository-relative code paths remain unchanged. Read the relevant section before modifying that area. Focused user guides and ADRs linked below retain their existing scopes.

### AgentSession lifecycle (`lib/rpc-manager.ts`)
- One `AgentSessionWrapper` per session id, keyed in `globalThis.__piSessions`
- Both RPC and extension-command Reload paths invalidate settings-listing generations before execution and in `finally`, including partial failures. This does not refresh/rebind a session's ModelRuntime; edited model definitions require explicit idle model reselection.
- `globalThis` survives Next.js hot-reload; plain module-level Map does not
- Idle timeout: 10 minutes by default (`PI_WEB_IDLE_TIMEOUT_MS`, `0` disables). Concurrent `startRpcSession()` calls share a single start Promise (`globalThis.__piStartLocks`)

### Cooperative pause and explicit continuation

Activity pause state lives in private version-1 `pi-web/session-pauses.json`, bound to actual session IDs and exact generations, never copied fork/clone metadata. `session-pause-boundary.ts` chains public `agent.finishTurn` and an awaited low-level `turn_end` listener: end the complete batch, then call (but do not await) session abort inside that listener. Abort alone can attempt another request; end alone permits the SDK outer continuation loop. Pausing drains previously submitted input admissions/queues while refusing new inputs. SDK disposition, not the pre-hook streaming snapshot, determines queue versus fresh-run ownership. If a late steering admission lands after its old run became idle, its complete text/image envelope is saved as explicitly undelivered conversation context before clearing the live queue; explicit Resume processes that context rather than losing it or manufacturing an automatic model turn. Snapshot/write/clear is synchronous, and persistence failures leave Pause unconfirmed with a visible error. `session-pause-ingress.ts` adapts public SDK entry points and saves extension-triggered reports as context instead of allowing a fresh turn while paused. Arbitrary extension JavaScript is not sandboxed.

Publish Paused only after prompt/SDK/child-settlement ownership ends and the private write succeeds. Children retain ownership through cleanup and terminal-result persistence. Explicit Pause saves exact pending card payloads before cancellation; new waits are refused. No live card Promise survives restart. Main Resume is one new literal continuation prompt with cancelled-card context and child IDs/tasks/partial results; children have no browser Resume. Parent foreground results expose paused partial output; background paused-child reports never trigger a turn, including for an otherwise unpaused parent. Saved child results remain available through `get_subagent_result`; durable child pause records are also reconciled into branch-deduplicated context on the main session's next explicit ordinary prompt if an in-memory notification was lost. Explicit agent-tool resume remains a new run and fresh budget.

Resume revalidates the recorded branch ancestry and pause generation, deduplicates live submissions per session, and retains resuming records until the exact user message is persisted. Matching markers on abandoned branches do not count. Input interception/transformation refuses without discarding context; a new Pause supersedes a waiting Resume. Cold unconfirmed intent is not certified as a settled pause. Internal continuation and late request-preparation guards also prevent a Pause arriving between responses from reaching another provider call; a narrowly timed late stop may leave an explanatory cancelled/error response, never another tool batch. Superseded Resume preflight enters a cancelled run instead of throwing outside SDK 1.3's cleanup boundary, avoiding its poisoned-busy-state bug. No automatic startup continuation, tool replay, approval recovery or faithful scheduler restoration is promised. See [ADR 0028](adr/0028-cooperative-session-pause.md).

### Explicit model-definition reapplication

Selecting the current composer model again applies saved definitions only while its shared runtime family is idle. Save and resource `/reload` do not trigger this operation. `lib/session-model-refresh.ts` coordinates actual SDK public prompt/custom-user-message/compaction/bash/reload/navigation/model-set effects, background refreshes and host construction/title/auxiliary-use leases, including subagents that bypass `send()`. Idle siblings refresh their own same-provider model/scope metadata without inheriting the requester's model choice. Failed or timed-out application remains unavailable until explicit successful repair; a timeout does not certify that SDK callbacks have settled. Pending Pause is reconciled for all alive sharing wrappers after actual refresh/bind settlement, never merely after a timeout response; this emits no model turn or successful-run completion. Read-only status and Stop remain available. See [model contracts](model-internals.md) for identity, thinking and failure semantics.

### Per-message forks are non-destructive copies
`send("fork")` (before a user message) and `send("fork_branch")` (through a saved response) copy persisted history using a **separate** `SessionManager`. They work while the source is running and must never replace, navigate, abort, or shut down its wrapper. The original keeps its session ID, active leaf, queued work, event listeners, and pending extension UI; none of that live work is copied to the child. Current provider accounts and model speed are copied explicitly even when their entries lie after the fork point.

Do not call a replacement/fork API on the source's own manager or runtime: `createBranchedSession()` changes the manager's identity in-place. Clone retains its separate idle-only replacement lifecycle; in-session navigation still changes the original conversation.

### Two kinds of branching — don't confuse them
- **Fork** ("New session" on user message): creates a new independent `.jsonl` file. Shown as a child in the sidebar tree via `parentSession` header field.
- **In-session branch** ("Edit from here" / BranchNavigator): calls `navigate_tree` within the same file. Multiple entries share the same `parentId`. Switching between them calls `/api/sessions/[id]/context?leafId=`.

### Session files can be fully rewritten
`parentSession` in the header is **display metadata only** — has zero effect on chat content. Safe to `writeFileSync` the entire file (pi does this itself during migrations). Used when cascade-reparenting children on delete.

### ToolCall field normalization
Pi stores toolCall blocks as `{type:"toolCall", id, name, arguments}` but `ToolCallContent` uses `{toolCallId, toolName, input}`. `normalizeToolCalls()` in `lib/normalize.ts` handles this — called in both `session-context.ts` (history projection) and `handleAgentEvent` in `hooks/useAgentSession.ts` (streaming).

`lib/session-context.ts` owns the display-only projection of supplied entries: active-branch slicing, visible/raw paging bounds, model/thinking metadata, signatures, receipts and deferred thinking/images. `session-reader.ts` re-exports that implementation for production callers and retains SDK/file/cache/catalogue ownership. Projection never opens a session or grants branch access; routes still validate full ancestry before building a bounded page.

Argument rows are display-only projections, never replacements for these records. `rawInput !== undefined` excludes rows/file-text views even for empty or apparently complete partial JSON; authoritative `toolcall_end` removes that buffer. `getToolCallInputText()` remains the canonical full-copy/raw-view source. See [tool argument presentation](feature-internals.md#tool-argument-presentation).

### New session tool preset
Tool names are passed at session creation (`POST /api/agent/new` -> `toolNames[]`) and persisted in versioned `pi-web:tool-selection` custom entries. The latest explicit builtin pin remains session-wide across tree navigation: after successful SDK navigation, the public method adapter reapplies only those builtins while retaining the SDK-restored active extension set. RPC and extension-command ingress share that adapter inside the model-runtime effect guard. Cancelled navigation and missing/cleared pins retain native behavior; historical declarations never override the explicit builtin pin. No entry means a legacy session and keeps Pi's default behavior; an empty array means Chat only. Chat only resolves before services are created, loads no extensions/skills/prompts/themes, and replaces Pi's base prompt with the ordered contents of Pi's discovered context files. Crossing the Chat-only boundary rebuilds the wrapper; changing between nonempty presets updates it in place.

**Exact system prompts go through `before_agent_start`.** Since pi 0.86 the prompt lives in the transcript: `agent.state.systemPrompt` is a getter replayed from persisted system messages (assigning it throws), and the agent loop's request context has no `systemPrompt` field, so neither mutating the state nor patching `prepareNextTurnWithContext` reaches the model. Chat-only sessions and subagent profiles in replace mode register `lib/exact-system-prompt.ts` as an inline extension factory on the resource loader; its `before_agent_start` handler returns `{ systemPrompt }`, which the SDK projects as the provider's leading system prompt for the whole run while the transcript keeps recording Pi's structured sections. `get_state.systemPrompt` reports the exact prompt for those wrappers because the SDK state only shows the structured sections. Subagents persist their active tools plus profile-level skill and extension loading switches in `resourceSnapshot`; loaded extensions cannot expose the reserved `Agent`, `get_subagent_result`, or `steer_subagent` tools to a subagent. See `docs/adr/0002-chat-only-tool-selection.md`.

The last preset explicitly selected by the user is stored in browser `localStorage` and initializes fresh-session composers only. Existing sessions never trust that preference; they use their live `get_tools` state or pi's default when no wrapper exists.

### Managed acceptance tools

The default-off bundled Acceptance plugin uses one global user-owned switch. Ordinary coding sessions receive it through the bundled registry; extension-enabled subagents load only its explicit factory, never unrelated bundled plugins. Hidden definitions preserve permitted child selector/SDK allowlist identity while off without model exposure; enabling never widens restricted/saved child grants. Chat-only and extension-denied profiles retain their restrictions. Disabling withdraws tools, revokes pending admission/approval and durably cancels not-started queued jobs; started jobs remain independently owned with browser status/cancel/recovery available. Re-enable never replays cancelled jobs. `acceptance_run` binds the caller to its actual SDK session ID and physical own-project identity, never model-supplied caller/control identity. Admitted jobs are independent project operations, not child sessions or active session turns. Session Stop/Pause cancels pre-admission/tool waiting only; explicit acceptance cancellation remains separate and owner checked. No automatic completion turn, startup replay or restoration of saved approval occurs. [Shared project acceptance](acceptance.md) owns snapshots, scheduling, evidence, browser controls and restart recovery.

### Native session tools

[Native session tools](native-session-tools.md) owns explicit MCP/Code-mode intent, inert configured-server metadata and ordinary-session admission. Native-enabled wrappers use selected-session idle replacement on explicit HTTP Reload/Apply, not SDK in-place reload; other wrappers retain their native configuration. Setup-only selection is persisted without a message and retains its SDK ID. Fresh ordinary creation alone may snapshot a user-owned repository/worktree native-tool default; explicit selection/off wins, and existing sessions never read current defaults. Native shutdown/disposal shares a completion barrier before same-ID reuse. Child/launch defaults remain off; OAuth and configuration editing are deferred.

### Command environment ownership

Normal host Bash is a hidden, inactive-by-default replacement that sanitizes command environments while retaining explicit tool selection and user-extension ownership priority. Fresh and cold-reopened non-chat-only subagents install the same host fallback even when profile extension loading is disabled; this does not activate Bash in read-only/chat-only profiles. The managed SSH socket is inherited unchanged, while server login/control fields and host-only command variables are removed. Explicit environment isolation/overrides remain explicit; native MCP keeps its own allowlist and `inheritEnv: false`.

`bin/command-env.js` owns the narrow private-field filter for application Git/check/npm/skill/browser-opener/discovery helpers; trusted Next workers are not command consumers and keep their server environment. The active SSH plan separately tracks the approved version-pinned SDK subprocess patch. Trusted arbitrary in-process extensions still access server memory/environment; this hygiene is not an OS sandbox.

### Empty sessions and browser composer drafts

Explicit **New** (sidebar or keyboard) initializes and saves an ordinary SDK session immediately, without a prompt/model turn. Ordinary `/api/agent/new` creation flushes the SDK header and setup entries before acknowledging the real ID; subsequent SDK writes append normally. The session appears in the catalogue even with zero conversation messages and uses ordinary archive/delete controls. Startup still applies the user's saved model/account/tool/native-resource defaults. Passive project welcome/setup composers, including direct `?cwd=…` navigation, remain lazy so configuration can be chosen before startup; merely browsing a project does not create a session.

On mobile, New closes covering Activity/Starred/Git overviews and reveals chat independently of previously opening a session in that project. Desktop New retains independent sidecars and their loaded state, including Git Explorer. Explicit creation shares the existing initialization promise with Send/System, including Strict Mode replay. Promotion moves the literal unsent draft to the real ID before publishing navigation. Leaving during creation retains the outgoing draft for the eventual saved session; a late response refreshes the catalogue but cannot select itself over a newer navigation or edit the next chat's input. Creation failures keep the provisional composer and show an error, not a persistence claim. Per-tab memory saves its provisional draft identity synchronously on New. Reload before acknowledgement recovers that text in a passive setup composer without automatically retrying an uncertain creation; an original session already saved by the server remains separately available in the catalogue. This is draft recovery, not a durable/idempotent creation transaction. Startup captures the layout-hydrated tool preference rather than a stale first-render default, and an account change made during creation waits to update the saved session.

`lib/draft-store.ts` keeps text and image drafts in page memory and mirrors **text only** to per-draft versioned browser `localStorage` keys after edits. Reload/browser restart can restore literal unsent text for that session in the same browser profile/origin. Rekey, clear-on-send and rejected-submission restoration update storage too. Images remain memory-only. Storage corruption, privacy restrictions or quota failures fall back to in-page drafts; persistence is best-effort, not a server save or cross-device synchronization. Other open tabs are independent editors, not live-synchronized drafts; their last successful stored edit is what a new page can restore. Failed writes/removes cannot resurrect old stored text within the current page. Passive welcome drafts keep their existing project parking lifecycle.

Guided-review batches use the existing selected chat only. FileWorkspace scopes
its optional handoff callback to the visible active view; AppShell validates the
preview's captured destination against its latest selected session and mounted
composer. `insertText(text, {atEnd:true})` appends the exact delimited batch without
replacing a cursor selection or changing attachments. It rejects an absent textarea.
Other insertion callers retain their cursor semantics. Preparing/drafting does not
create a session, start an agent, submit text or approve tests/fixes/Git. Normal Send
is a second action; the notebook persists Prepared/Drafted, not a sent receipt.

### Fresh composer and quote focus

Explicit New actions request desktop composer focus once after the intended fresh draft mounts, with the caret after any restored draft. The request is bound to draft identity and navigation revision; mobile, visible modal/native dialogs, inline card/quote/picker ownership, subsequent pointer/key interaction and intervening control focus take priority. Covered/inert, hidden, disabled and composing textareas refuse the request. Ordinary mounting, session selection, polling and streaming never request this autofocus. The imperative focus handle changes only DOM focus/selection, not draft text or session configuration.

Ask here leaves selection/focus to the existing insertion path and never clears document ranges afterwards. Insertion retains the surrounding draft and puts the caret after the inserted quote, not after a retained suffix. Ask in new chat retains its distinct source-entry-ID and immediate-send lifecycle.

### Context-file change notice
A live ordinary session retains the context files (`AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`) loaded at startup or last session reload. `get_state` compares that snapshot to the SDK's read-only `loadProjectContextFiles()` discovery, so new, edited, removed, and newly overriding files offer a **Reload session** button in the selected chat. The browser polls while visible and checks on visibility return; it does not reload resources automatically or create a wrapper just to check. Chat-only sessions also load context files; subagents with context loading disabled do not show the notice. Other resources (skills, extensions, prompts, themes) are not monitored by this notice.

### Streaming display and client payloads

`lib/streaming-message.ts` retains the single reducer but publishes through a session-hook-owned `StreamingStore`, outside parent React state. `useStreamingSelector` uses batched state subscriptions and repairs the render/subscription gap in a layout effect. ChatWindow subscribes only to streaming/content booleans; its memoized `StreamingReply` owns chunk-level message updates and post-commit tail following. Minimap measurements read a stable getter. Composer/minimap memoization does not promise to eliminate tool-progress renders while other props change. Transcript/entry-ID commits, run guards, receipts and blocking cards retain their original lifecycle.

Sending an ordinary prompt attaches the chat to the real content tail, without scrolling the prompt to the top or adding a viewport-sized spacer. Committed streaming chunks and transcript updates follow the bottom only while attached. Scrolling upward detaches; scrolling back near the live tail or choosing **Scroll to latest** reattaches. Explicit history, minimap and restored-position navigation retain their own viewport ownership.

Markdown fences and Mermaid Source share the existing PrismLight renderer. Grammars load after mount on the first non-plain code consumer, including live code preloading; no live code is tokenized. Completed fences initially render plain through the same line-numbered highlighter, then receive one client-effect/idle grant per slice (50ms timer fallback, 500ms idle timeout). Recent fences are favored, with the oldest waiter receiving every fourth grant. Code/language/eligibility identity rejects stale grants; unmount removes callbacks and cancels an unused idle handle. Selection-blocked work requeues after selection clears rather than publishing a batch. The queue retains only mounted-consumer callbacks, not code/token trees. SSR starts no timers and always renders plain, even if another server render loaded grammars. This defers work; it does not split one tokenization, introduce a worker or establish a measured speedup.

Expanded thinking uses newline-aware 8,000-character pieces, hard-cut at about 16,000 without splitting surrogate pairs or losing blank lines. Ordinary answer copying is unchanged; native selection across hard-cut block boundaries may introduce line breaks. Stored/provider thinking is not rewritten. Individual pieces are not memoized, avoiding retained old sliced-string props. This bounds layout text nodes, not total loaded thinking or a measured RSS/time speedup.

`lib/message-signatures.ts` removes only block-level `thinkingSignature`, `textSignature` and `thoughtSignature` from copy-on-write assistant display projections: history, navigation trees, SSE start/end/toolcall-end and reconnect snapshots. Tool arguments and user/custom data are not recursively filtered. Original SDK/provider state and persisted replay entries remain unchanged.

### SSE reconnect on page refresh mid-stream
On `ChatWindow` mount, the initial history load also reads `GET /api/sessions/[id]/state`. The selected session maintains SSE automatically; live `thinkingLevel`, streaming and `isCompacting` state are restored from this response. Periodic recovery uses `GET /api/agent/[id]`.

Each agent SSE connection uses byte-based backpressure: beyond 512 KiB queued it drops only repairable message deltas and partial tool updates, never block starts/ends or control/receipt events. Authoritative end events repair the streamed content. `PI_WEB_SSE_BACKLOG_LIMIT_BYTES` selects the disconnect threshold (default 16 MiB; finite values at least 64 KiB). This is a backlog threshold, not a maximum frame size: an incoming frame may overshoot it, and the next non-droppable enqueue (including a heartbeat) errors the stream and releases its listener/liveness lease. Reconnection uses the existing snapshot/history/state reconciliation; it is not proof of instantaneous complete recovery. The pre-encoding check does not bound serialization or a single frame allocation.

### Compaction SSE events
Newer pi emits `compaction_start` / `compaction_end`; older versions emitted `auto_compaction_start` / `auto_compaction_end`. `handleAgentEvent` accepts both sets to keep `isCompacting` in sync. Manual compact is a blocking POST; both the toolbar and `/compact` show progress immediately, with SSE and authoritative state tracking the active phase.

While `isCompacting` is true, the composer shows an accessible, indeterminate **Compacting conversation…** status above the input, outside mobile More controls and independent of whether a prompt is streaming. It explains that earlier messages are being summarized, without inventing percentage/ETA. Previous success/error banners are hidden during a new compaction. Start/end events cover automatic, manual, cancelled and failed runs; initial GET state restores an in-progress compaction after reload. Recovery polling and visibility/network-return checks also run for compaction-only activity, so a missed end event or destroyed wrapper clears the status without manufacturing a completed prompt. The live region is not deferred behind a busy composer, including during `/compact`. Compaction-local read versions and phase generations supplement session/prompt guards: late initial or recovery snapshots cannot clear/resurrect a newer phase, and an older manual POST cannot hide a later SSE compaction. Recovery teardown invalidates pending reads. The indicator is UI state, never a persisted/model-context message.

### Transcript system messages, usage entries and context edits (pi >= 0.86)
- Every new session's first request persists a `message` entry with `role: "system"` holding the prompt sections and tool declarations; later prompt or tool changes append more. The agent loop announces them with `message_start` / `message_end` like any message. They are provider input, never conversation: `toClientAgentEvent()` drops them before the SSE stream (they carry every tool schema), `handleAgentEvent` skips any that slip through, `entryToUiMessage()` returns null for them, and `BranchNavigator` / `lib/project-tree.ts` never label or preview a branch with one. They still count toward `messageCount` and `totalMessages`, exactly as the SDK counts them.
- `usage` entries (`kind: "cache_warm"`) record prompt-cache warming that is billed but never enters model context. `computeSessionStats()` adds them like compaction usage so the token/cost counters match `/session` in the TUI.
- `context_edit` entries omit or replace an earlier entry's model context without changing raw history; the UI ignores them. A retain-none compaction stores its own id in `firstKeptEntryId`.
- `SessionManager.listAll()` now reads files newest-mtime first (then reverse filename) so `--resume` can render progressively; its stable sort keeps that order for sessions with equal activity time, and `listSessionsIncremental()` reproduces it from the stat fingerprints it already keeps.

### Incremental session-list scanning

`lib/session-list-scanner.ts` caches unchanged metadata and resumes growing files from a persisted LF-byte checkpoint. Before resuming it validates device/inode identity, the header and up to 512 bytes before the checkpoint. Full and tail reads share one accumulator: title changes/clears, all message counts (including system/tool messages), first user text, maximum user/assistant activity, newest valid archive marker (including restore), and first session-ID-validated spawn marker. The private atomic index is disposable version-2 metadata; old/corrupt indexes rebuild without modifying transcripts.

Detailed scans use one descriptor, bounded to its initial size. Changed identity/stat after reading prevents caching that result; the next listing rebuilds. Catalogue index owners are serialized across summary/detail and generation-invalidated scans. This is not a transactional snapshot against external writers. Truncation, non-growing edits and failed samples fall back to full reads. Sampling cannot detect same-inode historical edits outside the header/sample followed by growth; stale list metadata can persist until a non-growing change or failed validation forces rebuilding. It is not authorization or an integrity guarantee.

Incomplete trailing records are reread from their start. A parsed unterminated record counts immediately but disables resumption until a full scan, avoiding double-counting when its newline arrives. Byte buffering preserves UTF-8 across chunks and raw U+2028/U+2029 within JSON strings, matching the SDK file loader rather than Node 24 readline's separator behavior. CRLF/lone-CR parsing is retained. Oversized or non-first-line headers scan normally but do not create checkpoints.

Unchanged summaries reuse complete cached rows. Cold/changed summaries still read header/stat **and the whole transcript for archive markers**, so archived sessions never briefly appear active; they do not overwrite complete accumulators with pending rows. This port does not optimize cold archive discovery or make the separate summary header/archive reads transactional against external replacement. Index writes coalesce over a five-second window, capturing their destination and snapshot. The unreferenced timer never keeps a process alive; a lost save merely costs a rescan after restart. Catalogue enumeration/stat and project attachment still run outside the append-tail saving.

Relation projection now reuses a process-only reader WeakMap keyed by the exact
scanned row and an immutable scanner-validated physical/stat fingerprint. Only
compact subagent parent/profile/description/status (or stable absence) is retained,
never transcript entries, tasks, results or resources. The private index stays
version 2 and persists no relation cache. Restored entries become eligible only
after this process validates their stats. Changed summaries revoke the previous
complete row's eligibility even though its accumulator remains available; missing,
unstable, reset and switched-agent-root rows cannot certify reuse.

Warm relation hits add no content reads or per-file stats beyond the scanner's
existing stat boundary. Misses keep the original first-two-physical-lines/256-KiB
prefix and conditional 256-KiB tail visibility and `readSubagentRun` semantics,
using one nonblocking regular-file descriptor. Initial/final descriptor stats,
pathname identity and current scanner eligibility must agree before memoization;
read/validation failures never become cached negatives. Header-parent IDs are
resolved anew against each catalogue, and returned relation objects cannot mutate
the private cache. This remains best-effort display metadata: a write after the
scanner's stat observation can wait until the next rebuild, not a transactional
snapshot, authorization or integrity proof. First reads after restart and changed
files still perform bounded relation parsing.

`useSessionCatalogue` gives each Sidebar one `SessionCatalogueLoader`: one active
HTTP/body workflow, merged pending demand and separate caller waiters. A successful
nonempty summary with no `detailsPending` rows skips forced initial hydration;
pending, empty or failed summaries retain the one-shot 750ms fallback unless a
real detail demand claims it. Strict Effects replays observation, not bootstrap.

Version observations can join a covering summary; unmatched observations receive
one post-observation attempt. Tokens are opaque (including resets), not numerically
ordered, and mismatch never starts an equality-retry loop. Notifications retain
forced refresh semantics. Explicit mutation requests advance publication epochs
immediately; stale bodies/errors/finally drain without overriding optimistic state.
A qualifying newer follow-up can settle earlier mutation callers successfully.
Forced demand cannot settle from ordinary work. Serial refreshes can wait behind a
slow older body; this adds no abort policy, timeout or polling-cadence change.

Release immediately gates admission/publication and cancels hydration. Synchronous
Strict replay retains the instance; terminal disposal joins admitted bodies through
the existing navigation-work observer. Current callback/controller ports are used
at publication. Activity receipt, suppression and completion-tone authority remain
unchanged. Coordination itself does not project payloads or imply a production
latency guarantee.

### Lossless catalogue transport

Browser catalogue reads opt into `GET /api/sessions?compact=1`, also with summary
or force. The outer reply/version/running/suppression metadata is unchanged; only
`sessions` may become `{format: 1, strings, rows}` instead of an array. The stateless
`lib/session-catalogue-wire.ts` codec shares repeated first messages, names,
directory/project identities, branches and subagent descriptions/profiles through
response-local numeric references in those fixed slots. IDs, file paths, dates,
counts, flags and relation discriminants retain their normal representation.
Conservative JSON UTF-8 savings include the table, envelope and actual index digit
widths; unprofitable/unique catalogues stay arrays. This is not a persistent index,
a cross-request dictionary, a new metadata authority or additional content I/O.

`readSessionCatalogueReply` completely decodes at the Sidebar, remembered-workspace
restore and selected-session hydration HTTP boundaries, before any controller,
state or selected-row merge. Unknown formats, non-string tables, malformed transport
structure/selected slots or invalid references fail the existing read/error path,
never partial publication. There is no codec-specific retry; a failed startup
summary still permits the existing 750ms hydration fallback. This is not complete
SessionInfo schema validation. Legacy arrays remain accepted, and default API reads, detail/context and
server search keep their existing full-data contracts. Row/relation copies isolate
decoded models from encoded transport objects. Existing lifecycle/epoch/navigation
guards and request cadence remain unchanged.

No first message, name or task description is truncated. Agents searches the full
raw first message even when a title hides it; Activity/Agents/search retain full
labels/tooltips, and Sidebar/mobile still collapse complete skill envelopes before
their 50-unit fallback. Clone/prompt/history data is untouched. Unique text can
still dominate a response; sharing does not bound decoded memory. JSON byte savings
are not a promise of gzip-transfer or deployed latency improvement: compare those
separately after an authorized rebuild/measurement. [Production performance](production-performance.md)
owns recorded empirical findings and the deferred production/SPA measurement
follow-ups; the executed implementation plan is archived.

### Running state polling + reconciliation
- The sidebar polls `/api/agent/running` every 2.5 seconds while the tab is visible and pauses polling in background tabs. The session-list response remains the initial fallback.
- `invalidateSessionListCache()` bumps the generation but **keeps** the previous scan, and the cache is fresh only while its recorded generation matches. Ordinary agent activity invalidates it frequently. Rebuilds still enumerate/stat the catalogue, attach project state and read changed relations; unchanged relation metadata is reused under scanner-validated fingerprints. Callers that only need metadata — mapping search hits to sidebar rows — pass `listAllSessions({ allowStale: true })` to read the previous scan and let the rebuild happen in the background. A stale scan is a complete catalogue apart from sessions created seconds ago, so those callers accept a brief window where a brand-new session is not yet listed.
- `useAgentSession` treats per-session SSE as primary for chat events and opens it before each prompt. `prompt_done` completes the current UI stage and notification immediately, but the idle SSE stays open for a 30-second grace window and is reused by the next prompt. `agent_start` cancels that close timer; `agent_settled` finishes extension-injected runs that have no wrapper-level `prompt_done` and starts a fresh grace window. Do not close on the first `agent_end`: retries, compaction, and extension-queued messages can continue the same logical prompt.
- While a run is active, `useAgentSession` periodically calls `GET /api/agent/[id]` and also reconciles on `visibilitychange`/`online`. This fixes missed terminal events from background tabs or half-open connections.
- Prompt runs use a monotonic run id; late SSE or slow reconciliation responses from an old run must be ignored so they cannot resurrect stale streaming bubbles.
- Every SSE (re)connection in `useAgentSession` is gated on `sessionHookMountedRef`. React Strict Mode (on by default in `next dev`) re-runs effects in declaration order after a simulated unmount: the mount-only effect's cleanup sets that ref to `false`, and it is only restored when that effect re-runs, *after* the warm-session effect. The warm-session effect therefore re-asserts the ref before `maintainEventsConnected()`. Without it a dev-server tab never opened the event stream on mount or when switching back to a running session, so streamed output and new messages stayed invisible until the 15-second reconcile poll or a page refresh (`next start` was unaffected).

### Agent switcher recorded usage
- Opening Agents reads `POST /api/sessions/stats` with only 1–200 session IDs. The guarded, no-store endpoint reads an existing alive wrapper's manager or a genuinely non-writing disk snapshot; it never starts, renews, evicts or sends commands to wrappers. SDK parsing/legacy normalization runs only in memory, never through persistent `SessionManager.open()` (which can migrate/repair files). Disk reads require a regular, nonempty file with a matching saved header, at most 256 MiB, and a stable physical/stat fingerprint; missing, malformed, changing or oversized files remain unavailable. Only 64 fingerprint-keyed disk summaries are retained, never transcripts. Live-manager summaries reuse unchanged entry-count/latest-entry keys. Each ID fails independently: an omitted result means unavailable, not a zero estimate or proof of deletion.
- The mounted panel's single-flight coordinator deduplicates the full root/nested-subagent family and reads sequential chunks of at most 200 IDs. It refreshes on open, membership/running transitions (including final stop), and visibility return even when idle. Completion-scheduled three-second polling runs only while visible and a family member runs. Hiding/closing or superseding membership invalidates/aborts reads; a pending refresh waits for the previous flight to settle, and late generations cannot publish. No family-wide SSE subscriptions or startup reads are introduced.
- Compact metrics include recorded zero and cost/tool-only summaries. Successful omission clears an older value; failed requests retain it as explicitly stale. Family totals include retained stale values with a stale count, exclude unavailable values, and show available/expected coverage with **Partial** when incomplete. Initial reads show loading, never fabricated zeros. The sum is over the full listed family, independent of switcher search; forks remain independent families.
- **Summed estimated active time** adds existing all-entry timing estimates, including parallel overlap; it is not elapsed family time. Tokens/cost include compacted history, executed branches and recorded cache-warming usage; missing historical usage may be zero. Recorded cost is not an invoice. Family and selected-agent native disclosure breakdowns are outside option buttons and the listbox, available to keyboard and touch rather than hover only. The toolbar and Session info remain selected-session-only. Viewing/selecting/expanding usage never acknowledges Activity review.
- The Agents badge reuses the sidebar's running-ID snapshot: running subagent count while nonzero, otherwise total descendants. Main-session activity, queue IDs and persisted status do not prove a running subagent. Its accessible name reports the count; the decorative ring is static under reduced motion. No additional running poll is added.

### Receipt reconciliation after canonical advancement
- Live receipt verification binds the displayed ancestor to the exact receipt leaf. If a concurrent canonical read changes that ancestor, the retry reads the current canonical branch without retaining the captured receipt leaf: the new ancestor may already be a descendant of that receipt. Only receipts returned by the revalidated branch are merged; the captured entry is not blindly appended. Session, navigation-revision and live-view guards still discard stale responses, and ordinary messages remain on their SSE delivery path.

### Receipt reconnects after archive/restore
- Archive/restore can append a saved marker while an idle startup is still opening the previous file, before its wrapper is registered. An anchored context read whose ancestor is absent from that wrapper probes `evictIfDiskAhead()` and reopens disk only if the idle index is provably behind. It then revalidates the full ancestry as usual. Ordinary reads and known sibling anchors do not probe; running wrappers are never evicted, and unknown or sibling ancestry still returns `409`.

### Moving sessions between projects
- The row's **Move to project…** action proposes a project and registered worktree/directory, or another existing directory through Browse, without changing the sidebar checkout. The route accepts distinct registered checkout roots within the same repository, but refuses the exact current directory, same-repository subdirectories and running families. A move changes the header cwd and the SDK session-file directory for the selected session and its nested subagents; forks stay in place, but any stored parent path pointing at a moved file is repaired (including subagent metadata).
- Single and bulk move dialogs preselect the current project and worktree/directory for orientation, without proposing a no-op move. An explicit destination choice is required before Move is enabled; bulk selections may target the current checkout to consolidate other worktrees, with already-at-destination families excluded by preview. Opening historical sessions whose source directory was renamed/deleted retains those labels without implicitly requesting a working checkout listing for that missing source. Same-project destinations remain available. A confirmed move of the open chat retargets the replacement composer and Files context to the confirmed destination, rather than recreating them in a vanished source directory. The dialogs show an accessible indeterminate spinner/status while pending (including bulk result refresh). Bulk progress counts acknowledged families/sessions, never an estimated percentage or ETA. Controls stay disabled until settlement; reduced motion keeps the indicator static.
- A missing source cwd does not prevent relocation: persisted history is outside the checkout. The route waives only source-root/registration checks for `ENOENT`, including removed/prunable worktrees; known same-repository destinations still require a registered checkout root. It does not recreate the old directory, and running/queued-family restrictions remain unchanged.
- `/api/sessions/worktrees` supplies history-only directory inventory, including session-referenced missing paths. The Sidebar's worktree filter is independent from the effective cwd, applies to search, and resets bulk selection. Filtered child-only matches remain visible using full-catalogue ancestry; missing paths are never admitted as working directories.
- `/api/sessions/move` previews and executes explicitly reviewed batches through the same family mover. Recovery selects all persisted missing-cwd roots/subtrees in the project, including archived sessions, and requires a verified primary checkout. Missing means `ENOENT`, not an omitted registration or inaccessible directory. Expanded membership and missing eligibility are rechecked before mutation; serialized plans are not admission authority. The preview binds a maximum-4096-ID write footprint including incoming references; execution refuses newly introduced linked sessions outside it, so splitting requests cannot reset the aggregate affected-session limit. A request executes at most five reviewed roots and yields unattempted roots after a cooperative ten-second between-family budget. The client sends bounded requests sequentially with original bindings, validating every attempted/pending partition before admitting another request. Batches are partial, not durable transactions or whole-project migration. Any lost, malformed or non-JSON acknowledgement stops new execution and permits only `mode: "reconcile"`: current family locations are read after the entire dispatched batch settles under the same mover lock, with original source or independently admitted destination authorization, without starting/evicting wrappers or modifying transcripts (normal catalogue-index caching may still persist metadata). Duplicate persisted identities remain unknown before live supplements are merged. Uncertain dispatched chats are invalidated separately from moved-result counts, even if location observation fails: they retain a history-only view until canonical metadata or explicit reselection rebinds them, rather than creating a working composer at an unconfirmed source/destination. Settlement callbacks resolve against the current selected session, not the source row captured before dispatch: canonical relocation metadata must not be overwritten by a late uncertain response, and settlement for an older session must not clear a newer selection. Observations distinguish destination/source/changed/unknown, never certify execution, and never automatically retry writes. One indivisible family or lock wait can still outlive a proxy timeout; failed reconciliation remains unknown.
- `lib/session-move.ts` stages all rewrites, backs up originals for rollback, installs destination files without overwriting an existing file, evicts idle wrappers, and refreshes both session-path and list caches. Never only change the header or only rename the JSONL: Pi's session discovery and parent references must stay consistent. Other Pi processes writing concurrently are not coordinated with this operation.

### Agent-created ordinary sessions
- The bundled Session Launch plugin exposes `start_session` only to ordinary coding sessions. It creates an independent wrapper through the host's ordinary startup/prompt admission, never forks/replaces the creator or borrows subagent lifecycle.
- Defaults copy current model/account, thinking, speed and built-in tool selection; explicit changes are exact proposals. Initial prompts are literal, and final SDK preflight revalidates effective text/configuration and policy before dispatch. Creator cancellation only owns pre-acceptance work.
- A host-only, single-use symbol capability is installed in the fresh wrapper constructor before registry publication. Pending ownership participates in `isRunning()` and excludes ordinary mutation, including tools/account replacement; status and extension UI responses remain permitted. Binding/admission awaits race permanent refusal and recheck ownership/liveness. Successful final admission synchronously releases exclusivity, restoring ordinary queueing and child independence.
- SDK 1.4.0 still can leave its busy flag/abort wait poisoned when final `preflightResult("started")` throws after awaited `before_agent_start`. Keep that final guard and its original exception: `refuseInitialPrompt(owner, error)` latches failure only for the matching pending launch, rejects acknowledgement/setup races, settles wrapper prompt bookkeeping once, and synchronously marks the wrapper unavailable. Late callbacks still throw; no run journal, `prompt_done`, or completion notification is created. Ordinary unguarded SDK/auth rejection does not retire its wrapper.
- Owned refusal alone bounds extension shutdown by `INITIAL_PROMPT_SHUTDOWN_GRACE_MS` (1000ms), then calls public `inner.dispose()` exactly once on success/error/expiry, without SDK abort/waitForIdle or private-state mutation. Timeout/disposal errors are logged separately from refusal. Identity-checked registry removal cannot unregister a replacement. `globalThis.__piOwnedRetirements` publishes a completion barrier by canonical persisted SDK ID before retirement callbacks; persisted-file startup and start locks resolve that ID rather than URL aliases, and wait before SDK resource construction. Successful public disposal releases the barrier; disposal failure remains a fail-closed tombstone across module/HMR reload. This prevents delayed old disposal from cleaning a replacement's SDK-ID resources (such as Codex WebSockets); independent IDs do not wait. Pending-owned `destroy()`/`shutdown()` immediately refuse outstanding admission and use this bounded path, even during binding or preflight. Ordinary/accepted wrapper `destroy()`/`shutdown()` retain their existing lifecycle. Disposal is invalidation, not proof arbitrary extension code/processes settled; retained files may be explicitly reopened, but refused initial prompts are never auto-replayed.
- `pi-web:session-spawn` stores stable created/creator/operation IDs outside model context. The created-ID check prevents attribution on copied fork/clone history. It remains a top-level ordinary session with receipt/header links, not a family parent.
- See [Session Launch](session-launch.md) for permissions, feedback, persistence and verification.

### Built-in subagents
- The global `builtInEnabled` switch is persisted in `~/.pi/agent/agents/settings.json` and defaults to `false` when the file or field is absent. Malformed settings fail closed; atomic updates preserve unknown fields.
- The inline built-in extension factory is always present so reloading an existing wrapper can apply setting changes, but it registers no tools while disabled. After changing the switch, the user must explicitly reload the current session.
- When enabled, only a recognized legacy `pi-subagents` extension that registers any reserved tool (`Agent`, `get_subagent_result`, or `steer_subagent`) is removed. Unrelated extensions remain loaded, and resolved conflict diagnostics are discarded.
- Runtime `Agent` dispatch checks the setting again so a stale tool call cannot start a subagent after the feature is switched off.
- See `docs/adr/0003-built-in-subagent-toggle.md` for the precedence and persistence rationale.
- Individual built-in profiles (`general-purpose`, `explore`, `plan`) are switched off by name in the same file's `disabledBuiltIns` array, never by copying them out to a `.md` file: a copy freezes the built-in prompt at the version it was copied from and is visible to the other runtimes reading those directories. `builtInProfiles()` stamps `enabled` onto the constants so the panel, the `Agent` tool description, and `resolveSubagentProfile` agree; each write is a minimal edit that preserves names it did not touch, including ones no built-in claims (a newer build's). Reading the list fails *open* — the feature switch beside it has already failed closed — while `PATCH /api/subagents/profiles` with `scope: "builtin"` performs the write and `PUT`/`DELETE` still refuse that scope. A same-name file replaces the built-in outright and is switched off through its own frontmatter. Only the switch is live for a built-in; the rest of the form stays read-only. See `docs/adr/0005-built-in-subagent-disable.md`.
- A background run's completion notification (`notifyParent`) is skipped when the parent already collected the same result with `get_subagent_result`: the tool marks a finished background run consumed and the notification takes that mark. The check cannot happen only when the completion promise resolves — the parent is usually still inside its `get_subagent_result` poll at that moment (500ms interval) and `deliverAs: "followUp"` would just queue the duplicate until that turn ends. So `notifyParent` holds the message while the parent `isRunning()` and re-checks the mark before sending; an idle parent is still notified immediately.
- Agent profile files (`~/.pi/agent/agents/*.md`, project `.pi/agents/*.md`) are shared with other runtimes, so a save round-trips the frontmatter keys this app does not own (`name`, `allowed_subagents`, `exclude_extensions`, `disallowed_tools`, …) and carries foreign `ext:` tool selectors through. Managed keys are exactly `description`, `display_name`, `tools`, `load_skills`, `load_extensions`, `enabled`, `inherit_context`, `run_in_background`, `model`, `thinking`, `max_turns`.
- A background run's completion reaches the parent through `sendCustomMessage`, and pi's `convertToLlm` replays every `custom` message to the model as a plain `user` turn. `subagentNotificationText()` therefore prefixes the report with `SUBAGENT_NOTIFICATION_PREFIX` so a compaction pass — whose prompt asks what *the user* wants — does not file the subagent's output under Goal / Constraints (#875). Foreground `Agent` and `get_subagent_result` results keep the bare `subagentFinalText()`: they are already `toolResult` messages and need no marker. Keep the prefix in code, not in a profile prompt, so the model cannot drop it.
- The `skills` / `extensions` spellings pi-subagents reads are seeded on first save and kept in step while they are booleans; a hand-authored whitelist such as `extensions: pi-advisor-flow` is never rewritten, and the two flags fall back to those aliases when `load_skills` / `load_extensions` are absent.

### Subagent lifecycle, model references and budgets

A child is written to its private SDK session file before wrapper publication/queue dispatch, including setup/resource/account/speed entries but no fabricated conversation. SDK 1.3 otherwise leaves setup-only sessions unflushed. Every new execution, including resume, has an explicit `runId` in version-1 status/result metadata; session IDs remain unchanged. The latest lifecycle entry also carries that run's task, description, parent tool call, background mode and start time. Result consumption keys the exact run, so collecting an older result cannot swallow a resumed completion (even at the same timestamp); legacy results fall back to completion time. Resumed background reports keep the non-user prefix and explicitly supersede earlier reports. No subagent identity is a recovery-journal run ID.

Lookup prioritizes live controller ownership, then wrappers, then files. A persisted queued/running entry with no live execution or busy wrapper projects as interrupted, without writing a synthetic terminal result. Live queued results are nonterminal and `wait` polls them. Deleted files have no settled-memory fallback. Resume retains saved resources/model/thinking/accounts/speed; meaningful creation options are refused, not silently ignored (empty strings/lists and zero `max_turns` remain compatible). An explicit inheritance boolean is a creation option. Missing/inaccessible/non-directory working folders cannot be substituted or recreated; cold resume checks the folder before loading resources, and execution rechecks after queueing. These checks do not lock out external filesystem writers.

`Agent.model` and profile models accept a valid trailing `:<thinking level>`, but a whole registered ID always wins, including literal `:high` IDs. Selection remains exact and ambiguous bare IDs reject; do not use the SDK CLI resolver's fuzzy/auth-sensitive/unknown-ID fallbacks. Thinking precedence is explicit call thinking, call model suffix, profile thinking, selected profile-model suffix, parent thinking; the SDK clamps capabilities. Settings displays the base model while preserving the authored reference. Fresh-call thinking/turn/inheritance overrides remain supported.

Attached UTF-8 input files remain physically contained in the parent's cwd, deduplicated and limited to eight requests. Before creating a worktree or child manager, their allowance is `min(512 KiB, floor(child contextWindow * 4 / 10))`, using a nonthrowing lookup of the call/profile/parent model. Unknown/nonfinite/nonpositive windows retain the absolute cap. After trusted child services discover providers/refresh models offline, the same loaded byte snapshot is checked again before creating the child manager. A late refusal may need safe non-force worktree rollback. File bytes (including a stripped UTF-8 BOM) are not a whole-prompt token guarantee: task, wrappers, system/tools/skills, the separately truncated inherited context and output reserve remain additional. Early lookup never grants trust, creates an ambient account runtime or calls a provider.

New children persist the resolved turn limit (`0` explicitly unlimited). Each explicit resume gets a fresh saved budget; legacy children without the field retain unlimited resumes. The limiter chains the SDK's awaited `agent.finishTurn`, preserves natural final answers/finalized terminating tool batches, and grants unfinished work one wrap-up turn. That turn drains steering together; exhaustion clears/reports undelivered queues, refuses further controller steering, and fails with partial output. Hooks/listeners/steering mode are restored. Provider errors, parent cancellation and a child's own Stop remain distinct outcomes. Persistence is not prompt acceptance: do not manufacture recovery journals, Activity completions or interaction receipts for never-accepted work.

All terminal paths share result recording after safe worktree cleanup. Optional `worktreeExists` records settlement-time existence, not today's filesystem; unknown/inaccessible paths and legacy entries make no observation. Model-facing content states the recorded path/branch/retention reason without forwarding Git's force-delete advice or claiming cleanup verified current branch existence. Resume clears old cleanup observations and never removes a retained checkout. Result-write failure retains an inspectable failed live record rather than falsely claiming durable success. Native Git creation/removal, explicit project trust and dirty-work retention remain unchanged.

### Subagent extension selectors and default tools

`ext:` names resolve against loaded filename/parent/package aliases, including scoped and pinned npm sources. Extension names are case-insensitive; tool suffixes remain exact-case. Resolve the longest name before rejecting ambiguous grants; denials resolve across all claimants, so an ambiguous alias can narrow `ext:*` but never grant unrelated tools. Trailing `/` and `/*` mean the whole extension. Preserve authored grants and denials until spawn-time resolution, including deny-only and fully-denied profiles; do not turn an emptied allowlist into the legacy all-extension fallback. Saving preserves uppercase selectors and distinct tool suffixes such as `Search`/`search`.

Extension additions cannot reintroduce built-in profile-denied names (including PowerShell before shell mapping) or reserved subagent control tools. These name-selection rules do not sandbox extension code or uninstall replacement implementations. Ordinary-session sanitized Bash remains registered with `defaultActive: false`, so native `defaultTools`, explicit presets and reload—not extension registration—own activation. Native SDK regressions cover Bash-free startup/reload and explicit positive controls.

## Pi Session File Format

Location: `~/.pi/agent/sessions/<encoded-cwd>/<timestamp>_<uuid>.jsonl`

```jsonl
{"type":"session","version":3,"id":"<uuid>","timestamp":"...","cwd":"/path","parentSession":"/abs/path/to/parent.jsonl"}
{"type":"model_change","id":"<8hex>","parentId":null,"provider":"zenmux","modelId":"claude-sonnet-4-6","timestamp":"..."}
{"type":"message","id":"<8hex>","parentId":"<8hex>","message":{"role":"user","content":"..."}}
{"type":"message","id":"<8hex>","parentId":"<8hex>","message":{"role":"assistant","content":[...],...}}
{"type":"message","id":"<8hex>","parentId":"<8hex>","message":{"role":"toolResult","toolCallId":"...","content":[...]}}
{"type":"compaction","id":"<8hex>","parentId":"<8hex>","summary":"...","firstKeptEntryId":"<8hex>","tokensBefore":N}
{"type":"session_info","id":"...","parentId":"...","name":"user-defined name"}
```

`entryIds[]` in `SessionContext` is a parallel array to `messages[]` — maps each displayed message back to its `.jsonl` entry id, used for fork and navigate_tree calls. Live ordinary `message_end` events carry that ID too: the wrapper defers delivery one microtask because the SDK synchronously appends after notifying its public listeners, and attaches an ID only when the saved leaf holds the exact message object. The hook commits content and IDs atomically, including when an unchanged optimistic prompt is consumed. Unsaved or unmatched messages retain an empty ID, never a guessed navigation target; newly saved prompts can fork while the source keeps running without a reload.

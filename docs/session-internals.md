# Session implementation contracts

Implementation reference moved from `AGENTS.md`; repository-relative code paths remain unchanged. Read the relevant section before modifying that area. Focused user guides and ADRs linked below retain their existing scopes.

### AgentSession lifecycle (`lib/rpc-manager.ts`)
- One `AgentSessionWrapper` per session id, keyed in `globalThis.__piSessions`
- `globalThis` survives Next.js hot-reload; plain module-level Map does not
- Idle timeout: 10 minutes by default (`PI_WEB_IDLE_TIMEOUT_MS`, `0` disables). Concurrent `startRpcSession()` calls share a single start Promise (`globalThis.__piStartLocks`)

### Per-message forks are non-destructive copies
`send("fork")` (before a user message) and `send("fork_branch")` (through a saved response) copy persisted history using a **separate** `SessionManager`. They work while the source is running and must never replace, navigate, abort, or shut down its wrapper. The original keeps its session ID, active leaf, queued work, event listeners, and pending extension UI; none of that live work is copied to the child. Current provider accounts and model speed are copied explicitly even when their entries lie after the fork point.

Do not call a replacement/fork API on the source's own manager or runtime: `createBranchedSession()` changes the manager's identity in-place. Clone retains its separate idle-only replacement lifecycle; in-session navigation still changes the original conversation.

### Two kinds of branching — don't confuse them
- **Fork** ("New session" on user message): creates a new independent `.jsonl` file. Shown as a child in the sidebar tree via `parentSession` header field.
- **In-session branch** ("Edit from here" / BranchNavigator): calls `navigate_tree` within the same file. Multiple entries share the same `parentId`. Switching between them calls `/api/sessions/[id]/context?leafId=`.

### Session files can be fully rewritten
`parentSession` in the header is **display metadata only** — has zero effect on chat content. Safe to `writeFileSync` the entire file (pi does this itself during migrations). Used when cascade-reparenting children on delete.

### ToolCall field normalization
Pi stores toolCall blocks as `{type:"toolCall", id, name, arguments}` but `ToolCallContent` uses `{toolCallId, toolName, input}`. `normalizeToolCalls()` in `lib/normalize.ts` handles this — called in both `session-reader.ts` (file load) and `handleAgentEvent` in `hooks/useAgentSession.ts` (streaming).

### New session tool preset
Tool names are passed at session creation (`POST /api/agent/new` -> `toolNames[]`) and persisted in versioned `pi-web:tool-selection` custom entries. No entry means a legacy session and keeps Pi's default behavior; an empty array means Chat only. Chat only resolves before services are created, loads no extensions/skills/prompts/themes, and replaces Pi's base prompt with the ordered contents of Pi's discovered context files. Crossing the Chat-only boundary rebuilds the wrapper; changing between nonempty presets updates it in place.

**Exact system prompts go through `before_agent_start`.** Since pi 0.86 the prompt lives in the transcript: `agent.state.systemPrompt` is a getter replayed from persisted system messages (assigning it throws), and the agent loop's request context has no `systemPrompt` field, so neither mutating the state nor patching `prepareNextTurnWithContext` reaches the model. Chat-only sessions and subagent profiles in replace mode register `lib/exact-system-prompt.ts` as an inline extension factory on the resource loader; its `before_agent_start` handler returns `{ systemPrompt }`, which the SDK projects as the provider's leading system prompt for the whole run while the transcript keeps recording Pi's structured sections. `get_state.systemPrompt` reports the exact prompt for those wrappers because the SDK state only shows the structured sections. Subagents persist their active tools plus profile-level skill and extension loading switches in `resourceSnapshot`; loaded extensions cannot expose the reserved `Agent`, `get_subagent_result`, or `steer_subagent` tools to a subagent. See `docs/adr/0002-chat-only-tool-selection.md`.

The last preset explicitly selected by the user is stored in browser `localStorage` and initializes fresh-session composers only. Existing sessions never trust that preference; they use their live `get_tools` state or pi's default when no wrapper exists.

### Fresh composer and quote focus

Explicit New actions request desktop composer focus once after the intended fresh draft mounts, with the caret after any restored draft. The request is bound to draft identity and navigation revision; mobile, visible modal/native dialogs, inline card/quote/picker ownership, subsequent pointer/key interaction and intervening control focus take priority. Covered/inert, hidden, disabled and composing textareas refuse the request. Ordinary mounting, session selection, polling and streaming never request this autofocus. The imperative focus handle changes only DOM focus/selection, not draft text or session configuration.

Ask here leaves selection/focus to the existing insertion path and never clears document ranges afterwards. Insertion retains the surrounding draft and puts the caret after the inserted quote, not after a retained suffix. Ask in new chat retains its distinct source-entry-ID and immediate-send lifecycle.

### Context-file change notice
A live ordinary session retains the context files (`AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`) loaded at startup or last session reload. `get_state` compares that snapshot to the SDK's read-only `loadProjectContextFiles()` discovery, so new, edited, removed, and newly overriding files offer a **Reload session** button in the selected chat. The browser polls while visible and checks on visibility return; it does not reload resources automatically or create a wrapper just to check. Chat-only sessions also load context files; subagents with context loading disabled do not show the notice. Other resources (skills, extensions, prompts, themes) are not monitored by this notice.

### Streaming display and client payloads

`lib/streaming-message.ts` retains the single reducer but publishes through a session-hook-owned `StreamingStore`, outside parent React state. `useStreamingSelector` uses batched state subscriptions and repairs the render/subscription gap in a layout effect. ChatWindow subscribes only to streaming/content booleans; its memoized `StreamingReply` owns chunk-level message updates and post-commit anchor measurement. Minimap measurements read a stable getter. Composer/minimap memoization does not promise to eliminate tool-progress renders while other props change. Transcript/entry-ID commits, run guards, receipts and blocking cards retain their original lifecycle.

Expanded thinking uses newline-aware 8,000-character pieces, hard-cut at about 16,000 without splitting surrogate pairs or losing blank lines. Ordinary answer copying is unchanged; native selection across hard-cut block boundaries may introduce line breaks. Stored/provider thinking is not rewritten. Individual pieces are not memoized, avoiding retained old sliced-string props. This bounds layout text nodes, not total loaded thinking or a measured RSS/time speedup.

`lib/message-signatures.ts` removes only block-level `thinkingSignature`, `textSignature` and `thoughtSignature` from copy-on-write assistant display projections: history, navigation trees, SSE start/end/toolcall-end and reconnect snapshots. Tool arguments and user/custom data are not recursively filtered. Original SDK/provider state and persisted replay entries remain unchanged.

### SSE reconnect on page refresh mid-stream
On `ChatWindow` mount, the initial history load also reads `GET /api/sessions/[id]/state`. The selected session maintains SSE automatically; live `thinkingLevel`, streaming and `isCompacting` state are restored from this response. Periodic recovery uses `GET /api/agent/[id]`.

Each agent SSE connection uses byte-based backpressure: beyond 512 KiB queued it drops only repairable message deltas and partial tool updates, never block starts/ends or control/receipt events. Authoritative end events repair the streamed content. `PI_WEB_SSE_BACKLOG_LIMIT_BYTES` selects the disconnect threshold (default 16 MiB; finite values at least 64 KiB). This is a backlog threshold, not a maximum frame size: an incoming frame may overshoot it, and the next non-droppable enqueue (including a heartbeat) errors the stream and releases its listener/liveness lease. Reconnection uses the existing snapshot/history/state reconciliation; it is not proof of instantaneous complete recovery. The pre-encoding check does not bound serialization or a single frame allocation.

### Compaction SSE events
Newer pi emits `compaction_start` / `compaction_end`; older versions emitted `auto_compaction_start` / `auto_compaction_end`. `handleAgentEvent` accepts both sets to keep `isCompacting` in sync. Manual compact is a blocking POST; both the toolbar and `/compact` show progress immediately, with SSE and authoritative state tracking the active phase.

While `isCompacting` is true, the composer shows an accessible, indeterminate **Compacting conversation…** status above the input, outside mobile More controls and independent of whether a prompt is streaming. It explains that earlier messages are being summarized, without inventing percentage/ETA. Previous success/error banners are hidden during a new compaction. Start/end events cover automatic, manual, cancelled and failed runs; initial GET state restores an in-progress compaction after reload. Recovery polling and visibility/network-return checks also run for compaction-only activity, so a missed end event or destroyed wrapper clears the status without manufacturing a completed prompt. The live region is not deferred behind a busy composer, including during `/compact`. Compaction-local read versions and phase generations supplement session/prompt guards: late initial or recovery snapshots cannot clear/resurrect a newer phase, and an older manual POST cannot hide a later SSE compaction. Recovery teardown invalidates pending reads. The indicator is UI state, never a persisted/model-context message.

### Transcript system messages, usage entries and context edits (pi >= 0.86)
- Every new session's first request persists a `message` entry with `role: "system"` holding the prompt sections and tool declarations; later prompt or tool changes append more. The agent loop announces them with `message_start` / `message_end` like any message. They are provider input, never conversation: `toClientAgentEvent()` drops them before the SSE stream (they carry every tool schema), `handleAgentEvent` skips any that slip through, `entryToUiMessage()` returns null for them, and `BranchNavigator` / `lib/project-tree.ts` never label or preview a branch with one. They still count toward `messageCount` and `totalMessages`, exactly as the SDK counts them.
- `usage` entries (`kind: "cache_warm"`) record prompt-cache warming that is billed but never enters model context. `computeSessionStats()` adds them like compaction usage so the token/cost counters match `/session` in the TUI.
- `context_edit` entries omit or replace an earlier entry's model context without changing raw history; the UI ignores them. A retain-none compaction stores its own id in `firstKeptEntryId`.
- `SessionManager.listAll()` now reads files newest-mtime first (then reverse filename) so `--resume` can render progressively; its stable sort keeps that order for sessions with equal activity time, and `listSessionsIncremental()` reproduces it from the stat fingerprints it already keeps.

### Incremental session-list scanning

`lib/session-list-scanner.ts` caches unchanged metadata and resumes growing files from a persisted LF-byte checkpoint. Before resuming it validates device/inode identity, the header and up to 512 bytes before the checkpoint. Full and tail reads share one accumulator: title changes/clears, all message counts (including system/tool messages), first user text, maximum user/assistant activity, newest valid archive marker (including restore), and first session-ID-validated spawn marker. The private atomic index is disposable version-2 metadata; old/corrupt indexes rebuild without modifying transcripts.

Detailed scans use one descriptor, bounded to its initial size. Changed identity/stat after reading prevents caching that result; the next listing rebuilds. Catalogue index owners are serialized across summary/detail and generation-invalidated scans. This is not a transactional snapshot against external writers. Truncation, non-growing edits and failed samples fall back to full reads. Sampling cannot detect same-inode historical edits outside the header/sample followed by growth; stale list metadata can persist until a non-growing change or failed validation forces rebuilding. It is not authorization or an integrity guarantee.

Incomplete trailing records are reread from their start. A parsed unterminated record counts immediately but disables resumption until a full scan, avoiding double-counting when its newline arrives. Byte buffering preserves UTF-8 across chunks and raw U+2028/U+2029 within JSON strings, matching the SDK file loader rather than Node 24 readline's separator behavior. CRLF/lone-CR parsing is retained. Oversized or non-first-line headers scan normally but do not create checkpoints.

Unchanged summaries reuse complete cached rows. Cold/changed summaries still read header/stat **and the whole transcript for archive markers**, so archived sessions never briefly appear active; they do not overwrite complete accumulators with pending rows. This port does not optimize cold archive discovery or make the separate summary header/archive reads transactional against external replacement. Index writes coalesce over a five-second window, capturing their destination and snapshot. The unreferenced timer never keeps a process alive; a lost save merely costs a rescan after restart. Relation/project resolution and catalogue enumeration/stat work remain outside the append-tail saving.

### Running state polling + reconciliation
- The sidebar polls `/api/agent/running` every 2.5 seconds while the tab is visible and pauses polling in background tabs. The session-list response remains the initial fallback.
- `invalidateSessionListCache()` bumps the generation but **keeps** the previous scan, and the cache is fresh only while its recorded generation matches. Ordinary agent activity invalidates it constantly, and rebuilding costs hundreds of milliseconds because `loadAllSessions()` re-reads every forked and subagent session. Callers that only need metadata — mapping search hits to sidebar rows — pass `listAllSessions({ allowStale: true })` to read the previous scan and let the rebuild happen in the background. A stale scan is a complete catalogue apart from sessions created seconds ago, so those callers accept a brief window where a brand-new session is not yet listed.
- `useAgentSession` treats per-session SSE as primary for chat events and opens it before each prompt. `prompt_done` completes the current UI stage and notification immediately, but the idle SSE stays open for a 30-second grace window and is reused by the next prompt. `agent_start` cancels that close timer; `agent_settled` finishes extension-injected runs that have no wrapper-level `prompt_done` and starts a fresh grace window. Do not close on the first `agent_end`: retries, compaction, and extension-queued messages can continue the same logical prompt.
- While a run is active, `useAgentSession` periodically calls `GET /api/agent/[id]` and also reconciles on `visibilitychange`/`online`. This fixes missed terminal events from background tabs or half-open connections.
- Prompt runs use a monotonic run id; late SSE or slow reconciliation responses from an old run must be ignored so they cannot resurrect stale streaming bubbles.
- Every SSE (re)connection in `useAgentSession` is gated on `sessionHookMountedRef`. React Strict Mode (on by default in `next dev`) re-runs effects in declaration order after a simulated unmount: the mount-only effect's cleanup sets that ref to `false`, and it is only restored when that effect re-runs, *after* the warm-session effect. The warm-session effect therefore re-asserts the ref before `maintainEventsConnected()`. Without it a dev-server tab never opened the event stream on mount or when switching back to a running session, so streamed output and new messages stayed invisible until the 15-second reconcile poll or a page refresh (`next start` was unaffected).

### Receipt reconciliation after canonical advancement
- Live receipt verification binds the displayed ancestor to the exact receipt leaf. If a concurrent canonical read changes that ancestor, the retry reads the current canonical branch without retaining the captured receipt leaf: the new ancestor may already be a descendant of that receipt. Only receipts returned by the revalidated branch are merged; the captured entry is not blindly appended. Session, navigation-revision and live-view guards still discard stale responses, and ordinary messages remain on their SSE delivery path.

### Receipt reconnects after archive/restore
- Archive/restore can append a saved marker while an idle startup is still opening the previous file, before its wrapper is registered. An anchored context read whose ancestor is absent from that wrapper probes `evictIfDiskAhead()` and reopens disk only if the idle index is provably behind. It then revalidates the full ancestry as usual. Ordinary reads and known sibling anchors do not probe; running wrappers are never evicted, and unknown or sibling ancestry still returns `409`.

### Moving sessions between projects
- The row's **Move to project…** action proposes a project and registered worktree/directory, or another existing directory through Browse, without changing the sidebar checkout. The route accepts distinct registered checkout roots within the same repository, but refuses the exact current directory, same-repository subdirectories and running families. A move changes the header cwd and the SDK session-file directory for the selected session and its nested subagents; forks stay in place, but any stored parent path pointing at a moved file is repaired (including subagent metadata).
- A missing source cwd does not prevent relocation: persisted history is outside the checkout. The route waives only source-root/registration checks for `ENOENT`, including removed/prunable worktrees; known same-repository destinations still require a registered checkout root. It does not recreate the old directory, and running/queued-family restrictions remain unchanged.
- `/api/sessions/worktrees` supplies history-only directory inventory, including session-referenced missing paths. The Sidebar's worktree filter is independent from the effective cwd, applies to search, and resets bulk selection. Filtered child-only matches remain visible using full-catalogue ancestry; missing paths are never admitted as working directories.
- `/api/sessions/move` previews and executes explicitly reviewed batches through the same family mover. Recovery selects all persisted missing-cwd roots/subtrees in the project, including archived sessions, and requires a verified primary checkout. Missing means `ENOENT`, not an omitted registration or inaccessible directory. Expanded membership and missing eligibility are rechecked before mutation; serialized plans are not admission authority. Batches are sequential and partial, not durable transactions or whole-project migration. Never automatically retry an unknown response.
- `lib/session-move.ts` stages all rewrites, backs up originals for rollback, installs destination files without overwriting an existing file, evicts idle wrappers, and refreshes both session-path and list caches. Never only change the header or only rename the JSONL: Pi's session discovery and parent references must stay consistent. Other Pi processes writing concurrently are not coordinated with this operation.

### Agent-created ordinary sessions
- The bundled Session Launch plugin exposes `start_session` only to ordinary coding sessions. It creates an independent wrapper through the host's ordinary startup/prompt admission, never forks/replaces the creator or borrows subagent lifecycle.
- Defaults copy current model/account, thinking, speed and built-in tool selection; explicit changes are exact proposals. Initial prompts are literal, and final SDK preflight revalidates effective text/configuration and policy before dispatch. Creator cancellation only owns pre-acceptance work.
- A host-only, single-use symbol capability is installed in the fresh wrapper constructor before registry publication. Pending ownership participates in `isRunning()` and excludes ordinary mutation, including tools/account replacement; status and extension UI responses remain permitted. Binding/admission awaits race permanent refusal and recheck ownership/liveness. Successful final admission synchronously releases exclusivity, restoring ordinary queueing and child independence.
- SDK 1.3.0 still can leave its busy flag/abort wait poisoned when final `preflightResult("started")` throws after awaited `before_agent_start`. Keep that final guard and its original exception: `refuseInitialPrompt(owner, error)` latches failure only for the matching pending launch, rejects acknowledgement/setup races, settles wrapper prompt bookkeeping once, and synchronously marks the wrapper unavailable. Late callbacks still throw; no run journal, `prompt_done`, or completion notification is created. Ordinary unguarded SDK/auth rejection does not retire its wrapper.
- Owned refusal alone bounds extension shutdown by `INITIAL_PROMPT_SHUTDOWN_GRACE_MS` (1000ms), then calls public `inner.dispose()` exactly once on success/error/expiry, without SDK abort/waitForIdle or private-state mutation. Timeout/disposal errors are logged separately from refusal. Identity-checked registry removal cannot unregister a replacement. `globalThis.__piOwnedRetirements` publishes a completion barrier by canonical persisted SDK ID before retirement callbacks; persisted-file startup and start locks resolve that ID rather than URL aliases, and wait before SDK resource construction. Successful public disposal releases the barrier; disposal failure remains a fail-closed tombstone across module/HMR reload. This prevents delayed old disposal from cleaning a replacement's SDK-ID resources (such as Codex WebSockets); independent IDs do not wait. Pending-owned `destroy()`/`shutdown()` immediately refuse outstanding admission and use this bounded path, even during binding or preflight. Ordinary/accepted wrapper `destroy()`/`shutdown()` retain their existing lifecycle. Disposal is invalidation, not proof arbitrary extension code/processes settled; retained files may be explicitly reopened, but refused initial prompts are never auto-replayed.
- `pi-web:session-spawn` stores stable created/creator/operation IDs outside model context. The created-ID check prevents attribution on copied fork/clone history. It remains a top-level ordinary session with receipt/header links, not a family parent.
- See [Session Launch](session-launch.md) for permissions, feedback, persistence and verification.

### Built-in subagents
- The global `builtInEnabled` switch is persisted in `~/.pi/agent/agents/settings.json` and defaults to `false` when the file or field is absent. Malformed settings fail closed; atomic updates preserve unknown fields.
- The inline built-in extension factory is always present so reloading an existing wrapper can apply setting changes, but it registers no tools while disabled. After changing the switch, the user must explicitly reload the current session.
- When enabled, only a recognized legacy `pi-subagents` extension that registers any reserved tool (`Agent`, `get_subagent_result`, or `steer_subagent`) is removed. Unrelated extensions remain loaded, and resolved conflict diagnostics are discarded.
- Runtime `Agent` dispatch checks the setting again so a stale tool call cannot start a subagent after the feature is switched off.
- See `docs/adr/0003-built-in-subagent-toggle.md` for the precedence and persistence rationale.
- Individual built-in profiles (`general-purpose`, `explore`, `plan`) are switched off by name in the same file's `disabledBuiltIns` array, never by copying them out to a `.md` file: a copy freezes the built-in prompt at the version it was copied from and is visible to the other runtimes reading those directories. `builtInProfiles()` stamps `enabled` onto the constants so the panel, the `Agent` tool description, and `resolveSubagentProfile` agree; each write is a minimal edit that preserves names it did not touch, including ones no built-in claims (a newer build's). Reading the list fails *open* — the feature switch beside it has already failed closed — while `PATCH /api/subagents/profiles` with `scope: "builtin"` performs the write and `PUT`/`DELETE` still refuse that scope. A same-name file replaces the built-in outright and is switched off through its own frontmatter. Only the switch is live for a built-in; the rest of the form stays read-only. See `docs/adr/0005-built-in-subagent-disable.md`.
- A background run's completion notification (`notifyParent`) is skipped when the parent already collected the same result with `get_subagent_result`: the tool marks a finished background run consumed and the notification takes that mark. The check cannot happen only when the completion promise resolves — the parent is usually still inside its `get_subagent_result` poll at that moment (500ms interval) and `deliverAs: "followUp"` would just queue the duplicate until that turn ends. So `notifyParent` holds the message while the parent `isRunning()` and re-checks the mark before sending; an idle parent is still notified immediately.
- Agent profile files (`~/.pi/agent/agents/*.md`, project `.pi/agents/*.md`) are shared with other runtimes, so a save round-trips the frontmatter keys this app does not own (`name`, `allowed_subagents`, `exclude_extensions`, `disallowed_tools`, …) and carries foreign `ext:` tool selectors through. Managed keys are exactly `description`, `display_name`, `tools`, `load_skills`, `load_extensions`, `enabled`, `inherit_context`, `run_in_background`, `model`, `thinking`, `max_turns`.
- A background run's completion reaches the parent through `sendCustomMessage`, and pi's `convertToLlm` replays every `custom` message to the model as a plain `user` turn. `subagentNotificationText()` therefore prefixes the report with `SUBAGENT_NOTIFICATION_PREFIX` so a compaction pass — whose prompt asks what *the user* wants — does not file the subagent's output under Goal / Constraints (#875). Foreground `Agent` and `get_subagent_result` results keep the bare `subagentFinalText()`: they are already `toolResult` messages and need no marker. Keep the prefix in code, not in a profile prompt, so the model cannot drop it.
- The `skills` / `extensions` spellings pi-subagents reads are seeded on first save and kept in step while they are booleans; a hand-authored whitelist such as `extensions: pi-advisor-flow` is never rewritten, and the two flags fall back to those aliases when `load_skills` / `load_extensions` are absent.

### Subagent extension selectors and default tools

`ext:` names resolve against loaded filename/parent/package aliases, including scoped and pinned npm sources. Extension names are case-insensitive; tool suffixes remain exact-case. Resolve the longest name before rejecting ambiguous grants; denials resolve across all claimants, so an ambiguous alias can narrow `ext:*` but never grant unrelated tools. Trailing `/` and `/*` mean the whole extension. Preserve authored grants and denials until spawn-time resolution, including deny-only and fully-denied profiles; do not turn an emptied allowlist into the legacy all-extension fallback. Saving preserves uppercase selectors and distinct tool suffixes such as `Search`/`search`.

Extension additions cannot reintroduce built-in profile-denied names (including PowerShell before shell mapping) or reserved subagent control tools. These name-selection rules do not sandbox extension code or uninstall replacement implementations. Ordinary-session sanitized Bash remains registered with `defaultActive: false`, so native `defaultTools`, explicit presets and reload—not extension registration—own activation. Native SDK regressions cover Bash-free startup/reload and explicit positive controls.

### Exported session HTML
- `/api/sessions/[id]/export` delegates to pi's export helper, then patches recursive tree helpers in the generated HTML to iterative versions so very deep linear sessions do not overflow the browser call stack.

## Pi Session File Format

Location: `~/.pi/agent/sessions/<encoded-cwd>/<timestamp>_<uuid>.jsonl`

```jsonl
{"type":"session","version":3,"id":"<uuid>","timestamp":"...","cwd":"/path","parentSession":"/abs/path/to/parent.jsonl"}
{"type":"model_change","id":"<8hex>","parentId":null,"provider":"zenmux","modelId":"claude-sonnet-4-6","timestamp":"..."}
{"type":"message","id":"<8hex>","parentId":"<8hex>","message":{"role":"user","content":"..."}}
{"type":"message","id":"<8hex>","parentId":"<8hex>","message":{"role":"assistant","content":[...],...}}
{"type":"message","id":"<8hex>","parentId":"<8hex>","message":{"role":"toolResult","toolCallId":"...","content":[...]}}
{"type":"compaction","id":"<8hex>","parentId":"<8hex>","summary":"...","firstKeptEntryId":"<8hex>","tokensBefore":N}
{"type":"session_info","id":"...","parentId":"...","name":"user-defined name"}
```

`entryIds[]` in `SessionContext` is a parallel array to `messages[]` — maps each displayed message back to its `.jsonl` entry id, used for fork and navigate_tree calls. Live ordinary `message_end` events carry that ID too: the wrapper defers delivery one microtask because the SDK synchronously appends after notifying its public listeners, and attaches an ID only when the saved leaf holds the exact message object. The hook commits content and IDs atomically, including when an unchanged optimistic prompt is consumed. Unsaved or unmatched messages retain an empty ID, never a guessed navigation target; newly saved prompts can fork while the source keeps running without a reload.

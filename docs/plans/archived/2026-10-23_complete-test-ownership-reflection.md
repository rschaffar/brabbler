## Inherent complexity versus process-created delay

**Inherent:** real React Strict Effects and default callers; ignored-abort bodies;
original work versus dispatcher ACK versus native settlement; preserving SAME
errors after independent cleanup; genuine Git/SDK/PTY/clipboard/browser/service
authority; composing shared files without losing concurrent additions. These
requirements found real false greens and cannot be replaced by “the UI passed.”
Nix realization also legitimately makes a cold diagnostic expensive.

**Process-created:** too much work in flight before consolidation; repeated
source→packet→review→private-control→execution→addendum cycles; shared-file variants
that needed repeated sparse rebinding; historical status documents masquerading
as current control; a core/RPC tangent before promised browser retirement; and
repeated guessed selectors, catalog strings, Strict replay counts, gutters and
fixture policy that failed before reaching the intended assertion. Some delegates
required repeated continuations; two stopped tasks produced no new packet and the
Web control stopped with an unrun assembler. Delegation did not reliably shorten
the path to a usable candidate.

**Yes, the process became disproportionate.** At the assessment's start, the
retained root had 440 top-level `*-source` directories, 847 top-level `.log` files
and 91 top-level Python/shell helpers; the active plan had 674 lines. These are
metadata counts, not counts of failures, wasted runs or attributable hours. Many
controls were valuable, but their growing protocol and publication burden was not
itself progress toward removed Chromium work or complete-feedback speed. There is
no defensible total-hours attribution in the available evidence.

The strongest counterexample is Files: substantial qualification machinery still
missed an emergency-release hook invalidating an existing held-Save input. Better
review of the actual receiving contracts mattered more than another generic
marker/vector witness. Preserve that finding; stop expanding generic theorems.

## Keep, stop, change

**Keep:** actual production owners; exact old-input maps; finite meaningful faults;
original failures and source bindings; independent safety review of changed risk;
real installed/native bridges; the existing Nix entry points, deadlines and gates.

**Stop:** coverage/control counts and effort percentages as completion proxies;
whole-journey retention; rediscovering known fixtures; automatic extra controls for
every observer; speculative universal cleanup/idle proofs; RPC/cache/platform
expansion by default; duplicate full acceptance for a new commit ID; and copying
chronology into several “current” documents. The previous rough 91% effort figure
must not guide remaining-work estimates.

**Change:**

1. One parent-owned working candidate and one active implementation slice. Review
   that coherent slice, reuse earlier findings and integrate promptly after its
   gate; do not grow a queue of independently versioned source-only packets.
2. Name each blocker, owner, decisive evidence and stop condition once in the plan.
   Reuse passing controls by exact relevant inputs; add proof only for an uncovered
   changed contract. Preserve necessary distinct failure schedules, not quotas.
3. Resolve selectors/catalogues/fixture policy from actual source before expensive
   execution. A setup failure is a diagnosis, not a meaningful product fault.
4. Use the runner's immutable export and one result record per candidate/selection.
   Extra private variants need a concrete counterfactual purpose. Preserve existing
   roots without manufacturing more just to publish the same result again.
5. Take a whole-feedback checkpoint at the first coherent candidate. The known
   core branch already exceeded 351.05s; browser-only cuts cannot be assumed to
   solve that. If core still blocks, report it and seek a bounded decision before
   reopening deferred core work. Never substitute core optimization for browser
   retirement or spend indefinitely polishing focused speed.
6. On a failed gate, diagnose the exact cause and narrow/replan. If the needed next
   step expands policy, framework or scope, stop for a user decision. No unchanged
   retries, weaker proof, widened budgets or deadline inflation.

## Guidance applied and broader proposals

Repository-local changes make plans current control documents, distinguish
verification states, constrain work in flight and reuse evidence proportionally.
The authoring guide also distinguishes intentional observer unmount from terminal
teardown. These changes do not relax acceptance or Git safety. Existing dirty
browser-retirement guidance was reviewed and retained intentionally; the historical
census is explicitly not a live pending-work list.

**Broader/global proposals only:** encourage an explicit WIP limit and
contract-specific evidence reuse across projects; require delegation deliverables
to fit actual capabilities; and stop full-suite reruns caused solely by status
commits. Much of this is already supported by global/repository guidance—the
failure was execution discipline, not simply missing rules. No global policy or
permissions were edited, and no risk-based acceptance waiver is proposed as an
implicit fix.

**Known gaps:** No current whole-candidate acceptance or speed result exists;
source-only and partial work remains. No new tests, benchmarks or subagents were
used for this assessment.

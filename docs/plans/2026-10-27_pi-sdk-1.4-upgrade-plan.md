## Pre-upgrade assessment — verified source evidence, not runtime acceptance

**Decision: not a dependency-only bump, but no broad application migration is
currently justified.** Two version-pinned integrations definitely require changes.
Keep all other production adapters unless a targeted regression demonstrates a
necessary adaptation.

**Implementation amendment:** the two known version guards were not the whole
behavioral delta. Real native regressions additionally demonstrated late worker
admission for already-queued retired owners and explicit builtin-pin loss through
both RPC and extension-command tree navigation (the latter is inherited from 1.3).
The candidate now cancels/drains native execution results and reapplies only the
builtin pin through one guarded public navigation adapter. Existing context guards
already blocked new nested external-tool dispatch after shutdown; the queue red
proves late pure-script/worker execution, not an external-effect bypass. Result
drain is not worker-exit proof; fixture observations join actual exits separately.

## Rollback / recovery

Before integration, keep main/service unchanged and retain the feature if blocked.
Recover from an interrupted owned patch install only through the existing recognized
whole-file-state repair; unknown bytes are not repairable by widening fingerprints.
Reverting the upgrade means restoring the **coherent** 1.3 package/lock/cache hash,
patch/bridge guards and associated code together, not downgrading only the manifest.

No storage migration is planned. Tests use private synthetic histories, not operator
sessions. New 1.4 recovery may append context edits even though the format stays v3;
source review alone does not certify replay of every such history after a downgrade.
Any eventual host deployment/rollback requires separate user authorization and
ordinary private data backup/activation procedures; local integration is not deployment.
